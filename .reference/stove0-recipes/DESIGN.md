# Stove0 recipe language: replacement design

External reference for [#953](https://github.com/nashspence/riverhog/issues/953), under [#903](https://github.com/nashspence/riverhog/issues/903). Audited `main`: `802ed38225b4ecd9aacd1b7dc3de51a1b1fd1905`. This is proposed implementation input, not a second contract authority. The owning issue and subsequent maintainer decisions control. There is no compatibility or migration requirement.

## 1. Design thesis and boundaries

A recipe is a reusable, declarative **workflow definition**. It describes questions, classification, association, conditional calls, collection composition and source disposition. It is not an execution record, deployment file, script, event subscription or another storage ontology.

One semantic language has two representations: `RecipeSource`, written by people, and `CompiledRecipe`, a closed and normalized definition interpreted by Stove0. A compiler is a boundary, not a second runtime. The execution engine consumes only compiled definitions. No old reader, legacy spelling, source interpreter or parallel planner survives the cut.

The definition/work/attempt distinction is essential. A recipe defines policy. Existing `WorkIdentity` identifies one invocation on exact finalized roots and parameters. Observation questions, approved workflow plans and execution envelopes identify the actual bound work. Retry attempts, leases, cursors and physical batches are operational records, not new recipes.

The language must express current Stove0 capabilities without converting it into a general workflow platform. Observation tasks form an acyclic read-only graph, followed by deterministic decisions and a required fork of operation/subrecipe calls, optionally followed by one exact materializing join at each recipe level. Recursive recipes provide composition. No arbitrary target-output-to-observer edge, loop, race, event gateway, compensation engine, embedded expression language or unrestricted DAG is introduced.

## 2. Vocabulary and standards alignment

Use **recipe**, **observation task**, **input**, **role**, **input group**, **condition**, **call**, **fork**, **join**, **export**, **work**, **settlement**, and **source retirement** consistently in Python, CLI help and generated reference. Retire author-facing `route`, `coordination route`, `artifact rule`, `projection`, and ambiguous `no action` where the new terms apply. Wire types can change in this hard cut; names should describe their owner and meaning, not preserve obsolete implementations.

The closest precedent is [CWL v1.2 WorkflowStep](https://www.commonwl.org/v1.2/Workflow.html#WorkflowStep): named steps, explicit data inputs, conditional execution and subworkflows. Borrow those concepts, not CWL command execution, JavaScript, file-path ontology or scatter. A group-filtered branch here runs once with its complete accepted group set; it is **not scatter**, which creates separate executions for array elements.

[BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/PDF), especially Call Activity (§10.3.6), Inclusive Gateway (§10.6.3), and Parallel Gateway (§10.6.4), clarifies three distinctions: a reusable child definition, all matching conditional branches, and synchronization. A Stove0 fork is an inclusive selection: every true branch is required. Its completion barrier waits for all selected branches. A Stove0 `join` is additionally a declared operation producing a collection, not merely that barrier. No token-engine conformance is claimed.

[Open Workflow DSL](https://github.com/open-workflow-specification/specification/blob/main/dsl-reference.md), formerly CNCF Serverless Workflow, supplies recognizable `call`/`fork` vocabulary and reusable components. [PROV-O Plan and Activity](https://www.w3.org/TR/prov-o/) reinforces definition versus execution. These are terminology sources, not imported runtime requirements. Riverhog remains the owner of its actual provenance, identities, authorization and settlement contracts.

An observer reports facts; an observation task asks one particular question of an observer. Multiple tasks can use the same contract and provider with different options. A role describes how a recipe uses an exact member; it is neither a MIME type nor member identity. An input group is one primary member plus specifically related associated members. An export is a named collection result, never an implicit union of branch outputs.

## 3. Documents and ownership

### RecipeSource

The proposed format is `stove0-recipe/v1`. This is the new pre-v1 surface, not a versioned upgrade path. Its complete syntax is generated by `language.schema()` in this reference. That generator is a design prototype; production must derive schema and help from the executable compiler authority.

Top-level fields are `format`, `id`, `revision`, optional `description`, `parameters`, `roles`, `observe`, `classify`, `groups`, `decisions`, `fork`, `join`, `export`, and `source`. Only `format`, `id`, `revision`, and at least one nonempty `fork` or `decisions` are required. Recipes can be stored as separate YAML files; a stream is useful for examples, not a new runtime batch ontology.

Local names match `[a-z][a-z0-9_-]*`. Semantic IDs retain the audited protocol domain. Local names are unique within their named section. A view reference is `task.view`. Observer/operation/child resource aliases are resolved at compilation, not looked up at runtime.

YAML is the JSON-compatible YAML 1.2 subset: string object keys, ordinary JSON scalars, arrays and objects; duplicate keys, aliases, merge keys, custom tags, non-finite numbers and non-JSON scalar types are rejected. There are no textual includes, environment substitution, executable tags, YAML inheritance or hidden overlays. Named resource reuse and explicit subrecipes provide composition. Comments and the top-level description are non-semantic.

### Dependency catalog

A deployment compiles recipes against a local catalog of **exact documents**. It maps readable aliases to one of:

- Observer resource: exact observer contract `{id, sha256}` and exact observation interface `{id, sha256}`.
- Operation resource: exact operation contract `{id, sha256}`.
- Recipe resource: exact compiled recipe `{id, revision, sha256}`.

The resolver verifies each supplied document and the full transitive closure. An alias is not a version constraint, URL import, capability search or mutable `latest`. Required contract and interface bytes must be available offline to compilation/installation. Different revisions of one operation ID can coexist under different aliases because resolution is by exact identity, not ID alone.

The catalog is an authoring/installation input, not the recipe's runtime environment. Unused catalog entries do not affect a compiled recipe. Recipe graph nodes retain their local task/branch IDs for diagnostics and work binding, while resource and role aliases are replaced by exact semantic references. Recipe dependency cycles are rejected iteratively without a semantic depth ceiling.

### Deployment bindings and execution profiles

Endpoints, credentials, token files, provider registrations, transport settings, scheduling, subject batch size, concurrency, result transport budgets and retry timing belong to deployment/runtime configuration. An optional task/call `executor` is a **logical provider-binding requirement**, not an endpoint or executable command. It is retained in the compiled recipe; the selected provider must satisfy its exact contract. An omitted executor leaves provider selection to installation/invocation policy and the approved binding record, never to an unrecorded runtime guess. Observer tasks as well as operation calls support this requirement.

Semantic question options, requested operation intent/options, permission to retrieve, output policy and source-loss/retirement policy remain recipe-owned. Do not move `preset`, destination identity, observer options or permission to initiate retrieval into an uncommitted mutable profile merely because they sound operational. Conversely, do not let batch size or timeouts become recipe identity. This separation follows the configuration authority in #492.

The approved preview/plan binds actual descriptors, resolved output-placement policy where necessary, and execution settings. Existing work resumes against that approved meaning. A provider upgrade or changed deployment default requires a new approved plan/invocation when it changes a bound choice; it cannot reinterpret an accepted plan. Transient credentials may rotate within the existing capability contract without mutating semantic identity.

## 4. Normalization and identity

Compilation produces an envelope of the following conceptual form, with a separately retained exact dependency closure:

```text
CompiledRecipe {
  format: "stove0-compiled-recipe/v1",
  id, revision: positive exact decimal string,
  language_profile: exact compiler-semantics profile,
  parameters_schema: closed local schema,
  observations: normalized task-ID map,
  classification: ordered cases and otherwise,
  groups: normalized group-ID map,
  decisions: ordered decision list,
  branches: normalized branch-ID map,
  join: exact join definition or null,
  export: explicit export definition or null,
  source: explicit source policy,
  dependencies: canonical unique exact references
}
```

`sha256` is outside its own payload. Hash the complete normalized payload using the repository's canonical JSON/exact-scalar authorities, with the format and semantics profile included for domain separation. Reuse those authorities; do not implement hashing with `json.dumps(sort_keys=True)` or a new approximate numeric codec. Validate recursively before hashing. The reference linter does not implement this encoder or assert golden hashes.

Both integer source revisions and canonical positive decimal strings normalize to the exact wire string; booleans, leading zeroes and floating revisions fail. Known exact-integer fields follow the owning scalar contract. Arbitrary JSON values in options/intent retain their declared JSON types and existing canonical-JSON domain: do not globally stringify numbers or coerce `true` to `1`. Duplicate semantic role IDs under aliases should be rejected as misleading.

Materialize language defaults once: empty options/intent/evidence/bindings, `retrieve: available-only`, default role `source -> stove0.source/v1`, classification `otherwise: source`, branch `select: all`, condition `true`, source unmatched `retain-in-source`, retirement `retain`, and retirement grace `0` when retirement is selected. If custom roles omit `source`, require explicit classification. `parameters` omitted means a closed empty-object parameter contract; arbitrary parameters require an explicit schema. JSON Schema annotations do not apply values: parameter defaults are not inserted implicitly. Runtime parameter values must satisfy the declared contract.

Keep external contract documents and their digests exactly as owned. Only the recipe language's designated documentation annotations are omitted from recipe identity; do not rewrite external schemas to preserve hashes. Parameter-schema documentation can be normalized through the same explicit semantics profile; no guessed annotation removal at arbitrary JSON locations.

Named maps and set-valued arrays normalize independently of author order. Sort task dependencies, role sets, forwarded task names, join members/output-role sets, and disjoint bindings. Preserve classification case order, relationship preference order and no-output decision order because their precedence changes meaning. Literal JSON arrays in intent/options are never sorted generically. Preserve local task/branch IDs because they bind evidence and child work, even though catalog alias spelling is erased.

A change to an exact operation/interface/observer/subrecipe dependency changes the recipe digest. A catalog alias rename that resolves to the same closure does not. Comments, map ordering and physical batching do not change semantic recipe/work identity. Physical request IDs, evidence sets, descriptor bindings and plan hashes **may** change when physical batching/provider binding changes; do not falsely promise identical evidence hashes across different request partitions. Provenance must still identify the actual approved requests and results.

The compiled representation must be readable and verifiable without original source files or mutable aliases. Persist/archive enough exact dependency documents to interpret it. Its semantics profile is pinned; adding a future compiler default cannot change an existing compiled definition.

## 5. Observation and classification graph

`observe` is a map of observation task IDs. Each task names `use`, optional `executor`, `options`, `retrieve`, named `inputs`, and optional ordering-only `after`. Input ports are declared by the exact observation interface. Subject-port values are `all` or `{roles: [...]}`; evidence-port values are `{evidence: task}`. Omitted `inputs` means `{subjects: all}` only for an interface with that single subject port. There is no positional port binding.

The compiler constructs a graph containing task nodes and a classification node. Evidence input references and `after` create task dependencies. Role-filtered subject ports depend on classification. Classification conditions depend on their referenced observation tasks. Detect cycles in this combined graph, including the common error of classifying from a role-filtered task that requires the classification it is supposed to establish. Report the dependency path, not merely `cycle`.

Classification cases are evaluated in source order for each exact input member; the first true case assigns its role. `scope: self` is that exact member before role assignment. It cannot filter on the role it is defining. A complete false permits the next case. An indeterminate earlier case cannot silently fall through to a default role. `otherwise: null` leaves a member unclassified; it remains in the original inventory and source obligations.

Task completion is identified by `(work, task ID, logical question/scope identity)` and a complete accepted evidence set, not registration ID, contract ID, arrival order or first completed batch. Repeating an observer registration/contract across tasks is valid and must remain distinct throughout requests, checkpoints, forwarding and preview.

An empty subject selection is an explicit completed-empty logical task when the interface permits this identity result. Do not issue an invalid empty observer request, fabricate an observed result, leave a successor blocked forever, or evaluate a global question without its required evidence. Interface-specific global questions may instead be inapplicable. Physical batching only partitions a valid complete question as permitted by its interface; pairwise relations needing whole-scope semantics cannot be naively batched into independent negatives. Progress and storage are paged without imposing a logical-total ceiling.

Accepted evidence and normalized fact/relation views are described in OBSERVATION_INTERFACES.md. The controller may validate/project declared representations; it never inspects bytes, invents filename semantics or substitutes unaccepted cached facts.

## 6. Conditions and value semantics

Predicates are a closed AST. Boolean literals and `all`, `any`, `not` compose facts predicates. A facts predicate specifies `view`, `scope` (`input`, `candidate`, or `self`), optional role filter, explicit `quantifier` (`any`, `every`, `none`) and a row predicate. No implicit field lookup or string expression evaluation occurs.

A row predicate contains Boolean composition, `test`, or `items`. `items` binds a nested array element before evaluating its complete child predicate, so two comparisons under one `all` must match the **same element**. Literal JSON comparison values are data even when keys are named `facts`, `not` or `items`.

Conditions use true, false and indeterminate. Malformed/forged evidence or violated contracts is an error, not a truth value. Missing/unaccepted/partial evidence is indeterminate and blocks any decision needing it. Negation maps indeterminate to indeterminate. For valid inputs, Boolean composition follows strong three-valued logic: false dominates `all`, true dominates `any`; otherwise an unresolved operand propagates indeterminate. Such logical reduction does not waive validation of supplied evidence or required task completion.

`any` requires at least one matching record. `every` is deliberately non-vacuous: for subject-keyed views each selected subject must have at least one record and all selected records must match. `none` requires complete evidence and no matching record. Complete empty domains give `any=false`, `every=false`, `none=true`; missing evidence is not an empty domain. A global view quantifies its declared global records and cannot be relabeled as per-member coverage.

`eq` and `ne` use type-sensitive JSON equality through the canonical scalar authority, not Python equality (`true` is not `1`). `in` requires a nonempty literal list and equality to one element. `contains` means literal array membership or literal string substring according to declared types; it is not a regex, path glob or recursive search. Wrong operand types fail validation. `exists` requires a Boolean expected value and answers field presence only within a verified complete record. A missing field makes other comparisons indeterminate, not `ne=true`. Present null is distinct from missing. An absent/ill-typed `items` array is not a complete empty list. JSON Pointer escaping follows RFC 6901; array indices are exact, no wildcard or implicit flattening.

Global decisions use only input scope. Classification can use self/input scope. Group-selected branch conditions can use candidate/input scope; whole-input branches cannot refer to a nonexistent candidate. A candidate role filter must be among that group's primary/attached roles. Scope/type compatibility should be checked against interface schemas at compilation and verified against actual data at planning.

## 7. Input groups, fork and calls

`groups` names reusable input-group construction. `primary` names one role, `attach` names associated roles, and `prefer` is an ordered list of relation views. Resolve each associated member to at most one primary according to the declared tiers. Only a complete negative from a stronger tier permits weaker fallback. Unsupported, ambiguous, insufficient, unavailable or malformed stronger evidence does not. Exact endpoints refer to member instances; equal bytes or filename stems never collapse identity.

A primary with no associated members can still be a group. When a relationship blocks a primary, do not silently execute it without the uncertain associated input. All excluded, blocked and unclassified members remain visible in coverage/explain output and source accounting. Preference changes are semantic changes.

`fork` is a named map of branches. Each branch selects all classified subjects or a named group set, optionally filters it with `when`, and makes one call with the aggregate accepted selection and exact input groups. Evaluate all branch conditions; retain intentional overlap. A group set is not N independent work items. Every selected nonempty branch becomes required ordinary child work; no branch is optional after sealing.

An operation call resolves an exact operation contract. `intent` is portable desired behavior; `options` is explicitly requested target-specific behavior. `executor` optionally constrains provider binding. Input role/cardinality, intent/options, result kind, evidence and output policy are validated against the exact operation/provider contract at the appropriate compile/preflight boundary. Do not invent missing operation defaults in Stove0; use the owning contract and record the accepted effective request.

`evidence` selects named tasks, preserving their original accepted request/result identities and declared scope. Multiple tasks sharing a contract remain distinguishable. A target must validate the relevant exact questions/options; it must not take the first matching contract ID and silently ignore other tasks. Ambiguous evidence use fails closed unless the exact operation explicitly defines how it is consumed.

A recipe call invokes an exact compiled child recipe with selected roots **and the separately bound exact member selection/groups**, not the entire contents of those collections. Parent binding, decision identity and child parameters are explicit. A recipe call has no target descriptor, target options or output-placement override; descendant calls own those. Child parameter bindings use only the portable child intent destination. Child recursion is finite and cycle-checked, without arbitrary depth limits.

### Explicit parameter/evaluation bindings

`bind` copies one JSON value from `parameters` (the work's effective intent) or its existing evaluation binding, using `path`, into `intent` or `options` using `at`. Missing sources are errors; JSON null is a value. There is no automatic fallback or string interpolation. Decisions requiring an evaluation field are inapplicable/error outside the expected invocation context, not silently populated with null.

Start with literal destination objects. `insert` requires its target field absent and may create absent object ancestors; `replace` requires its target present; `merge-object` requires existing destination and source objects and performs an **explicit shallow merge**, source keys winning. This named operation preserves the existing useful root-options merge for Review0 without pretending it is recursive merging. Non-object ancestors, array mutation destinations and overlapping binding destinations are rejected. Reads may traverse arrays; writes address object fields only. Root insert fails because the root exists; root replace/merge requires an object. Normalize bindings by decoded destination path after proving they do not overlap. Static literal-versus-binding collisions follow the selected mode and final documents are schema-validated. No last-write-wins list ordering.

## 8. Decisions, join, export and outcomes

Ordered `decisions` run after their complete required evidence is available and before irreversible operation execution. The first true `no_output` rule explicitly succeeds without a target. A pure decision recipe is valid. If no decision matches and no branch is selected, work is inapplicable; an empty fork is not implicit success. An indeterminate earlier decision cannot fall through into destructive work.

A no-output decision has a semantic code, human explanation, exact supporting evidence and optional per-member source-loss rule. It is not an empty collection, a failed target, a skipped join input or generic permission to discard bytes. Nested no-output produces a required successful no-output branch record.

A `join` names at least two distinct branch IDs and required output role sets, then calls one collection-producing operation. Those branches must be statically collection-capable: an operation with collection result, or a child with a declared collection export. Effect and no-export children cannot be members. At planning, every named member must actually be selected and capable of yielding the required collection for that selected child plan. A child's no-output decision makes that exact consuming join inapplicable. Never shrink a join's member set or merge whatever happened to finish.

Non-member branches remain required for parent completion. The join may become ready once its exact member settlements are successful; parent success still waits for every selected branch and the join. All joins consume exact settled branch collections/output-role selections and retain those inputs. A materializing join cannot run as an external effect, introduce retirement of branch sources, or absorb unrelated descendant outputs.

`export` is `join` or `{branch: name}`. It exposes exactly one collection and its producer settlement. It does not manufacture a new collection, flatten a child tree, export effect receipts as collections or rename archive authority. A child with a single output operation can explicitly export that branch without a dummy join. A child with several outputs exports one explicitly; no count-based heuristic applies. At a normal selected plan, a declared export must resolve; otherwise the plan is inapplicable before target execution. An explicit no-output decision bypasses export with a typed no-output result, not a false collection promise.

A recipe without export can coordinate multiple outputs/effects. Those outputs remain individually inspectable and settled; the recipe simply supplies no aggregate collection to a parent. Evaluation/Review0 that requires one collection must require an explicit export. This changes presentation/typing, not archive materialization semantics.

## 9. Source accounting and retirement

`source.unmatched` chooses retain-in-source or reject-work. `source.retirement` is either `{mode: retain}` or `{mode: after-settlement, grace_seconds: N}`. The latter is permission to consider retirement, never a command to delete after a successful process exit.

Keep the complete original immutable inventory separate from classified/selected members. Compute coverage over exact member identities, including intentional overlap. Unmatched/blocked members cannot disappear from accounting. Root retirement requires complete exact per-member disposition/settlement, applicable operation permissions, affirmative source-loss evidence for approved no-successor outcomes, the declared grace period, and ordinary Riverhog authorization/deletion checks. External effects require exact receipts and the existing effect-settlement authority.

Only root work can request source retirement. Child recipes' root-retirement preferences are suppressed in parent-bound execution and exposed as such in explain/plan output; they cannot delete their parent's shared sources. Suppression does not synthesize source-loss approval. A parent requesting retirement must validate the descendant disposition/permission closure, including no-output paths that lack successors. Use the actual Riverhog retirement authority rather than inferring permission from result kind, a target's name, collection export, or a generic Boolean in a mock catalog. Join operations consuming derived outputs do not independently grant permission to discard original inputs; do not broaden deletion authority during this refactor.

Every selected source-loss evidence requirement must be satisfied for **each exact discarded member**, by its pinned observer/interface/facts/semantic profiles and exact affirmative verdict. A global Boolean, whole-document match, missing record, unknown status, successful no-output code, or `none` over absent data is not such a proof. Preserve this rule even when a nested child declared its own source policy as retain.

## 10. Full invocation and lifecycle support

Explicit work may consume multiple finalized collection roots. The former `event_input_closure: single-finalized-collection` was admission-event closure, not a universal one-root restriction. Admission and departure continue to own event/catalog selectors, activation baselines and dispatch policy outside recipes. Their selected recipe identities and parameters go through the same compiler/preview/create path as explicit work.

Evaluation matrices, sample plans, variants and Review0 remain existing typed invocation contexts, not recipe-side loops. The binding mechanism must express current review sample plan, variant ID, portable variant intent and requested target options. Output tags/store/cache/copy policy remains explicit and follows Riverhog's owning definitions. No policy from qualification fixtures is silently promoted to a deployment default.

Preview must resolve the same semantic program as create/execution. Approved branch selections, groups, decisions, exports, exact operation/provider choices and loss/retirement obligations are immutable. Persist task identity, logical scopes and accepted evidence sets so restart cannot merge two same-contract tasks or accept partial completion. Preserve fencing, cancel/retry convergence, checkpointed nested planning and bounded pagination. A provider failure or resource quota is not an absent fact or a recipe-format error.

## 11. Compiler phases and diagnostics

Implement a single authority with phases: parse/source locations; structural validation; name and exact-document resolution; interface/parameter typing; combined dependency and recursion checks; call/group/condition/binding/source-policy validation; default expansion and canonicalization; closure verification; emit immutable compiled definition plus explain/source map. The source map is non-semantic auxiliary data, not part of the recipe digest.

Reject statically provable errors at installation. At invocation resolve parameter values, exact inventory and approved deployment bindings. At planning verify accepted evidence, predicates, groups, required joins/exports and source coverage. At preflight validate final operation requests. At settlement/retirement use the existing owning authorities. Do not require compile time to know actual artifact cardinality, content facts or future target results.

Diagnostics identify source path and local name, expected contract/view type, actual binding and the violated invariant. Explain output distinguishes complete-negative, indeterminate, excluded, blocked, selected, no-output, exported and retirement-pending. CLI should expose validate, compile and explain from the same production authority; API recipe views should distinguish source presentation from compiled semantic identity. Defaults and schemas should be inspectable without inspecting Python validators.

## 12. Integration exit

Re-express existing witnesses against the new language and compare semantic selections/decisions/obligations, not old source or request hashes. Replace all consumers and regenerated baselines together, delete old types and parser paths, and qualify on the actual integrated SHA. The reference's grammar checks are not a production compiler, canonicalization proof or runtime qualification. See CONFORMANCE.md for the feature account, required adversarial vectors and ownership map.
