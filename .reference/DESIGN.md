# Original native worker exit receiving

## Recommendation

Retain the native thread handle from creation through positive operating-system exit receiving, and record that result in the native owner before returning to Python. Core must use that one receipt for status, collection and shutdown retries. A completed Future remains the original semantic outcome; it supplies no exit authority. Submission must return after the one native creation call: runtime initialization, pending registry drains and bootstrap acknowledgement belong to the original worker and must not delay coordination. Collection separately accounts for the completed original's bounded weak-reference retirement.

The proposed shared owner lives in `retained-resource`, which Core already depends on. Linux creates a **joinable** pthread and makes at most one `pthread_tryjoin_np` call per receiving probe. The Windows draft retains the `_beginthreadex` handle and polls it with zero-timeout `WaitForSingleObject`, then receives the handle close. Native errors retain the original owner in quarantine. There is no worker reconstruction, replacement Future, thread-ID lookup or Python-sentinel fallback.

This revision addresses the [direct startup follow-up](https://github.com/nashspence/riverhog/issues/1005#issuecomment-7102561968) to the focused [#1005 request](https://github.com/nashspence/riverhog/issues/1005). It supersedes reference `3dce6780c4883ad96cb32ff3f7ef80883fef6528`, which the integration agent partially used for source review and independent reproduction without adopting it. It remains concrete input under [#903](https://github.com/nashspence/riverhog/issues/903), not an acceptance decision or a replacement durability design.

## What the source and experiment establish

The audited `PhysicalExecutionOwner` creates a Python `Thread`, treats `is_alive() == False` as exit, invokes `join(0)`, and then removes the original slot when its Future is complete. Removal refunds global lane and per-target allowances. `close()` uses blocking Python joins outside the registry lock. This implementation is byte-identical on authoritative main, the issue's `fee80a186ae31765addfbd4b2e3f877f9eb8b286`, the prior experiment's `3d039b382ee33d66c6049dd69e498169aa75bf6d`, and this revision's integration checkpoint `0b25c7c67f7b3ee8787d8d753d4b6d585e8cea1f` (blob `ef161cde4353ef80401796a526702f1b2c8d7b73`). The newer checkpoint changes two finalization-test files outside the proposed paths.

The maintained subprocess probe executes this actual owner. It waits until the real Future is published, holds either the original target tail or a `threading.local` finalizer, observes the original native task, and sends SIGINT only after the coordinator enters its actual join frame. On unchanged source, the worker is reported dead and one outcome is returned while the native task still exists. Both capacity charges disappear prematurely. The proposal keeps the slot and charges through two interrupted shutdown retries, then receives the same outcome after explicit release and actual native exit. A separate consumer probe holds the real retirement directory phase and lease namespace through interruption. These observations are recorded separately from the injected lost-reply cases.

The previous reference's native receipt survives that interruption, but its Python `Worker.start()` still waits repeatedly for `_started` while Core holds the shared execution lock. The integration agent independently demonstrated that a held bootstrap blocks submission, makes an already-exited independent original appear busy, prevents its collection, and refuses fresh work despite spare capacity. This revision maintains that controlled delayed-bootstrap witness against the exact previous wrapper and Core files, verified from the immutable reference manifest. The native C implementation is unchanged. Passing-after cases cover both collection and workspace execution, real SIGINT after native creation, and bootstrap exit before acknowledgement.

The source was not reset to a reference or modified on the integration branch. The reference's product paths stay on main; its patch was implemented and tested in an isolated checkout of the identified integration checkpoint.

## Why a native owner is necessary

[CPython issue #90882](https://github.com/python/cpython/issues/90882) documents the same false-dead observation: an interrupted join can release a thread-state sentinel it did not acquire. Retrying that Python join or rechecking `is_alive()` cannot recover independent native-exit evidence. The issue's later discussion identifies the changed 3.13 implementation; this does not repair the repository's pinned 3.12.3 runtime.

[CPython 3.12.3's pthread launcher](https://github.com/python/cpython/blob/v3.12.3/Python/thread_pthread.h) explicitly detaches the pthread it creates. Therefore a wrapper cannot safely attach `pthread_join` to an existing ordinary 3.12 Python Thread. The proposal must own a joinable native worker from the beginning.

A target-return event, Future callback or Python finalizer flag is earlier than native exit. Returning from a pthread start routine invokes thread exit and its thread-specific destructors; successful join is the termination observation ([pthread_exit](https://man7.org/linux/man-pages/man3/pthread_exit.3.html), [pthread_join](https://man7.org/linux/man-pages/man3/pthread_join.3.html)). The fault-native witness holds a real pthread TLS destructor after Python thread-state cleanup and native entry return. Linux polling stays pending until that destructor is explicitly released.

An upgrade or backport also needs two separate proofs: interruption-safe exit receiving **and bounded polling**. In [CPython 3.13.0's `_threadmodule.c`](https://github.com/python/cpython/blob/v3.13.0/Modules/_threadmodule.c), the timeout covers waiting for `thread_is_exiting`; that event is set before the native start routine returns. The code then calls blocking `PyThread_join_thread`. **Inference from that source ordering:** a held native TLS destructor can make the final native join block even after the event, so simply substituting that handle's `join(0)` is not a proof of this repository's zero-wait polling requirement. This packet neither benchmarks newer runtimes nor claims they are unsuitable for every use.

## Proposed ownership boundaries

| Owner | Responsibility | Authority it does not gain |
|---|---|---|
| Native `WorkerHandle` | Original process/interpreter, exact native handle, startup result, positive exit/handle receiving, unexpected bootstrap exception, primitive counters | Semantic success, resource closure, current authorization, durable cost settlement |
| Python `Worker` | Fixed pending identity and native-only submission; worker-owned runtime initialization/registration/cleanup; bounded post-exit bootstrap diagnosis; explicit shutdown waits | Exit evidence from a Python sentinel, bootstrap waits in coordination, daemon abandonment, general Thread compatibility |
| Core `PhysicalExecutionOwner` | Admit and retain one original slot, exact receiver/target/invocation identities, bounded rotating polls, original Future and capacity charge | Replacement execution, resource disposal or durable physical bits |
| Existing resource and retirement consumers | Current fencing, exact original resources/leases, metadata transitions and subsequent cleanup | Treating file sync or closed resources as evidence of native exit |

### Native creation and receiving

Allocation performs no native thread effect. Core first inserts and charges the slot, then calls `start()`. The C owner holds the GIL across the bounded OS creation entry and records its outcome before signal checking. The new worker cannot execute Python before its native handle and self-reference are retained. A lost or interrupted creation reply therefore leaves `started` true and the original charged slot present. Definite creation failure permits withdrawal; absence of a Python `ident` does not decide this. `Worker.start()` performs no bootstrap acknowledgement probe, wait, runtime registry acquisition or registry cleanup.

During execution, a native self-reference roots the original callback/owner. The worker clears its callback reference and original Python thread state before native return. GC traversal allows unstarted callback cycles and received exception cycles to be collected, while a running or quarantined owner remains rooted. No destructor joins, closes or fabricates receiving.

On Linux, `pthread_tryjoin_np` returns pending without waiting for termination; success is recorded once. The [Linux manual](https://man7.org/linux/man-pages/man3/pthread_tryjoin_np.3.html) documents this GNU interface and its `EBUSY` result. All native-handle operations are serialized by the GIL on the admitted profile. The successful receipt is stored before signal checks; retry after a lost Python reply returns the retained result without rejoining a consumed pthread. Unexpected errors quarantine the owner and suppress further native probes. This deliberately preserves custody rather than interpreting absence or an error as success.

The Windows draft records thread-object signaling and handle closure separately. [Microsoft's wait API](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject) documents zero-timeout polling; [thread termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-thread) documents signaling and remaining open-handle lifetime. [_beginthreadex](https://learn.microsoft.com/cpp/c-runtime-library/reference/beginthread-beginthreadex) supplies the retained handle. A numeric ID match is disambiguated through that original handle to avoid confusing a reused ID with the current worker. Wait or close uncertainty remains charged. This path has not been compiled or executed on Windows here.

### Python bootstrap and shutdown

The adapter reuses the pinned CPython 3.12 Thread bootstrap for normal `threading.current_thread()` identity, tracing/profile hooks, limbo/active registries and non-daemon shutdown bookkeeping. Launch, liveness and join methods use the native owner; they never invoke the vulnerable sentinel receiving path. The constructor initializes only fixed pending fields, one Event, the callback specification and the native owner. Start acknowledges native creation only; Python `ident`, `native_id`, enumeration and bootstrap acknowledgement can remain unavailable when submission returns.

Moving only the acknowledgement loop is insufficient. [CPython 3.12.3's Thread initializer](https://github.com/python/cpython/blob/v3.12.3/Lib/threading.py) inserts into `_dangling`; [WeakSet.add](https://github.com/python/cpython/blob/v3.12.3/Lib/_weakrefset.py) can drain an arbitrary pending-removal list first. The real `Thread.__init__` therefore runs on the original native worker as well. It establishes the ordinary hook and weak-registry state; the adapter preserves its original pending Event and drops the redundant callback specification after initialization. Limbo insertion, active registration, non-daemon sentinel maintenance and residual cleanup all remain worker-owned. No global registry is replaced or skipped in production.

The pinned bootstrap unconditionally calls `_delete()` even when it failed before active insertion. Exact-owner active deletion avoids replacing the original bootstrap error with a missing-entry `KeyError`. A worker-owned `finally` removes any residual exact limbo entry. Cleanup may wait on a runtime lock only on that worker; native exit receiving includes completion of this cleanup and subsequent Python/native TLS teardown.

After one positive native poll, the coordinator reads the stable acknowledgement flag once. Exit before acknowledgement raises `WorkerBootstrapError`, a `RuntimeError` subtype, from the exact retained native bootstrap exception. A bootstrap that simply returns without acknowledgement still produces the explicit missing-acknowledgement diagnosis. Core retains the original unset Future, slot and capacity; it does not manufacture a semantic result. Repeated diagnosis makes no additional native join. The rotating collection bucket allows a subsequent bounded call to receive an independent original for the same receiver. Bootstrap exceptions after acknowledgement remain retained in `bootstrap_exception`; if the original Future is absent, Core reports `outcome-missing` and keeps the slot charged.

`close()` closes admission under the registry lock and joins outside it. It receives later originals before reporting an already-received `WorkerBootstrapError`; that diagnostic cannot permanently prevent their shutdown. Actual coordinator interruption and unknown native results still propagate immediately. Each explicit blocking join alternates zero-wait native receiving with finite interruptible waits; those waits have no receiving authority. Retrying shutdown receives the same workers and retains their original outcomes for the proper receiver.

The adapter refuses other interpreter/minor-version profiles instead of assuming their private bootstrap fields are compatible. Public daemon mutation cannot turn a started but unacknowledged worker into an abandoned daemon. A worker may inspect its own liveness but cannot join or poll itself for exit receiving. Service shutdown must finish native receiving before interpreter finalization or closing shared dependencies, including workers whose runtime registration has not yet begun. Ordinary interpreter shutdown bookkeeping is not a substitute for an explicit native receipt. The native stack uses the OS default, so this is a focused Core worker rather than a general replacement honoring every `threading.Thread` configuration surface.

### Core status, collection and consumers

`status()` and each selected collection slot perform one native receive probe. Pending work remains running; a positively received and acknowledged worker without the original Future remains `outcome-missing` and charged. A pre-acknowledgement exit reports the bounded bootstrap diagnostic described above and also keeps its slot charged. Only a received native exit plus the original Future allows a completion. Exact receiver identity, stale invocation refusal, per-target isolation and the rotating bounded bucket are preserved.

The tests verify that independent work completes while another original is held; wrong receivers cannot consume it; original success objects and original exception objects remain identical. The real workspace lease is denied to a competing reader while the held target or TLS finalizer owns it and is obtainable after native exit. The retirement-consumer witness separately preserves the directory-phase `.lease` namespace and construction/physical capacity ledgers until actual receiving. File-resource receiving may already have happened at that point; it does not authorize early directory cleanup.

## Runtime/backend requirements and open integration decisions

| Profile | This packet's implementation | Executed qualification |
|---|---|---|
| Linux x86-64, glibc, GIL CPython 3.12 main interpreter | Joinable pthread and zero-wait tryjoin; real native TLS and SIGINT witnesses | Pinned CPython 3.12.3; exact environment and results in VALIDATION.md |
| Windows, dynamic UCRT, GIL CPython 3.12 main interpreter | Proposed original `_beginthreadex` handle, zero-wait wait, retained close | None; require native wheel, real interruption and handle-lifetime evidence |
| Darwin | Explicit refusal for Worker; existing file-resource functionality remains separate | No worker backend supplied |
| Free-threaded CPython, other Python implementations, subinterpreters, fork-transferred owners | Refuse unsupported profiles/ownership | Refusal witnesses where applicable; no execution support claim |
| Other CPython minor versions | Python bootstrap adapter refuses | Require explicit bootstrap reconciliation and bounded native-tail evidence |

Apple's [public pthread header](https://github.com/apple-oss-distributions/libpthread/blob/main/include/pthread/pthread.h) exposes joining but no public tryjoin counterpart. A possible Darwin design is a separately admitted native receiving service that performs the blocking join away from coordination and stores the original receipt. That design must prove its own helper lifetime, shutdown, resource/cost accounting and independence when one original is stuck. A single blocking reaper cannot simply stall receipt of unrelated completed workers. This packet does not introduce an unqualified helper, private Darwin SPI, `/proc`-style existence heuristic or polling fallback. The owner must resolve the supported Darwin strategy before cross-platform integration.

## Bounds and precise limits of the evidence

The shared witness observes native API entries directly, including pending and already-received retries. It varies unrelated retained originals without scanning them. There is one creation and at most one positive native exit receipt per actual worker; after receiving, retries make no further joins/waits/closes. Native owner storage is constant for the measured build.

The revised bounded-control argument also covers the actual Python wrapper. Maintained observations count caller-side Event/Condition waits, Thread/Worker joins, sleeps, runtime registry lock acquisitions, registry mapping/weak-set work, pending weak-reference removals and acknowledgement reads. Worker-owned initialization is excluded from the caller's scope by actual thread identity, not by hiding a call behind a native start counter. Public start and construction perform zero acknowledgement probes, waits and registry operations; post-exit polling performs at most one acknowledgement read and no wait or registry operation. A held-bootstrap witness and deliberately pending weak-registry cleanup make those boundaries executable.

Core's growth witnesses compose those actual wrapper observations with the existing native start/poll counters, mapping work, full key widths, populations and quanta. Collection also observes automatic retirement of the completed worker's own weak reference: at most one direct set removal or pending-list append per removed original. This finite cleanup is distinct from draining unrelated pending removals, which remains absent from coordination. The observation harness does not retain extra worker references that would postpone the callback until after measurement. No whole-registry enumeration is permitted in coordination. No wall-clock target, numeric-policy relaxation or claim about scheduler/allocator-internal latency is introduced.

Real SIGINT tests establish coordinator interruption behavior. Fault seams separately establish the ordering of native effects, receipt storage and Python reply loss; synthetic unknown-state tests do not pretend to reproduce an OS failure. All fault and native-tail control methods are absent from the production wheel.

The proposal does **not** add an acknowledged completion-batch delivery protocol. An arbitrary Python exception after Core removes a slot but before its caller receives the returned tuple is a distinct delivery boundary. A native exit receipt also does not create persistent recovery across process death, settle final lifecycle costs, renew a lease, authorize replay, or qualify power-loss durability. Those consumers remain subject to their owning issues and current source reconciliation. No provider, release, merge or independent scale campaign was performed.
