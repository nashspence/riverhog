# Capacity, receiving and workflow budget

This document settles the shared storage/resource decisions for the #999 proposal. It consumes the existing repository owners and the pinned #995–#998 reference seams; it does not establish a new service, storage tier or authority registry. [IMPLEMENTATION.md](IMPLEMENTATION.md) gives source/provenance and [QUALIFICATION.md](QUALIFICATION.md) gives the outstanding concrete checks.

## One workflow budget, different mandatory liabilities

Use the #995 policy exactly: adaptive replay target 120s, optional-tax fraction 1/8, no default checkpoint-count ceiling and two usable retained generations. Restart mode, zero optional count and cheap completion are resolved before allocating an optional store. Policy controls optional recovery; it never suppresses required original intent, encrypted continuation state, archive backing, quota accounting, output publication or original receiving.

| Entry | Accounting root and attachment |
|---|---|
| Standalone archive copy/repair | Original copy request/generation is the root. All source preparations, transfer workers, destination parts and receiving join it. A parent workflow supplies its attachment instead when present. |
| Standalone retrieval | Original planning request/selected job is the root. Planning, restoration orchestration, cache hydration and streaming share it. A CLI materialization operation forwards its existing root, as selected by #998. |
| Discovery/index rebuild | Existing Core discovery construction/build is the root; Native children and prepared-index installation share it. Query-only ephemeral readers create no independent recovery root or checkpoint store. |
| Independent recovery | One explicit recovery invocation and exact selected archive roots/output intent form the local root. Its metadata/planning/decryption phases do not each receive another 120s allowance. It remains independent of Core/client databases. |
| Local materialization/repair | Original CLI operation and output mapping intent own the root, including the downstream retrieval attachment. Required output/quarantine barriers do not reset optional exposure. |

Consume #998's immutable `RecoveryAttachment`, numbered disjoint grant offers and parent-driven authenticated pull handshake. Remote receivers do not receive ambient credit from knowing a root ID. Root gate, optional phase permits, completed-cost readback and acknowledgement remain with their existing immediate owners; Core does not call arbitrary client callback URLs. Mandatory cleanup/receiving proceeds when optional admission is sealed. Optional GC, compaction, failed candidate disposal and restore/revalidation cost remain charged to their original root. A restart, process boundary, change of phase or provider waiting interval creates no fresh credit.

Useful work is measured verified fresh transfer/computation, not elapsed restore wait, sleep, identical status, duplicate replay or receipt polling. Natural accepted part/object/output receipts are reused only for their exact proved coverage. Do not write a duplicate optional checkpoint merely to name an already durable object. Saved transport bytes must be valued against measured retransfer/revalidation cost, not total object size when most of that size would not be replayed. An incomplete unknown provider effect is not a resumable frontier.

For genuinely useful long private work, consume #996's immutable page-root mechanism and #997's prepared acceptance. No chained delta replay, complete growing-database copy at every checkpoint, per-member independent budget, or naked cursor without semantic state is selected. No valid bounded cost/space estimate means no optional promotion. Mandatory progress can still proceed under its own capacity. Cheap read/recovery/copy planning in this packet creates zero optional checkpoints; the experiments do not establish integrated long-run promotion economics.

## Retained metadata admission

The #998 application proposal introduces explicit positive `retained_state_max_bytes` and `retained_state_min_free_bytes` in the owning Stove0 support/FTP/Gogurt configuration and sampler-owned protected control roots. Keep those settings, sampler control/workspace incarnations, original receiver/retirement records, and their owner-local adapters. The small installed example values remain 1073741824 and 67108864 bytes respectively, explicitly fixture choices, with no universal production default. #999 supplies common measurement/admission rules; it does not import a Stove0 application implementation into FTP, Core or recovery, or create a quota database.

Put persistent reservations on existing original/accepted/operation records. For SQL owners, add any constant-size accounting row to that **same application's** state transaction. Immutable-file owners keep reservation fields in their existing accepted/owner envelopes under the exclusive original allocation owner; do not add a quota database or independently updated aggregate file. One admission record includes exact original ID, selected backing allocation/incarnation, ceiling/geometry revision, retained request bytes, finite result-envelope reservation, next mandatory transaction/sidecar reservation, owned staging and receiving/cleanup liability. An unknown upper bound is not zero. Split unbounded work into next bounded units; refuse before accepting a unit that cannot reserve its required outcome. Do not impose a total archive/history limit to obtain the bound.

Admission shares the mandatory original selection boundary: compare current live charge plus outstanding liability plus the proposed bound against the configured ceiling; retain the exact reservation; then permit acquisition/effect/disclosure. SQL owners select both records in one transaction. File owners publish/sync the exact immutable envelope through their existing original publication protocol, read back ambiguous publication, and then update the guarded derived aggregate. Unknown publication freezes new admission without refund. Concurrent admissions serialize only on that owning allocation row/fence, never on a repository-wide lock. Retried acceptance compares the exact original and returns its existing reservation. Disposition and charge release use the same required owner boundary and are idempotent by original ID. Never release capacity in a generic exception handler.

Separate these dimensions explicitly:

| Dimension | What establishes it |
|---|---|
| Encoded retained bytes | Exact canonical request/result/control lengths plus owner-declared bounded next outcome. Include retained uncertainty and compact historical originals. |
| Physical backing | Actual allocation owner measurement: file allocated extents, database/pages and journals/WAL, provider object/session liability, directory/metadata costs within the qualified backend envelope. Logical JSON bytes do not establish it. |
| Execution/receiving slots | Actual retained worker, connection, cursor, file/borrow, HTTP body and child-process records. Worker done is not resource received. |
| Private execution storage | Disposable live SQLite/sidecars, indexing/planning scratch, candidate snapshots and failed partial objects until received/reclaimed. |
| Required tail | Space/work for bounded result, cancellation state, exact outcome and eventual receiving/reclamation, reserved before admitting the original. |

SQL owners maintain aggregate live charge transactionally. File owners rebuild the derived in-memory aggregate by bounded streaming reads of accepted/owner envelopes before readiness and maintain it under the exclusive original owner thereafter, exactly as #998 selects. Neither rescans every historical original on each admission or poll. Bounded reconciliation is explicit owner work, uses a fixed source view/epoch and an idempotent final receipt, and fails closed on corrupt mandatory state. Historical records can be compacted only after the exact recipient's acknowledgement and local receiving allow it. The compact identity/transfer record remains charged for the original allocation's lifetime where its owner still requires replay protection. No TTL authorizes deleting an uncertain original. At capacity, defer new work while retaining status and original receiving.

## Physical admission and platform selection

There is no portable equation that turns a free-space check into a promise that the next SQLite/PostgreSQL transaction or filesystem rename will survive arbitrary storage failure. The selected implementation makes the claims precise instead of changing all databases to a faster synchronization mode.

**Application files and ordinary SQLite state.** Use the application's existing protected allocation and original resource owner. Under that allocation's admission fence, obtain fresh physical usage/free-headroom observations, include maximum sidecar/transaction and receiving liability, and refuse new admission before entering an effect if the next envelope does not fit. Apply the configured dedicated-volume quota as the independent physical ceiling and reserve the configured free headroom for control/receiving. Ordinary/new/optional work cannot consume `min_free_bytes`; only the previously reserved mandatory tail and original receiving can consume that protected allowance. Their admission checks use their original reservation, not the fresh-work headroom test. Cooperating owners sharing a physical quota must share one actual allocation fence/accounting domain, or receive disjoint independently enforced quota allocations; separate application counters cannot each promise the same free headroom. `max_page_count` can bound the database file, but `journal_size_limit` is not a peak-transaction/WAL bound; include those explicitly in the backend envelope. A sparse or merely truncated reserve file is not allocated backing. A supported deployment profile must qualify the actual filesystem/quota/allocation mechanism it uses; a missing or unsupported geometry is an explicit capacity/capability refusal, not an unlimited fallback.

Keep the exact physical original through every commit/close. Where the SDK already owns backed prepared-primary state, use its **public** `PrimaryStore`/prepared-primary resource contracts rather than weakening or reimplementing them. The source has distinct database, journal, native handle and operation grants and fixed original physical-readiness records; these are not disposable progress. The existing `_prepared_primary_sqlite_journal.py` checks allocated backing, not just file length. Its private implementation is source evidence, not an import surface for other applications. Independent recovery does not acquire an SDK dependency to reuse it.

**Core PostgreSQL.** The database server owns its physical allocation; a client-side `statvfs` result is irrelevant. Keep atomic logical reservations/counters in Core's catalog, and use the deployment's separately enforced database/volume limits and monitored operational headroom. Do not pretend a SQL row reserves physical WAL blocks or add an unqualified SQL preallocation table. Missing required storage capacity reports admission unavailable before new external entry. PostgreSQL commit/rollback and receiving are qualified against its real server and storage profile. The catalog's current durability policy is unchanged.

**Unexpected exhaustion after acceptance.** The guarantee is preservation and no false completion, not uninterrupted liveness under an unrelated writer filling a volume or a device failing. Stop new/optional admission, retain the original reservation and resource owners, and attempt mandatory receiving within already admitted control resources. If a required record/barrier still fails, report capacity/unavailable/unknown and keep the original recoverable intent; never acknowledge acceptance, publication, cancellation completion or resource release that was not established. Restoring capacity and reconciling the same original is the defined continuation. Do not compensate by deleting operator data, old authority, unreceived output or the only usable generation. This closes the failure behavior without claiming that advisory headroom is physically infallible.

**No new physical storage engine.** Shared code belongs in focused existing resource/state support for common arithmetic, upper-bound validation and original receiving. Each concrete SQLite, filesystem, PostgreSQL or provider owner supplies its actual measurement/reservation geometry. Do not export client-private prepared-primary code or introduce a general payload spool. Required installed examples exercise each shipped backend's selected refusal/success behavior; unsupported physical claims stay explicitly unavailable until qualified.

## Original receiving and reclamation

[`retained-resource`](../packages/retained-resource/src/retained_resource/__init__.py) already establishes the essential local rule: reserve and retain the original resource/borrow record **before acquisition**, receive in reverse dependency order, and remove only after positive original receiving. Its handle bound is not a disk-byte budget and its `Group` is not a destructor stack. Use it where applicable; do not infer worker completion from closing a file or vice versa.

For copy/retrieval, retain the source stream object as well as its iterator, every admitted future/executor and the destination invocation records. On cancellation, seal new dispatch, request cooperative stop, receive all entered workers/HTTP bodies, record exact outcomes, then run selected cleanup and finally retire catalog/source/cache dependencies. A timeout only changes the public pending/reconciling state. An unknown original remains in the registry and consumes its real capacity; a successor cannot reuse its authority or slot. Transport closure and remote effect outcome remain separate.

For discovery, retain the original Native summaries, Core reader, cursors, scratch connection and workspace. Eviction/context exit cannot remove an original before `storage_received`. At most the admitted live cache plus one blocked eviction remains; unresolved receiving stops new acquisitions. For materialization, output/quarantine publication intents retain destination and parent identities plus staging originals until both publication and actual resource receiving are established. The whole dependency graph, not a final Python `finally`, determines when a path may be removed.

Reclamation runs in bounded worker quanta using exact immutable original selections, current destructive authorization and source/cache incarnation. Retain old optional generations until a complete usable successor is selected and their readers are received. Use the #996 page map/reference accounting and bounded sweep; do not traverse the entire corpus on every candidate or rebuild a full reference graph at each checkpoint. Count partial generations, database compaction, provider orphan sessions and delayed deletion in normal lifecycle cost. A status call neither reclaims nor forces a checkpoint. Explicit maintenance may wait on resources; the scheduler remains responsive to independent jobs.

Native directory publication is qualified per platform. The existing Windows `retained-resource` CRT path accepts regular files and `_commit`; that is not a directory-durability primitive. The current recovery Windows directory sync is a no-op. Do not claim Windows power-loss durability by reusing those calls. The selected no-clobber intent/reconciliation algorithm is in [MATERIALIZATION_RECOVERY.md](MATERIALIZATION_RECOVERY.md), and its installed native qualification is a required implementation deliverable, not a choice left to an integrator or a guarantee made by this reference.

## State cut and failure classification

Mandatory old application state is not erased to install the new model. Quiesce/drain with the compatible old executable when safe; retain unresolved original work with that owner. The new executable refuses populated incompatible pre-v1 state. Initialize only an explicitly new/empty allocation using the existing state-schema mechanism; keep supported future upgrade machinery. No automatic migration, reset, deleted effect history or archive re-encoding is selected.

Missing/corrupt optional generations may replay from verified inputs after original receiving. Missing/corrupt authority, original output intent, quota liability, provider identity or construction receipt is an error requiring its owner's exact resolution. Do not convert it to a cache miss or empty result. This distinction is maintained under zero optional checkpoints and under capacity exhaustion.
