# #999 — supplied adapters, copy, repair, and retirement

This is the adapter and copy portion of the #903 integration handoff for #999. The source audit is pinned to **`c28eceaa2dfec1b3712135469ba12230e74f5ffa`**. Product files are unchanged. The executable experiment changes one copy-service method in a reference subclass; it does not implement the proposed durable invocation owner, public progress contract, policy integration, or provider terminal proof.

The selected change is to remove persistence of replayable copy counters while preserving original transfer identities, external-effect obligations, sealed receipts, and backing representation. Completed filesystem segment ledgers remain mandatory. S3 traversal keeps its current verification semantics and measured cost. Copy/repair and retirement use their existing owners and the existing storage protocols, with bounded original execution receiving and explicit unknown states.

Read this with [IMPLEMENTATION.md](IMPLEMENTATION.md), [CAPACITY_LIFETIME.md](CAPACITY_LIFETIME.md), and the single [shared read-preparation invocation](RETRIEVAL_CACHE.md#shared-read-preparation-invocation). The latter governs both copy and retrieval, including AWS restore consent and opaque provider policy. There is no second paid-restore design in this document. The governing archive distinction is already explicit in [README.md][readme]: sealed objects and immutable published roots define archived content; operational state may preserve obligations without acquiring archive authority.

## 2. Filesystem representation: mandatory state is not a checkpoint

`begin_write` fixes the original random session token, path, byte count, content type, identity assertions, placement and creation time. It preallocates the admitted payload with `posix_fallocate`, creates the segment database and exact state, and synchronizes the bootstrap. A repeated exact request returns the same session; changed identity is refused. A new segment writes and synchronizes its payload range before `_insert_segment` commits the matching receipt and authority accumulator. `_verify_replayed_segment` compares supplied bytes with the original stored range. These operations are actual storage custody and cannot be deferred because optional checkpoint allowance is exhausted. [Source][fs]

Completion preserves **both** payload and segment database in the completed revision. `_install_write_as_revision` links them into a private revision, publishes metadata, synchronizes the directory, installs the revision, selects `current`, synchronizes that selection, and retires the live write directory. The stable revision derives from the original session. Retrying after revision installation but before current selection receives that same revision. The constant-sized authority accumulator avoids rescanning all segments during normal completion; the maintained test explicitly rejects a completion that rereads the payload. No #999 change weakens these barriers. [Implementation][fs] · [maintained tests][fs-tests]

The ledger is subsequently required by `_verify_object_payload` for a multipart completed object and by materialization's representation validation. A normal read checks the physical ledger's presence/type; this is not a claim that every read revalidates every ledger entry. The reference test completes two real filesystem segments, closes/reopens the actual adapter, reads exact bytes, observes that the original write state has retired, then removes only that disposable test's **completed** ledger and checks refusal. The test is a negative representation witness, not a destructive action on a user archive. [Reference tests](implementation/test_adapter_experiment.py)

`FilesystemInventory` has the opposite status. Its own module declares the provider files authoritative and the index disposable. Under the exclusive instance lock it rebuilds once, with linear metadata reads and space, O(N log N) index construction, bounded SQLite page cache, and indexed keyset pages. Selected behavior is unchanged: do not add a durable optional generation just because startup may revisit history. If future measurements justify an optional index generation, it must be a separate derived candidate under the common budget and complete source validation; that optimization is not part of this implementation plan. [Source][fs-inventory]

Reader gates remain part of physical lifetime. `read_object` holds the gate until the returned stream is received/closed; deletion waits. Adapter `close()` itself does not join an arbitrary caller's retained streams, so service shutdown must first receive its outstanding request/stream owners, then close the adapter and release the instance lock. Replacing the configured root pathname cannot redirect the existing filesystem instance, which retains a directory FD and its `/proc/self/fd` path. These are Linux/POSIX properties of the supplied adapter, not a cross-platform atomicity claim. [Source][fs] · [deletion/stream baseline][fs-tests]

## 3. Copy and repair: separate work, live progress, and original effects

### 3.1 What the source already owns

`ArchiveCopyJobRecord` binds source and destination storage incarnations, the original destination prefix, selected cache behavior and initiator. `_plan_destination_upload` retains each exact object identity. `_copy_volume` first receives an already completed exact object if present; otherwise it reuses the retained write token. The transfer verifies each original archive part's stored-byte hash and copies **existing ciphertext**; `crypto_seconds=0` correctly describes that operation. `_copy_completion_precondition` traverses provider receipts and verifies exact segment coverage independently of progress counters. `_record_copied_object` atomically retains the sealed destination receipt, placements, original crypto/part state and cache receipt when selected, then removes that object's in-progress upload row. `_finalize_completed_copy` checks complete object/provenance/root families before publishing the final catalog result. [Copy owner][copy] · [models][models]

The current source window is at most **32 objects**. Within one volume, pending writes are bounded by **twice `write_concurrency`**, with byte and request reservations. The thread-pool context receives original worker futures before returning from a transfer exception. That is useful existing behavior, but cancellation is currently checked principally at object boundaries; `_record_copy_progress` checks only that the upload row still exists. It is incorrect to say that removing its transaction removes a current per-part authorization check: none is present there. [Source][copy]

### 3.2 Selected progress change

Replace `_record_copy_progress` persistence with one latest advisory value per active copy/object execution. Bind it to `(copy_attempt_id, execution_epoch, object_id)` and the accepted source/destination incarnations. `copy_attempt_id` is fixed when the original copy job is accepted; execution epochs fence workers without creating new allowance or new work. Only the currently retained executor may replace its slot. A stale epoch, retired object, cancellation gate, or completed job cannot overwrite the final receipt. Drop the slot on worker release/restart. Completed status is rendered from the original durable job and object receipt.

`ArchiveCopyJobOut` currently exposes **no byte/segment counters**. Keep its state-oriented public presentation; the new live slot is private diagnostics, not a new numeric-progress API. In diagnostics distinguish processed bytes/segments from the **durable resume frontier**, whose source is completed sealed objects and validated original session/receipt state. During a process restart processed counters may disappear. They never imply that the old byte count selects a verified prefix. The first implementation creates no new per-segment optional generation for this cheap counter. It retains the current restart behavior where safe original receiving permits it: an incomplete volume may replay its source and original session; an already sealed exact object is received without retransferring it. A later segment-skip optimization is outside this selected change and is not assumed in qualification. [Current public model][archive-schema]

Use `read_snapshot` for status and any point lookup needed to reject a missing upload record. A status endpoint reads the current durable state and returns; it does not prepare a restore, poll a provider, acquire a transfer reservation, or write the database. Current `get` already has no provider work or DML, but uses `session_scope` and therefore emits read-only commits. The production cut replaces that session choice too. The reference subclass retains a read-only missing-upload lookup while deliberately leaving public status unchanged. [Copy implementation][copy] · [reference code](implementation/adapter_experiment.py)

### 3.3 Mandatory original execution change

Deleting progress writes is not a substitute for safe original-effect handling. Copy currently calls legacy `begin_write`, `write_segment`, `complete_write`, and `put_immutable_object`; `StorageAdapterArchiveResumableObjectStore.execute_write` is separately available. The upload service already demonstrates durable armed dispatch and original result receiving, but its `ArchiveWriteControlRecord` is collection/upload-construction scoped. Independent destination copies must not borrow that row or spend its allowance again. [Delegate][objects-delegate] · [upload owner][upload-writes] · [upload records][write-models]

Implement the copy specialization in `archive_copy_jobs.py` with a small `archive_copy_writes.py` helper and copy-owned model records in `catalog_archive_copy_write_models.py`:

- `ArchiveCopyWriteControlRecord` binds the accepted `copy_attempt_id`, immutable construction (collection, original archive/root identity, both incarnations, destination prefix, cache choice), gate/epoch, monotonically issued call sequence and common root/grant binding. It survives an upload-row deletion and terminal cleanup while any original effect is unreceived. It is not archive authority.
- `ArchiveCopyWriteEffectRecord` retains the exact existing `WriteInvocation`, original input/source identity, reserved capacity and original returned `WriteExecutionResult`. Use the existing public request/result digests and execution/outcome validation. The original object plan and all random IDs are fixed before possible provider entry. No retry replaces an original invocation or manufactures a new destination prefix.
- Arm one bounded batch of exact part invocations, up to the current pending-work window, in a short owner transaction before dispatch. Receive original completed results in bounded same-owner transactions; no waiting for a batch to fill. The final batch is flushed before completion/cancellation/release. This is batching required intent/result barriers, not making every progress callback mandatory. Receive results after the gate closes; a closed gate forbids fresh effects.
- Successful sealing plus exact returned receipt is the natural per-object anchor. Receipt publication, upload-row retirement and accounting receive can share the existing catalog transaction after validation. Unknown calls stay retained and block fresh conflicting mutation, destructive cleanup and terminal success. A provider list, timeout, cancellation flag, empty prefix, or newly constructed Future cannot discharge them.
- Once the caller has received exact completed original effects and the enclosing object/job terminal boundary permits reclamation, reclaim receipt details in indexed bounded batches while preserving the control's issued/received continuity and original sealed receipt. Do not add an unbounded in-memory call-history map. Unknown records are never reclaimed by age. Capacity/backpressure and tail lifetime follow [CAPACITY_LIFETIME.md](CAPACITY_LIFETIME.md).

The selected handling of unproved closure is **retained unknown/refusal**, not an implementation question. #442's original provider terminal-proof obligations remain real qualification requirements. Merely discovering the exact completed object may recover semantic output while the original invocation's execution closure is still unresolved. The experiment demonstrates semantic recovery only; it does not claim that the legacy service already distinguishes those facts.

Select the public `ArchiveCopyJobState` set `requested`, `reconciling`, `needs_consent`, `canceling`, `completed`, `failed`, `canceled`. Current `waiting`/`checking`/`copying` become private execution phases, not public transitions requiring repeated progress writes. All four nonterminal states have `finished_at=null`; only a closed failure has a failure receipt. Add nullable typed `attention_reason` with `restore_outcome_unknown` and `restore_window_expired`, shared with the read-preparation contract. `reconciling` means the original execution has not been positively received; `needs_consent` means a fresh preparation requires explicitly accepted consent and all conflicting predecessor executions are already closed. Keep all four nonterminal states in `ARCHIVE_COPY_JOB_BLOCKING_STATES` and update the copy check constraint. Cancellation retains `canceling` with unresolved originals. Ordinary retry returns the same attempt. Make protocol literals, API schema/validator, client validation, state inspection and tests agree in the same cut.

Fresh dispatch and final acceptance must recheck current job gate, original source/destination incarnation, current permitted initiator access, source/root identity and relevant current selection. Revocation stops new work while exact receiving/cleanup obligations remain owned. Registration/pinning and the accepted original intent supply identity; a cached descriptor or a progress overlay supplies no authority. Do not change source hashes, archive headers, nonce/crypto continuation, receipt semantics or placement assertions to obtain a resumable prefix. [Registry][registry] · [storage incarnation checks][incarnations] · [HTTP client][http-client]

### 3.4 Cancellation, scheduling, and source streams

`process_due` currently performs a full `_process_one` synchronously from Core maintenance; `cancel` may perform immediate cleanup when no active transfer phase is recorded. The production change is a bounded retained execution owned by the copy service: maintenance admits/resumes one bounded owner action; control/status only inspect or close its gate. Keep active futures and source ownership in that retained execution. Before another part/cohort dispatch, observe cancellation and current authority. Cancellation then receives all already entered original calls, records their results, closes the exact read stream, and runs bounded exact cleanup. It may remain `canceling`/unresolved when proof is unavailable. It cannot delete the destination and report canceled while an original writer can still enter it. [Maintenance][api-app] · [copy cancellation][copy]

There is a concrete shared source-stream gap. `StorageAdapterArchiveStore.iter_stored_archive_object` currently extracts `.content` from `ObjectReadStream` and loses its explicit `close` callback. `_copy_volume_parts` also relies on iterator exhaustion/cleanup rather than an explicit source-close path on all failures. Add a narrow closeable iterator wrapper in that existing storage delegate that retains the whole original stream and has an idempotent `close` method. It must close even if no iteration started; a bare generator's unstarted `finally` is insufficient. Close the wrapper in the copy owner's `finally`, **after original destination workers are received**; preserve the same wrapper through download-allowance/decryption delegates. Close HTTP response bodies on validation failures before constructing a returned stream as well as on normal exhaustion. No new spool, byte copy, or plaintext tier is needed. [Delegate][store-delegate] · [S3 read body][s3] · [AWS read body][aws-provider] · [HTTP framing close][http-binding]

Fix the paired `ObjectReadStream.close` exception path at its protocol owner. It currently marks closed before calling `content.close`, so an exception skips the separate callback and makes a retry a no-op. Attempt the original callback in `finally`, track which original close actions succeeded, and mark the resource received only when both obligations are settled. Preserve/propagate an unresolved close instead of releasing its source pin or claiming quiescence. Repeated close must not redispatch a provider effect. [Current close implementation][protocol]

## 4. S3/AWS/B2: provider limits and observations

The supplied S3 descriptor declares 5 MiB minimum nonfinal parts, 5 GiB maximum parts and 10,000 parts. These are backend limits, not an archive size ceiling or a policy checkpoint interval. AWS currently documents the same part constraints and at most 1,000 entries per ListParts response. B2 requires the original UploadId for each part and preserves encryption selected at MPU creation. Keep backend requirements in the supplied adapter and keep Core's existing preflight against the descriptor. Do not invent a smaller global archive cap, or assume obsolete provider-wide object-size limits. [Adapter constants][s3] · [AWS multipart specifications](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html) · [B2 UploadPart](https://www.backblaze.com/apidocs/s3-upload-part) (primary documentation checked during this audit).

Current part traversal is costly and precisely identifiable. For `P` accepted parts, a public page calls `_listed_segments` and hashes all `P` receipts before slicing at most 128. A complete traversal therefore repeats provider work roughly `ceil(P/128) * ceil(P/1000)` times when the provider fills its pages. The reference uses the actual adapter with a metadata-only paginated provider fixture: **2,050 parts → 17 public pages → 51 ListParts calls → 34,850 returned metadata rows**. It transfers no multipart payload and supplies no measured provider latency. A changed receipt between pages still rejects the original traversal token. [Source][s3] · [measurement](evidence/adapter_comparison.json)

Selected first implementation: retain this behavior and budget/describe its real cost. A cached immutable list is not justified as a current provider snapshot when external mutation has no compatible generation fence. #964 owns coordinated traversal changes. Do not claim that #999's Core progress change eliminates these scans or that a short public page bounds total lower-provider requests.

`create_s3_client` configures exactly one owned SDK wire attempt and disables additional redirects/retries. CompleteMultipartUpload can return a nominal HTTP 200 containing an error; `_single_attempt` runs after SDK parsing and rejects it without replay. An injected/custom client cannot assert the owned transport's execution closure. The maintained loopback-wire tests exercise lost part response, lost completion response and embedded completion error without contacting AWS. [Transport][s3-client] · [wire tests][s3-wire-tests] · [AWS CompleteMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html)

Abort is also an effect, not a stop primitive. AWS explicitly allows an already running part upload to succeed after abort and advises later ListParts verification for physical cleanup. The existing `execute_cleanup` is stronger than raw `abort_write`: it has a bounded request/in-flight grant, checks live incarnation inside that grant, operates on exact versions/upload IDs, records each disposed/pending/deferred/unknown item, and stops lower-provider entry after ambiguity. Reuse it for copy/retirement cleanup **after receiving original writer ownership**. Its own closed cleanup turn does not retrospectively close a separate write invocation. [Adapter cleanup][s3] · [AWS AbortMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_AbortMultipartUpload.html)

AWS restore policy remains adapter-owned. Copy and retrieval use one shared durable preparation invocation with exact object version/incarnation, original consent and opaque policy snapshot. A prepare response lost before Core stores `read_requested_at` cannot cause a second restore. Expired/unknown original preparation is read/reconciled, not automatically renewed. **A conflicting successor preparation requires positive exact closure of the entire predecessor invocation, including all delegated executions.** Closing a local worker, Future, socket or response body is insufficient. Explicit new consent may acknowledge an unknown previous charge/outcome only after that execution is closed; unknown execution retains/refuses a conflicting new preparation even if the user has supplied a new request key and consent digest. B2 and filesystem immediate reads do not acquire synthetic restore attempts. [Shared preparation decision](RETRIEVAL_CACHE.md#shared-read-preparation-invocation)

The copy HTTP/SDK cut is owner-local and exact. Current `CreateArchiveCopyJobRequest` has no request idempotency identity, preparation offer, renewal consent digest or restore-policy field. Add required `idempotency_key` using the shared validated request-key representation and explicit `restore_policy` (`allow`/`never`). Retain an `ArchiveCopyRequestRecord` for each original request, scoped to the initiating principal and request key; canonicalize and freeze the collection, source/destination selections, incarnations, cache choice, effective policy and any predecessor/renewal bindings before execution. A repeated key with changed input is a conflict. A repeated identical key receives the same original copy attempt and does not create another preparation or another root allowance. [Current request/service][archive-schema] · [copy owner][copy]

For renewal, use the existing `POST /archive/copy-jobs` and current copy-status path rather than a new generic request API. The retained owner prepares a bounded predecessor-decision manifest under the common contract; status carries the exact shared `preparation_decision_count` and `preparation_decision_sha256` fields plus `renewal_offer_etag`. Add `GET /archive/copy-jobs/{collection_id}/{destination_store}/preparation-decisions` and SDK `list_copy_preparations(collection_id, destination_store, position, page_size)` for bounded immutable pages, bound to that exact offer ETag and current collection authority; a stale offer is refused and a GET never prepares/renews work. The manifest includes the exact predecessor calls, selected source/policy and known/unknown prior charge outcomes, and has no archive-length JSON list in the control response.

An explicit renewal POST supplies a **new immutable request key**, `renewal_consent_sha256` equal to the offered manifest digest, the exact predecessor request identity, and `If-Match` equal to the current offer ETag. `restore_policy=allow` is also required. Select the already prepared immutable manifest, acceptance, existing copy-root binding and bounded next-work/receiving reservation in one short owner transaction after current auth/source/policy checks. Do not install an archive-length array of successors in that transaction: admit each next bounded per-object invocation batch under its exact selected manifest entries and retain its reservation/intent together before entry. Accept only if every conflicting predecessor execution covered by the renewal has positively closed, using the manifest's prepared exact closure evidence plus the current owner fence; readiness or expiry is insufficient. Each accepted object decision allows at most one new invocation. Preserve the predecessor, including unknown charge information, and preserve the copy's original budget and destination/session identities. An SDK/CLI transport retry reuses the original request key and declaration; it never fills in a new consent digest automatically. A changed/stale/missing digest or ETag refuses renewal without provider entry. These fields, manifest paging, state models, client methods, generated contracts and inspection/refusal are one pre-v1 cut.

CloudFront currently checks origin HEAD length, exact requested version, response status, Content-Length and Content-Range, and closes its response on failure/exhaustion. Keep those fences and current credentials/authorization. A cached URL or cached descriptor never waives them. Local HTTP reader closure and the remote paid restore's available lifetime are different facts. [AWS reader][aws-provider]

## 5. Retirement and repair lifecycle

`retire` already preserves an exact accepted challenge and plan before deletion, uses current target incarnation, refuses the last complete replica, verifies a retained replica, checks cache/retrieval/copy blockers, deletes mutable documents and target archive material, and finally removes catalog state. `_purge_terminal_retrieval_plans` uses bounded catalog steps. These remain required safety barriers; the verification timestamp is not an optional reusable progress snapshot. [Source][retirement] · [maintained retirement tests][retirement-tests]

Retain the current `retirement-plan` / `retire` semantic operation and challenge, but make `POST /archive/copies/retire` accept/resume its retained owner instead of completing all provider I/O in the request. Its typed `ArchiveCopyRetirementStatusOut` returns `operation_id`, collection/store, state, nullable terminal result and nullable failure. Derive `operation_id` as SHA-256 of the domain `riverhog-archive-copy-retirement/v1` followed by a NUL byte and the exact accepted UTF-8 challenge; do not mint another ID on retry. Return 202 for nonterminal acceptance/readback and 200 for the retained terminal result. Add `GET /archive/copy-retirements/{operation_id}` with current `ARCHIVES_MANAGE` and collection-access checks; it reads retained state only. States are `accepted`, `verifying`, `deleting`, `reconciling`, `completed`, `failed`; only `completed` carries the existing `deleted`/`already_absent` result, and `failed` requires all entered execution to be closed. A missing operation is 404, not reconstructed success. [Existing routes][archive-router] · [current schemas][archive-schema]

Add `ArchiveCopyRetirementOperationRecord`, keyed by `operation_id`, for the original plan, exact target/retained source bindings, gate/epoch, phase, invocation/cleanup receiving and terminal result. It has no cascading dependency on the target copy. Keep the existing `(collection_id, store)` `ArchiveCopyRetirementRecord` as the active pointer to that operation so current admission/blocker lookups remain indexed. `_finish` installs the exact original terminal result, removes the active pointer and removes the target copy in one short transaction after received cleanup. The operation record remains independently addressable and charged to retained capacity; a later distinct retirement of a newly created copy does not overwrite it. Do not merely keep the old active row forever: its current target-copy cascade and tuple key cannot provide this lifetime. [Current record definitions][models]

Extend the public response contract, `RiverhogClient.retire_archive_copy` and new `get_archive_copy_retirement`, operation inventory, generated schemas and HTTP tests together; the old blocking-response interpretation is a hard cut, not an optional compatibility path. The state-only response does not add a per-object progress payload or another execution API.

Page target object identities by existing immutable object order; do not build the whole archive's object history in RAM or rewrite it into a progress JSON document. Retained-copy verification is similarly bounded source work. It may be replayed from the beginning after restart when no useful optional resume generation was admitted; a verification progress count is never deletion authority. Current immutable root, exact object identities, incarnation and accepted challenge are revalidated before effect entry and final catalog acceptance. Each deletion uses existing bounded cleanup inventory/execution on exact versions and markers, with original result receiving. An abort/absence/HTTP success observation cannot erase unresolved original writers. Mutable description/tag deletion retains the existing requirement that another current replica of that information is available before removal. [Retirement owner][retirement] · [storage delegate][store-delegate]

Repair does not weaken retirement. Creating or revalidating a replacement replica must finish through the ordinary copy/verification owner before it can satisfy the retained-copy condition. A canceled, partial, cached-only or unreceived destination cannot justify removing the source. Terminal cleanup must not collapse an interrupted original operation into ordinary `failed` and then recreate it through a new challenge. Unknown original effects remain visible and block destructive progress until exact reconciliation.

## 6. Shared policy, state cut, and qualification

Use one logical root from the common proposal. An independent copy job's original accepted attempt owns its root; an application/upload-selected copy inherits the exact parent grant. A mirrored cache population and its archive write receive disjoint subgrants of that same work. No new full percentage at each provider, object, phase, retry, repair or restart. Parent/root identity, reservations, unresolved cost and original results survive upload-row retirement. Server-local policy remains a clamp. [IMPLEMENTATION.md](IMPLEMENTATION.md) owns exact accounting types and [CAPACITY_LIFETIME.md](CAPACITY_LIFETIME.md) owns admission/lifetime.

The selected progress optimization creates **zero optional copy generations**. If another covered candidate legitimately saves replay, count full preparation/sync/promotion/cleanup/validation cost and restore cost. U includes only verified fresh useful execution from this root, excludes provider/queue/restore waiting and replay, and does not sum overlapping workers. Existing sealed part/object receipts and mandatory original intent/result barriers are not relabeled as optional snapshots to fit a budget. Failure or unknown cost never resets an allowance. The measured `process_due` elapsed is not a U measurement.

Coordinate the implementation as one explicit cut:

1. Add copy invocation and retirement retained-result model/schema ownership, immutable attempt/epoch and common policy bindings. Register new model modules in `catalog_db.py` and current state schema; classify populated incompatible state through existing inspection/refusal. Do not silently initialize missing controls over an old active copy or erase unknown calls.
2. Change copy/retirement worker ownership, exact dispatch/receiving, progress overlay and closeable stream propagation. Replace automatic paid-restore retry through the common preparation protocol. Keep IO, hashing and provider queries outside shared writer transactions; admit/arm and receive in short transactions.
3. Hard-cut public copy reconciliation state and retirement acceptance/status semantics in service output, API/client/protocol schemas and generated artifacts together. Keep copy counters private and mark processed versus resumable facts correctly in diagnostics. Add no progress-triggering side effects to GET/status. Configure owner-local capacity and bounded active execution through the common required configuration; update installed examples explicitly, with no silent new ceiling on archive history.
4. Preserve original selected state under cancellation, revocation, restart and wrong-incarnation refusal. Rebuild only explicitly derived inventory/progress; never treat absence of those bytes as proof that a provider call or original session never existed.

Focused remaining integration qualification is concrete: original invocation admission vs reply-loss across Core/adapter/provider hops; read-preparation policy/consent mismatch; cancellation during retained worker/stream ownership; stale epoch progress/final receipt; late original success after a closed gate; source hash/current-root/incarnation change; exact cleanup partial progress and unknown provider completion; no writer lock held through provider waits; active-owner/capacity saturation; restart with populated incompatible state; and installed public schema/config/state inspection. Real AWS/B2 wire qualification and provider terminal proof require their separately authorized infrastructure. They have not been performed here.

Both arms create one provider session, read 20 source objects, and write exactly 16 or 64 destination segments respectively. Completion scheduling naturally groups different numbers of futures per progress callback (current/volatile: 4/3 and 8/12). Consequently the 64-part volatile arm has **more total SQL statements** (168 vs 160) from its read-only point checks even while it removes all eight progress UPDATEs and commits. The table reports actual transaction-level observations, not fsync counts or a claim that every database operation decreased. No scheduler control, repeated sample campaign, large payload/provider latency, or hardware durability trace was performed; the elapsed differences do not establish an end-to-end speedup ratio.

After that first passing reference run, the paired test's minimum callback assertion was corrected from `> 1` to `> 0`: batching is scheduler-dependent, while one current UPDATE per observed callback and zero volatile UPDATEs are the actual invariant. The original run keeps its original test hash. The common final qualification run binds the final test file; the measured implementation script and measured results are unchanged.

Fault witnesses establish the intended narrow distinction. Losing advisory counters replays bytes in the original retained session and yields exact output. Losing catalog acceptance after the provider sealed the object recovers that original object with no second source-volume read or transfer. Stale progress cannot recreate a retired row or overwrite final output. Status performs no DML/provider work. Cancellation waits for the held original worker before destination removal. Completed filesystem ledger loss is refused. S3 traversal still detects changed receipts.
