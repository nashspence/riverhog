# Small-context integration session

This is a suggested #903 handoff protocol, not new product policy, a required PR
count, or a replacement for the repository's actual validation rail.

## Load only the current slice

At a fresh start read HANDOFF, the latest GitHub checkpoint, and one packet.
A packet may route several owners: select one function, producer/consumer boundary
or testable invariant. Read one numbered design section, then the corresponding
current implementation and scoped tests. Do not paste complete evidence logs,
all family entries, repository trees or entire issue histories into context.

Use `read.py P06 --read 1`; follow its next-offset instruction only when needed.
Use `read.py --family G59` to inspect one existing inventory entry. The reader
performs no network calls, tests, source modifications or product operations.
Packet dependencies name predecessor **artifacts**, not live issue status; verify
actual source. P06/P07 publication and P09/P10 input interfaces need agreement
before activation, without introducing circular all-or-nothing implementation.

## Gates and working order

P00 may begin now. #961's current issue-body guide supersedes historical patches.
#963's approved measurement policy permits approved-target, approved-no-numerical-
target, or unresolved timing applicability; do not invent a seconds value.
Integrate the foundation before dependent #964 production/evidence work.
Use P02 for the still-required workload/conditions/target/cadence checkpoint;
obey the owning issue before broad implementation. Packet order does not waive it.

Choose one bounded candidate: reproduce a concrete issue or define an exact vector,
change one owned path and the necessary paired consumers, run its relevant checks,
and record results. Existing required pre-push and substantial-change gates remain
required; focused checks are iteration evidence, not a substitute. Agree shared
interfaces before parallel writers touch shared models, hashes or publication locks.

Stop on a new protected-contract conflict, absent prerequisite, or an incomplete
proof being needed by a dependent slice. Stop before context becomes crowded;
checkpoint while source state and evidence can still be reconstructed reliably.
Do not continue automatically into the next packet merely because one test passed.

## Durable checkpoint — put this in GitHub, not tracked main files

```text
#964 checkpoint: packet / one exact slice
Reference SHA; authoritative source SHA; branch/PR/worktree identity:
Scope and current status: ready / active / blocked / slice validated
Approved decisions used (comment IDs); changed owner contract/vector identities:
Changed files/symbols; worktree clean or exact uncommitted patch location/digest:
Commands actually run, environment, pass/fail/skip and durable evidence locations:
Functional / growth / evidence integrity / timing applicability and disposition:
Last safe boundary; unfinished work and resource/cleanup state:
Next action with exact file/test; predecessor interface or decision needed:
```

Use a short main checkpoint and links to detailed evidence; retain failures too.
A context reset reads that checkpoint, verifies Git/source state, then loads the
same packet. Do not rely on assistant memory or claim an uncommitted change tested
at the last committed SHA. Keep evidence outside tracked main source per its owner.

## Initial pushback and escalation

Initial return: exact source/ref, ready/dependency-blocked/specific conflict, first
slice, and any precise approval needed. No full-repo implementation plan is required
in one response. Propose a smaller split when a packet is too broad.

Escalate changed capabilities, semantic acceptance, custody/security authority,
protected identities beyond approvals, target/workload/cadence changes, or waived
proof. Routine backend/index/schema/test details stay with integration and review.
A surprising implementation difficulty is not evidence of missing user intention.
No arbitrary public capacity defaults, hidden ceilings, second scheduler/registry,
pre-v1 compatibility readers or automatic operational data loss are authorized.
