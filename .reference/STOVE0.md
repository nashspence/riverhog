# Stove0 application and extension execution: selected #998 implementation

This is the Stove0 portion of the #903 reference for #998. All current-source links below are pinned to `c28eceaa2dfec1b3712135469ba12230e74f5ffa`. The branch changes reference material only. The executable witness changes advisory projection on the **actual current target owner**; the broader integration below remains proposed work, not a claim that #998 is implemented.

The selected cut is to keep exact invocation acceptance, original observations and outputs, effect uncertainty, publication custody and settlement durable, while running replayable planning and advisory progress without a durable write for each turn. The common policy, root grant accounting, remote useful-work meter and public progress definitions are in [BUDGET.md](BUDGET.md). Review0's additional sampler protocol is in [APPLICATION_EFFECTS.md §4](APPLICATION_EFFECTS.md#4-review0-exact-remote-execution-before-workspace-release).

## 1. Findings that determine the implementation

1. `PersistentTargetService._report_progress` currently reloads and replaces a JSON status file for every callback. `_write_model` flushes and syncs the file, replaces it and syncs its parent. `TargetExecutionSession.report_progress` explicitly describes these values as milestones without evidence. A generation-bound volatile sample removes this persistence without weakening accepted requests or successful results. [Target owner][target-owner], [execution session][execution]
2. The controller independently amplifies these observations: `Stove0WorkService.record_target_status` calls `_replace`, whose replacement always increments the durable revision. `_poll_target` first refreshes current authority and then records the returned status. Keep that authority check; stop a merely changed progress counter, or an identical poll response, from replacing the `WorkRecord`. [Work state][work], [coordinator][coordinator]
3. Names are insufficient to classify state. `TargetOutputCheckpoint`, `TargetCompletionCheckpoint` and concrete `step_value` tool/output records preserve original bytes or selected nondeterministic evidence. They are mandatory anchors. Planning hash cursors, projected accepted views, task scans and production/settlement traversal cursors are reconstructible from retained originals. [Output checkpoint][output-checkpoint], [completion checkpoint][completion-checkpoint], [accepted observations][accepted], [planning state][planning-state]
4. Existing local supervision already keeps the original OS ownership descriptor through tool containment and worker receiving. Preserve it. Tool cancellation, a status change, a timed join or a new wrapper object cannot establish that the original consumer stopped. The Review0 HTTP sampler has an additional cross-process receiving gap, addressed in its own application plan. [Consumer scope][consumers], [supervised subprocess][subprocess], [native supervisor][supervisor], [dispatcher][dispatcher]
5. Two proposed safety corrections accompany the optimization. Age does not prove downstream reception of an original result. A sealed external-effect plan cannot enter ordinary abandon/retry/no-output handling after a failed or ambiguous target outcome. The selected dispositions are retained originals with capacity backpressure, and an unresolved sealed effect until exact successful receipt/settlement respectively; neither introduces a general semantic-result reception or no-effect closure API.

## 3. Controller planning and sealing: one private epoch per admitted work domain

### Exact boundary and storage placement

Add `stove0_core.planning_epoch.PlanningEpoch` inside the Stove0 application owner. It owns bounded live conductor state, a disposable admitted local derived store and a single current replay domain. It is not a service and does not own new workflow semantics. `CompiledStatePort` currently exposes both its engine and original evidence/selection stores; split it into explicit original read/accept ports and the epoch's derived store. Keep the durable authority in the existing PostgreSQL `SqlAlchemyStateStore`. SQLite's current use as a unit-test backend does not qualify PostgreSQL replacement. A private SQLite scratch implementation is a derived execution substrate, not a new authoritative control database. [State ports][state-ports], [persistence][persistence]

Bind the epoch to root work ID, exact accepted work/recipe/compiler and owning semantic-provider configuration, selected input identity, retained original question/result envelope identities, accepted branch/child bindings and relevant original effect receipts. Bind its active control lease/fence separately so restoring a useful computational snapshot never restores an expired permission. Lease/contact/advisory changes alone do not change the captured semantic input generation; fresh authorization and the final current control-row CAS still apply, consistently with [Core's semantic revision cut](CORE_WORKFLOWS.md#3-complete-set-preparation-and-acceptance). Keep capabilities, client connections, Futures, thread/process handles and monotonic clock values out of durable state.

`CompiledRuntimeState.change` mixes phase progress with immutable scope/declaration/child fields. Keep those original bindings on the authority side; do not move a whole current table to scratch simply because some columns are cursors. Similarly, `AcceptedObservationStore.accept` owns approved request matching, owning semantic validation, exact accepted evidence, duplicate coverage rejection and the original retained evidence JSON. Retain that envelope durably before acknowledging its receipt. Projected fact/relationship rows and later evidence-set hashing can be rebuilt from it. [Runtime state][runtime-state], [accepted observations][accepted]

### Execution, publication and recovery

Use the existing bounded page/turn algorithms inside `PlanningEpoch.advance`. Cancellation and coordination yield at their current safe boundaries. A yield means only that the coordinator can service another work item; it does not imply any durable progress. Keep expensive source access and semantic validation outside control-row write transactions. Never run the complete planner on an API status read.

At an original boundary—accepting a physical question, selecting a provider/child, acknowledging target declarations, sealing production or recording a settlement—first complete and validate its exact source-dependent representation, then use a short transaction/CAS to install the original decision together with the required recovery accounting update. Do not acknowledge a question or dispatch a child until its selected original identity is durable. All side-effecting replay goes through these retained identities and existing owning idempotency/currentness rules.

The producing callback boundary needs particular care. Freeze receiving declarations before sealing, then conduct bounded private validation over that immutable generation. A resumed cursor without its matching output/disposition/source-edge index and hash state is invalid. Final `TargetProductionAuthority` selection must compare the same accepted declaration generation, exact job and current fence; a new declaration or changed source is a stale proposal, not permission to splice two generations. Preserve the owning operation validator and deterministic error order. Settlement similarly binds the exact output collection and production commitment. [Callback authority][callbacks], [seal records][work]

Only an admitted, beneficial complete snapshot may become an optional recovery generation under [BUDGET.md](BUDGET.md). Reuse the neutral complete-generation mechanics from the #996 integration: immutable indexed dependencies, changed-page capture and an atomic selected root after dependencies are durable. Do not serialize the entire retained observation/history list on every promotion. A generation contains the complete derived tables, conductor/cursors/hash accumulators and an immutable dependency-set root. It neither contains only a cursor nor imports independently changing live table rows on restore. No optional write is created for cheap work, a yield, a poll or final completion. A cheap successful seal goes directly to required acceptance.

Missing/corrupt optional state restarts derived computation against the same retained originals. Missing original testimony, accepted child identity, output bytes without exact custody, or an effect intent is a custody/unresolved error; it is not a cache miss. Revalidation of restored derived facts uses the owning current semantic contract and exact source/algorithm identity. Keep the original next failure and stale-source refusal behavior.

### Safe batching and coalescing

Keep the existing bounded original acceptance transactions, including approved observation result plus its coverage and exact original reference. Several already prepared original declarations may share one existing callback transaction only when they have the same work/job/fence/declaration generation, fit current request/resource admission and are each fully verified before the transaction. Retain per-item identity and conflict semantics; all-or-none acceptance cannot acknowledge an uncommitted item. Flush at the existing input/authority boundary or response deadline; do not delay waiting to fill a batch.

Do not combine the pre-dispatch accepted request with a post-effect result. Do not cross the receiving-to-sealing boundary, a source-fence change, custody release or final acknowledgement to save a commit. Ordinary filesystem target/observer original records retain their existing per-file durable selections; this proposal makes no claim that several renames become an atomic multi-record commit. The small NVENC group selector in §6 has a different purpose: selecting already durable dependencies.

## 4. Target and controller progress: concrete coalescing cut

### Target owner

Construct a new private progress-slot object in `PersistentTargetService._prepare_dispatch` after the actual current running-attempt marker is selected and before its executor runs. Bind `(job_id, attempt, request_sha256, plan_sha256, slot object identity)`. The slot object's identity is an in-process generation token; the same job/attempt cannot inherit a prior callback's permission merely because its integers match. Keep at most one sample per current admitted payload worker, under the existing owner lock.

`TargetExecutionSession.report_progress` validates/copies the four current fields and replaces this one sample. It does not load a file, encode a durable document, write a journal or spend optional checkpoint budget. Drop the slot on cancellation, attempt replacement, terminal result, owner close, inconsistent durable identity or any uncertain status-write exception. A late callback silently loses to that invalidation. The actual status commit path continues to make terminal results immutable and reject stale attempts. The current redundant `running/preparing-inputs` presentation write becomes a volatile phase update; keep the original pre-dispatch marker that tells recovery an invocation may have run. [Session][execution], [target owner][target-owner]

`get_job` reads original status and overlays only a matching current running slot. Return an independent typed copy. Status reads never write, sync, repair an index, execute a tool, replay a planner or wait for a worker. On restart the volatile sample vanishes; the original accepted request and started/interrupted attempt remain. This is honest regression of processed progress, not loss of a promised resume point.

Hard-cut the published progress model consistently with [BUDGET.md](BUDGET.md): bounded `processed`, nullable `resumable`, explicit `replay_guarantee` and uncertainty/receiving diagnostics. Do not expose a list of historical progress events or every output identity in the status response. A tool's processed counter is never a resumable point. Use exact counters with the repository's numerical contract, bounded object count and existing control admission; do not add an artificial total-archive ceiling to make status fit.

### Controller owner

In `Stove0WorkService.record_target_status`, validate every incoming status against the exact accepted request and owning operation as today, then compare its **semantic lifecycle/outcome** with the retained observation. Keep current attempt monotonicity and terminal immutability. If only advisory progress changes, replace the controller's bounded volatile projection; if the typed semantic observation is identical, return the current record without revision/event/counter writes. A new accepted attempt, cancellation/uncertainty, original terminal result, output identity or failure decision still commits through the owning work CAS.

`Stove0Coordinator._poll_target` still obtains current claim/runtime/callback authority and sends the same accepted request identity. A warm display cache does not authorize a payload read, provider action or stale capability. The scheduler's fair scan cursor and unchanged-contact observations can remain volatile; `ControlContacts` already keeps local active/backoff state in memory. Preserve exact metadata-transfer selectors, unresolved original IO owners, claim-renewal outcomes and any actual safety retry schedule. Never infer that every field called a cursor/contact/due time is disposable. [Coordinator][coordinator], [work state][work], [scheduler][scheduler], [contacts][contacts]

## 5. Mandatory output, completion and SDK boundaries

`TargetExecutionSession.step_value` selects immutable original records bound to job/request/plan. Its concrete toolchain and output-group uses are mandatory. Replacing an original tool version or encoded-output group on retry would change evidence, even if a rerun looks equivalent. Keep `TargetCompletionCheckpoint`'s exact pre-root result and execution preimage, length/digest verification and immutable selection. An interrupted publication reuses these originals; it does not author a new execution record under an old hash. [Session][execution], [completion checkpoint][completion-checkpoint]

`TargetOutputCheckpoint.retain` binds exact output identity, source edges, materialization decision, protected workspace/path and retained observation-input descriptor, and syncs the original file/dependencies before selecting its manifest. Keep those bindings and the existing point-record bound. `load` currently also invokes `_immutable_file` for the member lookup and syncs the state root. That duplicate `<job>.output-members/<artifact>.json` is a derived lookup, not another original result. Split readonly original load from explicit index repair. Missing lookup may schedule one bounded, coalesced job-level rebuild over immutable originals; do not scan the job's entire output history separately for every missing member or status read. `iter_members` already streams one record at a time and should remain bounded. [Output checkpoint][output-checkpoint]

Preserve the concrete publication order in `TargetCollectionPublication`: retain original output → declare original output/source relations through current callback authority → append the exact member through SDK → receive exact custody → release only the covered local file. `resume_output` first reconciles authenticated custody without reopening a preimage; only absence of custody requires the exact protected retained file. A missing file is never permission to run a codec to reconstruct an accepted identity. The #997 prepared-primary implementation and receipt-only warm control rules supply the SDK layer; do not create a target-specific second publisher. [Publication runtime][runtime]

At completion, `finish_success` first seals original production, validates the exact execution preimage, retains pre-root completion, builds completion records and publishes the collection. It then receives output/archive/derivation identity and records the exact successful status before runtime cleanup can downgrade it. The archived completion still has invocation, implementation, execution, target-result and output-declaration evidence with the existing relationships. Keep original reservation/UUID/timestamp/custody ordering from #997. The polling loop while production is sealing does not itself create an optional checkpoint. Native work reached by these paths uses #996's common executor and the same attached grant.

### NVENC group ordering

The current NVENC target selects `session.step_value("nvenc-output-group:" + input_id, ...)` containing three output identities before calling `publication.prepare_output` for those members. The latter is the step that syncs protected output bytes and selects each original point checkpoint. A crash can therefore select the group while a member has not reached its durable dependency barrier. Current `_resume_media_outputs` correctly fails closed on changed/missing group evidence; do not weaken that check. [NVENC implementation][nvenc]

Change only this concrete target ordering: finish and verify all three original files; sync each file and required protected parent directories; select the existing immutable three-member group record; establish/reconcile all three point output checkpoints; only then declare/append any member. On recovery, the original group fixes all three identities. A missing point checkpoint may be installed only from the exact original protected file that matches the group, never a new encoding. Existing selected groups with missing required originals remain a custody error. The group has three members because this operation contract specifies them; it is not a general archive-count limit or a multi-file atomic-rename claim.

### Tool lifetime and budget

Use the actual extension `subprocess` wrapper, `ConsumerScope`, inherited original state/permit descriptors and `BoundedExecutionDispatcher`. The native supervisor owns the tool process group, contains descendants, and continues receiving after termination escalation until the group is gone. Preserve the original object through `wait`/`communicate`; only a positive result releases its ownership. Do not return a successful shutdown on a join timeout. The POSIX supervisor's platform refusal remains explicit. [Subprocess wrapper][subprocess], [consumer scope][consumers], [supervisor][supervisor], [dispatcher][dispatcher]

There is no proven mid-operation save point for ffmpeg, ffprobe, exiftool, `file`, rclone or an arbitrary subprocess. Their external waits earn zero invented useful-work credit, and their percentage output cannot authorize an optional checkpoint. Keep exact completed output/observation as the natural mandatory anchor. Runtime CPU work that can be measured and attributed separately may use the common root meter; do not call wall time spent waiting on a tool “useful execution.”

## 7. Rclone and sealed external effects

`RcloneDestination.commit` currently copies objects, performs `check --download`, publishes `manifest.json` last, and reads the marker back to compare exact digest/length. Its exception wrapper yields `TargetEffectCommitUncertain`; the generic target owner retains interrupted effects and does not automatically execute them again. Keep those semantics, destination/rules identity and current authorization. [Rclone][rclone], [target owner][target-owner]

Before the first possible remote write, retain a small target-owned original delivery intent with job/request/plan, source selection commitment, destination/rules identity, delivery ID, original manifest digest/length, artifact count/total bytes and execution commitment. The manifest itself is a streamed immutable retained file, not a full inventory embedded in `step_value` or status. Use the existing immutable-file durability pattern and protected state admission. Keep credentials out of this record. Local object copies remain reconstructible from the exact archived source until source-retirement authority; they are not evidence of remote success.

Add a specific readonly `RcloneDestination.reconcile` path. It reads the exact configured original delivery marker, verifies its original digest/length and validates the referenced remote object bytes against the original sealed manifest. Successful exact readback can finish the same effect receipt. Schedule this bounded original reconciliation through the existing execution/due owner after the required current read authority check; a status GET only projects its retained state and never launches the provider read or subprocess. Reconciliation does not invoke `copy` or `copyto`, change a delivery ID, select new naming rules, create a replacement job, infer absence from a timeout, or treat a missing marker as proof that nothing was copied. Missing, changed or unverifiable state stays unresolved and retains the original intent. No live provider qualification is claimed here.

There is also a controller/Core gap outside rclone's explicit wrapper. `record_target_status` currently maps canceled, inapplicable and nonretryable failed outcomes to `abandon_pending`; `retry` asks Core for a fresh fence after retryable failures. A generic exception or cancellation after a possible external effect cannot justify either path. Select the following hard rule across the controller and Core owners:

- Before external-effect plan sealing, existing no-action/ordinary abandon semantics remain available.
- Once that plan is sealed, ordinary abandon, restart and no-output routes reject. Failure, interruption, cancellation, transport uncertainty, process exit, missing marker and an operator's locally inferred “never dispatched” are not closure proof.
- Keep the exact original target request, effect intent, claim/source obligation and unresolved outcome. Resume only authenticated receiving/reconciliation of that same effect.
- Only the exact successful effect receipt and owning Core settlement close this sealed effect and enable any policy-authorized source retirement.

This is a selected conservative refusal, not a deferred choice of closure API. The current contract has no independently verified authenticated no-effect proof that Core can accept; this reference does not add one. A locally positive pre-dispatch observation cannot be promoted into a forged controller authority. Normalize every effect exception after the started boundary to unresolved unless an original successful receipt already wins. Keep unknown accounting sealed as specified in [BUDGET.md](BUDGET.md), independently of the semantic original receiving obligation. [Coordinator][coordinator], [work state][work], [target owner][target-owner]

## 8. Original retention and operational capacity

Current target terminal collection retention checks active dispatcher ownership, primary publication/custody, and retained unpublished output/completion evidence. It permanently retains succeeded effects. Current observer retention removes completed status/accepted/cancel records by age and no active worker. Neither target nor observer HTTP binding currently provides a positive authenticated durable downstream-reception acknowledgement. Age and local process completion cannot supply that missing fact. [Target retention][target-owner], [observer retention][observer-owner], [target binding][target-http], [observer binding][observer-http]

For this implementation, **disable age-only collection of original accepted request/result/intent/cancel records**. Keep the current stronger unresolved primary/output/custody fences. Derived lookup files, volatile progress and unselected complete scratch generations can be reclaimed by their own proof-based rules. Application SQL retention must likewise distinguish a derived planning component from original accepted observation/child/effect obligations; cascaded deletion of a parent must not erase an unresolved original. Do not run an unbounded history scan or load every retained result into RAM to answer a status call.

This changes storage growth and must be exposed honestly. Retained originals occupy `O(retained jobs + evidence bytes)` disk. The current `maximum_pending_jobs` counts nonterminal jobs; `maximum_workers` and `ExecutionAdmission` limit live execution; `PrimaryStatePolicy` bounds prepared-primary custody; HTTP metadata admission bounds control transfers. **None currently constitutes a byte quota for completed observer/target JSON originals.** Do not claim those existing knobs solve retained-terminal capacity. [Extension admission][extension], [observer owner][observer-owner], [target owner][target-owner]

Wire a small owner-local `RetainedStateCapacity` adapter in `stove0_extension_support` through the existing target/observer constructors and supplied deployment adapters, separately from payload execution permits. Require explicit operator `retained_state_max_bytes` and `retained_state_min_free_bytes` positive exact integer settings for the dedicated protected state volume; no silent unlimited default. Connect both fields to the installed configuration and examples. Select `1073741824` retained bytes and `67108864` free-headroom bytes for the small installed configuration/qualification examples, clearly labelled fixture values rather than universal recommendations; deployment values remain explicit operator configuration. Admit exact incoming original metadata and reserve the next required output/result barrier before dispatch or disclosure. Keep accounting/reservations on existing accepted/owner records and update them with those barriers, not with progress polls. Private staging and cleanup are charged to the same operational capacity, and release requires exact original transfer/settlement proof. If the next barrier cannot be reserved, return the existing typed `admission_unavailable`/503 without accepting new work; retain existing originals and keep current status, cancellation, reconciliation and actual consumer receiving operable. Physical volume quota is the independent hard limit; leave reserved headroom for control/cancellation/terminal receipt writes.

Use this concrete protocol, without a second authoritative quota database:

1. The hard-cut per-invocation accepted/owner envelope retains `state_capacity_reserved_bytes` and `state_capacity_retained_bytes` outside its immutable semantic request. They are conservative capacity liabilities, not progress. Preserve the original request identity while replacing only the operational envelope under the existing exclusive state owner.
2. On acceptance, `RetainedStateCapacity.reserve_original` validates the current aggregate plus proposed liability against `retained_state_max_bytes` and physical free space against the separately retained `retained_state_min_free_bytes` headroom. It selects the exact original envelope and reservation before dispatch. Include accepted-request/control encoding, bounded response/completion metadata, temporary immutable-file candidates and required cleanup/receiving headroom. Use the existing metadata-response admission bounds and the operation's available output bounds; an unknown next requirement is not a zero-byte reservation. Defer dispatch if a safe next original barrier cannot be reserved. Existing protected-workspace/primary limits remain independent bounds for payload files.
3. Keep the aggregate in memory as a derived counter under that same exclusive owner. Rebuild it at startup by bounded streaming reads of the accepted envelopes or an explicitly derived index, never by loading all result bodies into memory. Do not trust a stale aggregate across restart. A missing/corrupt mandatory envelope or an unexplained original file produces an actionable capacity/custody refusal, not an empty store or a refunded liability. Normal point status reads never trigger this scan.
4. Before a larger original result becomes authoritative or is disclosed, extend its existing reservation through the same original envelope barrier if necessary. Stream/stage within the already admitted bound; leave work pending with its original protected bytes/owner if an extension is refused. A selected result cannot be dropped or regenerated to fit a quota. Completed result/dependency files become durable first; `settle_original` then replaces the envelope with verified retained size and releases only proved unused reservation. A crash between these steps leaves the older larger reservation held. Exact duplicate settlement is idempotent.
5. A lost envelope-write acknowledgement rereads that exact original selection before updating the derived aggregate. Unknown actual size, publication outcome or remaining cleanup keeps its liability and freezes new admissions until exact reconciliation; absence from an in-memory map never refunds it. Receiving already reserved original work and reporting the capacity refusal remain possible. No callback, poll or phase percentage writes a capacity record.

The original files' existing durability selections remain in force; this is not a multi-file atomicity claim. A configured dedicated-volume quota is still the independent physical bound, including allocation/metadata overhead that logical byte counters do not prove. Qualification must exercise full volume, interrupted reservation/settlement, lost acknowledgements and restart with a conservative held reservation.

Capacity refusal is an operational deployment condition, not an archival maximum artifact count, journal length or collection size. Do not erase evidence, auto-reset state, fabricate successful receipt or inflate optional allowance to escape it. Existing operator retention durations may continue to govern eligible derived records; they no longer authorize deletion of original evidence without reception proof. This reference selects retention and backpressure, and adds no general target/observer semantic-result reception or no-effect closure API. The bounded recovery cost/phase receiving operations in [BUDGET.md](BUDGET.md#3-grant-and-receipt-lifecycle) are separate; they do not prove reception of semantic evidence or authorize original-record GC.

## 9. Shared grant, public contract and private-state cut

Follow [BUDGET.md](BUDGET.md) exactly. The root application record is accepted before any child claim/collection. Original child admission retains an immutable zero-allowance `RecoveryAttachment` binding root, policy, domain, receiving component/incarnation and assignment to the exact invocation; it does not need an already earned optional grant. After useful work has accumulated, a separately numbered `RecoveryGrantOffer` may be accepted on that same assignment and invocation through the bounded grant method. Root reservation precedes offer acceptance; lost acknowledgements retain it. Later offers do not reparent work, change semantic request identity, advance an attempt, replace its progress-slot generation or dispatch the operation again.

Every target, observer, SDK/Core and Native optional operation needs its accepted disjoint offer and phase-start acknowledgement. One assignment cannot fund two Core constructions, and parallel children cannot each consume the parent's full cap. Use the shared offer/start/receive/accounting methods, not a repeated semantic seal/execute POST or a status read, to move that operational state. A child receives a cap, not a new full fraction or reset success count. An attached Core owner must also satisfy its server-local clamp; caller-reported useful time is never Core authority. Preserve actual cost receiving after closure, unknown-cost sealing and original grant/count identity across retries and phases. Each candidate still proves its own net replay saving; a parent's accumulated useful time does not make a cheap child eligible.

For remote owned children use the common bounded cohort rule, including conservative optional-overlap subtraction, suppression of further credit when accounting is missing/unknown, no parent credit during the cohort and no fresh credit for pre-restart epochs. An authenticated cumulative accounting prefix from an actual bounded execution boundary can establish conservative useful progress while the child is still running; it is separate from terminal original receiving. Coalesce these prefixes in memory, persist their required binding only with existing grant/selection/mandatory anchors, and freeze further credit while any optional accounting-phase gate is outstanding. A status poll cannot create a new prefix or increase credit merely because time passed. Do not sum overlapping child elapsed time or retroactively erase valid previously anchored credit. The tool wait exclusion in §6 applies even if the Future took a long time to complete. Required evidence/custody writes remain mandatory; they are never optional work merely because a file is named checkpoint.

Make the public cut in one integration:

| Surface | Required update |
|---|---|
| `stove0_target_protocol.TargetProgress`, `TargetJobStatus`; observer operational status | Separate processed from resumable and expose replay/uncertainty/receiving limitations. Keep original semantic result/evidence documents and their hashes unchanged. |
| Target/observer clients and HTTP bindings, supplied adapters and authentication | Carry immutable assignment, later grant offers, phase handshakes and accounting receipts outside semantic identity; use current registered authentication and exact invocation/fence binding. Status/accounting GETs remain readonly. Preserve request/error/metadata-transfer limits and declared errors. |
| `stove0_core` work/status/inspection schemas, API/CLI and application registrations | Project the same bounded fields. An old `completed` counter must not be silently interpreted as a resume point. The controller's volatile observation is not a new durable revision. |
| `Stove0Document`, `Stove0RuntimeConfig`, `generated_config_schema`, installed `config.schema.json`; concrete component settings | Connect root policy and protected scratch/retained-state capacity settings to actual constructors. Keep strict unknown-field, exact numerical and finite-control validation. No dead configuration knob or application-selected server authority. |
| Protocol/schema/conformance exporters, contract freeze, installed packages and docs | Regenerate through owning exporters, update strict consumers/examples/error coverage and qualify installed imports. Do not hand-edit only generated files. |

The source schema owner is `Stove0Document`; the installed schema is loaded using package resources. The operator database is PostgreSQL with explicit state-schema verification, while tests can use a disposable SQLite backend. New scratch format and authority-schema versions must be explicit. Opening populated incompatible control/target/observer state refuses with an actionable owner/format error **before** cleanup, tool dispatch or publication. Do not scan an old directory and silently delete entries to start fresh. Initialize only a deliberately new empty state root; no compatibility fallback may reinterpret an old progress counter or missing mandatory record as new accepted state. Two cases hold the actual dispatcher worker through close, proving the original state owner remains unavailable until that worker is received. A POSIX case launches a harmless supervised Python child and positively receives it before releasing the original lock.

The final focused run passed 13 cases. [Evidence and reproduction](evidence/stove0_validation.md) retains those outcomes and commands.

- Private planning/production/settlement replay with optional mode disabled and with an admitted complete generation produces exactly the same accepted evidence, selected scopes, error order and final roots. Unknown/missing mandatory evidence refuses; a missing optional generation replays the exact originals.
- Generation publication/currentness races, changed provider/recipe/source, stale claim/fence, incomplete dependency closure, interrupted snapshot, original-count/accounting preservation, child grant subdivision and optional overlap use the common #995/#996/#998 qualification rather than another local allowance.
- Real target/controller polls issue no persistence for identical or advisory-only observations; readers never repair the output-member index or run semantic work. Index rebuilding is bounded/coalesced once per job and never authors a replacement original.

- Every sealed external-effect failure/cancel/timeout refuses abandon/restart/no-output; exact original receipt reconciliation alone advances settlement. Rclone readonly reconciliation never invokes copy/copyto and fails closed on absent/changed marker/object evidence.
- Retained-state capacity exhaustion refuses new admission before losing required original evidence, preserves reserved cancellation/receiving headroom and remains bounded in RAM. Time-based retention cannot delete unreceived originals, including across controller outage/restart.
- Actual owner/platform lifecycle tests cover held process/descendant, failed join/close, cancellation during capability refresh and no workspace/permit release before original receiving. Review0's remote sampler tests cover the extra cross-HTTP ownership transfer.
