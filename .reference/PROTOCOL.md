# Exact custody, batching and recovery protocol

This document closes the owner-level choices in the [#997 implementation proposal](IMPLEMENTATION.md). These are proposed integration decisions under #994, not new authority conferred by this branch. Current source is `c28eceaa2dfec1b3712135469ba12230e74f5ffa`.

## 1. Evidence that cannot be regenerated

| Identity/evidence | Retain before | Owner and restart behavior |
| --- | --- | --- |
| Original create request, allocation/service/account scope, construction/delivery context, accepted completion declaration | An uncertain create reply or any member operation using the construction | SDK session and Core original construction retain exact parameters; retry queries/reuses that identity, with current authenticated access. Changed parameters conflict. |
| Member ID, payload length/hash, attribution/request, captured observation, graph, journal and materialization decision | Registration/staging/binding that could leave an accepted original journal | SDK `PrimaryStore` retains all five preimage roles (`request`, `observation`, `graph`, `journal`, `decision`) plus the original whole-manifest integrity seal. The same logical preparation returns the selected winner. |
| Accepted early primary, input-history extent/selection, completion obligation and selected final history | A custody acknowledgement or later closure/root relying on the choice | Core binding/selection records are immutable under the original construction. A content-identical payload does not authorize another journal or input selection. |
| Random encryption state, exact plaintext/request target, object/part identity, provider session and executor identity | Provider begin/part/complete/put or any ambiguous remote mutation | Existing archive preparation/effect owners retain the original preparation and request. Reconcile exactly; never generate a new key/nonce/header for an uncertain operation or reuse a continuation for different plaintext. |
| Verified effect result, sealed encrypted object/metadata/root receipt and completion output identity | A subsequent effect, custody acknowledgement, public result or source release relies on it | Receive and durably adopt exact bytes at the current owner, keeping original resource receivers through lost commit replies. A returned observation can remain unresolved even when some metadata is usable. |
| Exact materialization-decision acknowledgement | Prepared-state reclamation and terminal settlement | Independent SDK control; an authenticated custody receipt does not fabricate a setter acknowledgement. |
| Terminal request, original epoch/frontier, current authorization/claim disposition and original execution receipts | Cancellation/discard selection, cleanup and final settlement | Existing terminal owner retains ambiguity until actual quiescence and original receiving. A timeout, expired lease or changed row is not proof of stop. |

Source owners: [prepared publisher](https://github.com/nashspence/riverhog/blob/c28eceaa2dfec1b3712135469ba12230e74f5ffa/packages/riverhog-client/src/riverhog_client/_prepared_primary_publisher.py), [prepared store](https://github.com/nashspence/riverhog/blob/c28eceaa2dfec1b3712135469ba12230e74f5ffa/packages/riverhog-client/src/riverhog_client/_prepared_primary_store.py), [archive preparation/effect models](https://github.com/nashspence/riverhog/blob/c28eceaa2dfec1b3712135469ba12230e74f5ffa/riverhog/src/riverhog_core/catalog_archive_write_models.py), [archive-write admission](https://github.com/nashspence/riverhog/blob/c28eceaa2dfec1b3712135469ba12230e74f5ffa/riverhog/src/riverhog_core/services/archive_write_admission.py).

## 2. SDK prepared-primary: preserve the winner, remove redundant read barriers

### Mandatory selections remain

`PrimaryPublisher.prepare()` compares the immutable request before invoking an observer/author; `PrimaryStore.prepare_or_load()` installs the selected original preimages and sealed manifest before the producer registers/stages them. Preserve this structure. After staging succeeds but binding fails, restart loads that same original; it must not author a second journal. Conflicting input is rejected before a replacement observer/author runs. Replay strictly validates every byte it consumes.

The decisive historical correction is the [#981 receipt-only ruling](https://github.com/nashspence/riverhog/issues/981#issuecomment-6438227888), [implemented at its recorded checkpoint](https://github.com/nashspence/riverhog/issues/981#issuecomment-6438729136). Apply it across preflight, receipt admission, returned-record checks, terminal callbacks and reclaim:

- Verify the **original** complete manifest seal and its allocation/session/member/compact-control commitments; never mint a missing seal from currently observed bytes during reconciliation.
- Receive the complete receipt through the currently authenticated/authorized service. Reparse it, verify its self-commitment, and compare the exact collection/member/length/hash, every primary anchor/delivery-association coordinate, completion requirement including absence, and any original handle. The receipt's self-hash alone is not authenticated custody.
- With intact original controls and the exact authenticated receipt, missing/truncated/changed local preimages do not undo separately established remote custody. Receipt control work reads **zero pending-preimage contents**. A later byte-dependent replay still fails closed.
- Source-payload release follows its authenticated custody contract. Prepared-preimage reclaim additionally requires the independent exact decision acknowledgement. Missing decision acknowledgement keeps its obligation/reservation even after custody is saved.
- Reclaim only original fixed-name preimages, account capacity once from their **original reserved lengths**, and retain compact original commitments until authoritative allocation retirement. Deletion/flush/receiving work remains measured.

### Selected batching disposition

The current [`PrimaryStorage` protocol](https://github.com/nashspence/riverhog/blob/c28eceaa2dfec1b3712135469ba12230e74f5ffa/packages/riverhog-client/src/riverhog_client/_prepared_primary_storage.py) offers point `put_bytes`, `put_control`, `remove_control`, `sync` and child operations. Neither POSIX storage nor `TransactionalPrimaryFiles` exposes a supported cross-member atomic selector. A private SQLite transaction helper is not permission to bypass separate payload/readiness/resource ownership.

**Keep the original per-member preparation, decision, custody and reclamation selection barriers on both current adapters.** No new multi-member SDK transaction or HTTP endpoint is part of this implementation. Core's existing result transaction and the receipt-source batch below provide the safe grouping opportunities. This is an evidenced no-change decision, not an unimplemented question. Any later backend group facility would need an explicit public storage contract and actual platform crash tests; it is not a prerequisite to consume this reference.

### Warm control-only durability proof

The selected SDK optimization is a backend-owned read-only receipt lease. Establish the underlying local durability proof **as a consequence of an existing successful mandatory publication/recovery barrier**, under the original `PrimaryStore` owner; a status request must not establish it by synchronizing. The backend remembers which local mutation generation was positively made durable. A bounded `observe_controls` lease takes the existing mutex, checks the current owned generation against that proof, and reuses it for point control reads. Exit before network work, cooperative yield or wait; never hold the mutex across polls. A cold/unknown generation with no valid proof exposes only available advisory metadata and leaves any required recovery to the execution owner.

The lease binds allocation/session/member, adapter resource identity and mutation generation. Every control read still checks current storage identity, original manifest seal, exact compact commitments and candidate absence. It caches no principal permission, remote receipt or public acceptance. No writes, create, candidate recovery, removal, reclaim, ordering maintenance or reservation-changing action is permitted inside the lease. Exit it before any such operation; invalidate its underlying proof **before** starting a mutation, complete the real mandatory write/receiving barrier, and only then mark that new generation durably known. An exception, close, owner transfer, generation change, unreceived transition or uncertain write invalidates the lease. A cold reopen runs full existing recovery/barriers in execution, not in status.

Keep this capability internal to the two owned backends. The production implementation must make mutation exclusion explicit in the storage/session contract and protect its lifetime; do not implement global monkeypatching, a cached boolean across sessions, or an unguarded `sync=lambda: None`. The reference experiment uses an explicitly guarded single-threaded patch solely to measure this narrow causal cut on the real POSIX owner. It deliberately charges a fresh existing control-load barrier at entry as a conservative comparison; that entry is not a proposed status implementation. It does not qualify Windows/SQLite or the production lifetime API.

The lease optimizes read-only observation. `accept_custody`, `accept_decision`, reclaim and any unknown transition still use real durability and original receiving. Receipt validation remains proportional to selected controls plus the **complete** receipt encoding, with separate point lookup/flush/deletion costs; it is not a constant-time claim for arbitrarily large receipts.

### Closing, inventory and completion

Keep `_prepared_primary_closing.freeze_inventory`'s original selected ordered inventory and framed commitment, plus complete `finish-ready` and `custody-settled` barriers. Intermediate `closing`/`custody-closing` offsets and hash accumulators are derived replay acceleration: advance them privately in bounded quanta, with no unconditional progress write. Without an admitted optional frontier, restart scans the same immutable inventory and reconciles already durable exact decision/custody/reclaimed controls. It does not reauthor members or reapply reservation accounting. If optional progress is admitted, its bounded SDK descriptor must bind the root grant, original inventory identity, exact framed prefix/offset/hash state and independent acknowledgement dependencies; use the common complete-generation/selection handshake, not a second percentage budget or a cursor that certifies missing acknowledgements. Full inventory contents stay in their owning bounded store, not in the descriptor.

The same original `producer.finish` deadline must be checked between every closing/inventory quantum, together with heartbeat and cancellation. The audited `while not advance_closing(...): _require_heartbeat()` loop currently omits that existing deadline check. Add it at this touched scheduling seam; do not reset the deadline per phase or create a new timeout policy.

For processing consumers, preserve `IncrementalDerivedCollectionWriter.finish`'s `_seal_completion` before `producer.finish`. `CompletionRecords` holds the exact output, history, controller and disposition preimages. Core `reserve_completion_recording` commits the original record-inventory hash, random completion journal ID and recording time before SDK authoring. `canonical_completion.write_completion_journal` and the maintained target relationship provider derive their record/assertion/entry IDs deterministically from that original reservation and exact canonical inputs. Stage that terminal journal with `selection_role="completion"`; only then construct dependent final histories and roots. Any completion assertion provider must preserve this deterministic-original-input rule. A finalized retry compares the published requirement and complete receipt; it does not create a second completion journal.

## 3. Core effect grouping at existing owners

### Preparation and live dispatch

Retain `ArchiveWriteAdmission.prepare()`'s original preparation and `arm()`'s short durable reservation before dispatch. `arm()` returns a one-shot `ArmedProviderWrite` only after its transaction commits successfully. A database row found after a lost arm reply is not permission for a cold process to manufacture a live capability. Receive/withdraw/reconcile the original execution according to its actual admission/dispatch owner before another attempt.

The first implementation does not group dependent provider requests merely to reduce the count: a part often needs the original begin result, and completion needs exact parts. Nor does it hold a shared writer while generating expensive crypto state or calling a provider. Preserve the current preparation and per-dispatch barriers; group independently known returned results as the source already permits. This satisfies the requirement to examine intent/result granularity without inventing a cross-database/provider transaction.

### Exact returned-result batch

`ArchiveWriteAdmission.apply_reports(reports, apply_result=...)` is an existing safe seam. All effects have already been armed. Use one admitted, nonempty bounded tuple from the **same construction and object/volume**, with distinct call IDs. Maintain the actual executor, dispatch nonce, request commitment and target incarnation for every report. Duplicate/conflicting/mixed identities fail before any batch is accepted; each encoded result must fit its reserved capacity.

Each effect keeps its own row and outcome even though the batch shares one transaction. The final logical checkpoint is applied with the corresponding exact batch in that transaction; all-or-none rollback preserves consistency. Exact duplicate reports do not advance the logical checkpoint or release resources twice. Do not broaden this API into a cross-volume envelope without a new owner contract; the proposed first cut does not need that change.

**Observation is distinct from closure.** `report.closure is None` records an exact observation and leaves the effect uncertain/unresolved. Matching adapter closure evidence allows settlement. A batch that installs useful checkpoint metadata does not prove that every provider invocation has stopped, permit terminal cleanup, or release unresolved charge. Keep the original returned-report receiver until the owner has received both execution and result. No timeout changes this rule.

Use existing archive-write grants for aggregate source/result/control capacity and cooperative quantum bounds. A batch cannot grow merely because individually admitted results arrived. No group timer delays an acknowledgement already required to release a scarce admitted resource or satisfy a request deadline; flush a smaller complete group. No unbounded queue and no mixing independent collection locks.

The [Core experiment](implementation/core_batch_experiment.py) uses the actual encrypted uploader/checkpoint/admission owners and a controlled per-report comparator. Its comparison isolates settlement transactions. Preparation, arming, ciphertext, report retirement and receiving remain present; the observed reduction is not a new-path F1 speedup or physical sync count.

### Verified member-custody batch

Extend the existing [`ArchiveArtifactCustodyReceiptFinalizer`](https://github.com/nashspence/riverhog/blob/c28eceaa2dfec1b3712135469ba12230e74f5ffa/riverhog/src/riverhog_core/services/archive_artifact_custody_receipt.py) with an immutable tuple of already captured `ArchiveArtifactCustodyReceiptSource` values for one construction. Selection and dependency verification happen outside the final acknowledgement transaction, through the original semantic/provider owners. The tuple is fixed once selected; never pick the next members after a lost reply to the first batch.

Admit the tuple by member count and sum of `reserved_source_bytes` plus actual receipt/control/write-result capacity. In one existing short writer transaction, call each source's `apply(session)` in stable artifact order. Each source rechecks its exact original primary/member/history/completion requirement and construction. Atomically store every receipt, completion output, custody-due update and both release counters. If any fresh source is stale, the entire uncommitted group rolls back. Existing identical acknowledgements are received idempotently; a second different receipt conflicts. Do not acknowledge a prefix of a failed group.

An already committed exact acknowledgement may be received after the terminal gate closes. A new acknowledgement requires the original forward epoch/open gate. After publication, including while its upload parent awaits retirement, each source uses `_verify_published`'s exact surviving construction and published member receipt/root; absence alone fails. The enclosing **single retained batch finalizer** preserves the original tuple and cached result through commit/reply loss. It owns the terminal lock/fence and uses `ArchiveFinalizerTerminal.drain_original(operation_id, None)` after nonblocking lock acquisition, as the current single-receipt finalizer does; source values are immutable data and have no drain method. The registry separately retains original semantic/provider/resource owners. A closed batch drain fences new acknowledgement; it does not establish that an unreceived transaction committed or release its resources. Receiving an old result must not be confused with fresh forward authorization.

No new public bulk receipt route is required. Existing per-member readback may return committed receipts; batching is an internal persistence choice. The public reader still applies current read authorization and exact original identity checks.

## 4. Failure and recovery decisions

| Observed failure window | Required next action; prohibited substitution |
| --- | --- |
| Before prepared-manifest selection completes | Resolve the original storage transition under its owner; no remote staging from a provisional candidate. Retain partial storage/resource evidence until safely received. |
| Journal staged; bind/decision reply absent | Load original sealed preparation, compare immutable request and replay/reconcile that exact journal/binding/decision. Do not invoke author/observer again to produce a different winner. |
| Missing local preimages, controls intact, authenticated exact custody available | Admit custody through control-only path; retain outstanding decision/terminal obligations. Strict byte replay reports the actual corruption; no new original is authored. |
| Preparation commit reply lost | Reload original preparation identity under its owner; never assume rollback and mint a new random encryption state. |
| Arm commit reply lost | No new capability is returned from the failed call. Reconcile original admission/executor outcome; unresolved intent stays charged. |
| Provider call throws/connection drops | Distinguish a positively not-started or adapter-proven closed call from an unknown possibly effective call. Preserve the latter and reconcile via exact original target/session/request. |
| Report transaction rolls back | Keep the original reports and the old logical checkpoint. Retry the exact same bounded batch through original-report receiving with its exact construction/request/closure fences, including after terminal selection. This is not fresh forward admission and must not require the now-closed forward gate or a new epoch. |
| Report transaction commits but reply is lost | Read back exact effect results and corresponding logical checkpoint; receive rather than redispatch. Divergent confirmed result is a conflict. |
| Provider sealed, custody/index/catalog not complete | Preserve the sealed receipt and original authority. Resume/rebuild only the unfinished derived or acknowledged portion; no source release based on a mere candidate and no destruction of sealed custody. |
| Derived generation/candidate missing or corrupt | Quarantine only optional/rebuildable state after original receiving; restart from mandatory exact source/outcome or earlier verified anchor. Missing mandatory evidence remains fatal/unresolved. |
| Index dataset changes after preparation, including same-count mutation | Content-revision/root/epoch CAS fails; discard the candidate. Reprepare from the current immutable accepted set; do not accept solely matching counts. |
| Final publication transaction loses its reply | Privately receive the exact original published tuple, input binding and index seal through the retained original owner. Public result readback separately checks current read authorization. A missing upload row or unrelated published collection does not prove success. |
| Gate closes while old worker is paused | Deny new forward work; retain and drain the original. A later sealed outcome can change terminal eligibility. Do not free its input/provider session or count it as stopped. |
| Optional generation selection/cost unknown | Pin the uncertain candidate and original receiver, seal further optional admission and preserve prior usable selection. Authorized mandatory work may continue with optional tracking abandoned; do not invent budget reset or block forever solely on optional progress. |
| Close/join/cleanup fails | Keep the exact owner reachable and its resources charged; report the pending settlement. Retry original receiving, not construction of a replacement receiver. |

## 5. Terminal selection, cancellation and original resources

Retain the [#984 adopted quiescence contract](https://github.com/nashspence/riverhog/issues/984#issuecomment-6559497945), its [atomic checkpoint/lock-order refinement](https://github.com/nashspence/riverhog/issues/984#issuecomment-6560933087), and [subsequent original-owner integration](https://github.com/nashspence/riverhog/issues/984#issuecomment-6716988796), reconciled with current source. The accepted reference is `684558c7446254dfbe9980725361e4ac10b8e3a8`; its existence is not public activation. In particular, the current public routes remain legacy as documented in IMPLEMENTATION.

Use the current owner lock order, not an ad hoc collection-wide mutex: authorization/key and stable-ordered claim locks precede upload/control/terminal locks; provider waits and actual worker joins occur outside them. Terminal selection atomically closes forward admission and retains the original request, epoch and frontier. Fresh or resumed effects recheck the gate under the same owner lock. Existing original reports have their separate receiving path.

Cancellation is pending until every participating reservation, input assembly, prepared constructor, dispatch, provider call, finalization/custody child, immutable report and Native reader/worker is positively reconciled. Unknown constructors and no-receiver returns stay pending. Cancellation cannot discard a sealed outcome; the terminal owner must produce the existing sealed refusal/reconfirmation semantics. Orphan discard additionally retains current deletion authority, original construction, inactive processing claim and the exact confirmation frontier; recheck renewed claims and authority each turn. Do not reuse a previous positive authorization result.

Discard planning remains a currently authorized **read-only** challenge/frontier operation. Only the later discard selection closes admission. Private original completion/resource receiving is also distinct from public result readback: `ArchiveUploadTerminalConfirmation.receive_completion` verifies its exact original target/identity, exposes no result data and grants no disposal authority. It does not require public read permission, so key revocation cannot strand an already confirmed original merely by blocking its private receiver. Public receipt/result reads still require current read scope; fresh mutation and disposal still require their current write/delete guards.

Required cleanup uses the original provider/session/resource identities and existing capacity grants. Replayable scan cursors may be coalesced; original quiescence and deletion predicates cannot. Do not delete unresolved remote sessions, infer resource withdrawal from a closed-state flag, or hide unpaid cleanup after reporting fully settled. Source custody, logical result, execution completion, resource close, worker join and ordinary admission withdrawal are distinct facts.

The [#989 adopted implementation](https://github.com/nashspence/riverhog/issues/989#issuecomment-6835494738) already separates coordination, original worker work and receiving. Its returned integer counts scheduling bookkeeping bounded by `4 * limit`; it is not a count of retired files or completed Native work. Keep original exception-frame receiving on the retained execution path, plus the positively unstarted reservation case and causal negative controls. Phase coalescing in #997 must not regress that distinction or move filesystem/frame traversal back into a scheduler poll.

## 6. No-change dispositions and what must actually change

Keep original prepared evidence and whole-manifest integrity, receipt-only reconciliation, independent decision acknowledgement, crypto-before-provider preparation, one-shot live capabilities, exact report/custody receiving, late-write terminal predicates, encrypted archive identities, independent recovery and existing original-resource accounting. These mechanisms have concrete obligations; the focused experiments test reuse rather than replacing them.

Change redundant warm read barriers, per-yield Native/Core projections, replayable registration/history/catalog cursors, semantic work performed under shared writer ownership, and final catalog/index acceptance granularity. Required final output rows still need bounded installation; their presence cannot excuse an extra durable recovery machine. Implement the public route/terminal activation as a coordinated hard cut, and retain actual focused/backend/platform/full-lifecycle qualifications specified in QUALIFICATION.

This division supplies an explicit disposition for every reviewed seam. Reference experiments demonstrate only the paths and conditions recorded in VALIDATION; unchanged mechanisms must still participate in the integrated end-to-end and fault tests.
