# Processing claims, exact outcomes and economical set construction

This is the selected #998 proposal for Core and SDK processing owners at `c28eceaa2dfec1b3712135469ba12230e74f5ffa`. [IMPLEMENTATION.md](IMPLEMENTATION.md) supplies the integration order; [BUDGET.md](BUDGET.md) owns composed accounting. All product paths remain unchanged. The common collection publication mechanism remains [#997](https://github.com/nashspence/riverhog/blob/a7ea19bf795c249476c9d767eb821d74bcf98b2a/.reference/IMPLEMENTATION.md), not an application-owned archive writer.

## 2. Accepted rows versus replayable hash state

Current append methods commit each bounded exact batch and export `input_hash_state` or `artifact_hash_state` into the same row. These continuations accelerate hashing of already retained rows; removing them does not erase accepted inputs. They are derived even though they currently share a required commit. Merely piggybacking extra replay state does not make its encoding/storage cost mandatory or free.

Retain input/artifact/capability rows, accepted ordinal/count/byte accounting, duplicate comparisons and original canonical order. A lost append reply retries the exact ordinal and values; divergent bytes conflict. Do not drop accepted rows because a final set is not yet sealed. The new private set conductor holds hash continuation and the verified accepted prefix in memory/private admitted scratch, keyed by owner, fence, set kind and exact source revision. It advances through the same canonical framing functions; it does not change `claim-inputs`, `claim-artifacts`, disposition newline framing or `claim-outcomes` framing.

On a warm append, advance the private prefix only after original transaction receiving. An uncertain commit is reconciled by exact accepted row keys/contents; it neither advances twice nor repeats external work. On cold start, rebuild one prefix in bounded canonical-order pages from accepted rows, or restore a verified admitted optional generation. Do not restart that full scan for every appended page. With optional recovery disabled, losing that private prefix is permitted and reported honestly.

The seal request freezes the accepted set and retains its exact original intent in the existing set owner when asynchronous work is needed. Use the same conductor in all modes. A ready warm result can complete in the existing bounded acceptance call; a cold/large set returns a bounded accepted `sealing` state and advances through execution/due work. No status read performs the rebuild. This is one executor with retained live state, not separate durable and fast implementations.

Extend input/artifact/capability receiving responses coherently to `receiving`, `sealing`, `sealed`, `failed`; no usable identity exists until `sealed`. Update SDK, controllers, capability issuance and installed consumers together. Waiting preserves the original caller deadline and current lease/heartbeats. A known semantic failure remains a typed failure; interrupted private execution can rebuild from exact accepted inputs. Remove obsolete per-step hash-state fields/interfaces rather than keeping a second legacy execution route.

Claim input/artifact status is read through the existing `get_processing_claim`. Add the bounded authenticated `GET /v1/collection-processing-claims/{claim_id}/capabilities/{capability_id}/artifacts/status` route and `CollectionWorkflowMethods.get_processing_capability_artifact_status` for the otherwise missing capability seal readback. Its typed response includes the exact claim/capability/fence/scope revision, accepted count/bytes, status and complete identity or typed failure; it never returns the capability bearer token. Read status from accepted control state without advancing execution. Update the current composite SDK methods `create_or_resume_processing_claim`, `seal_processing_claim_plan` and `create_processing_capability`, plus Stove0's `_acquire_document_claim` and `_stage_artifacts` in `stove0_core/riverhog.py`, which currently expect an immediate sealed identity. They retain original request identity and deadline, renew the real claim lease independently, and poll bounded status until exact seal acceptance. They must not force a capability active or repeat the seal/creation POST to drive work. Capability activation continues only after the exact sealed scope and current authorization checks pass.

## 3. Complete set preparation and acceptance

Add a focused Core `ProcessingSetExecution` owner/registry alongside the current collection-workflow service, not a reusable workflow service. Existing maintenance invokes bounded scheduling; worker execution, reads and waits stay outside scheduler locks. An original operation object remains retained until its result and resources are positively received, including failed close. Capacity refusal leaves an accepted seal request pending/discoverable rather than falling back to synchronous unbounded work.

Use one operational `processing_semantic_revision` on the claim, plus `scope_revision` on each independently accepted capability and `set_revision` on its disposition/outcome owner where required. Advance the appropriate revision in the SAME existing transaction that changes protected accepted rows, selected work/plan, exact evidence, outcomes or source-release state. Required participants include `_clear_plan`, `_insert_processing_outcome` including child settlement attachment, consideration evidence/subject insertion or removal, capability scope reset/revocation, and deletion/retirement/cleanup delegates. Lease/contact/advisory updates and installation of the deterministic ordinals for an unchanged frozen set do not change the captured semantic revision. Revisions use canonical nonnegative text and never reset or reuse a value. Fenced plan replacement invalidates the old execution even when the replacement has equal counts.

Each private operation captures a fixed binding: claim/work/execution, consumer, fence, set kind, source revisions, sealed input/plan identities, accepted counts and expected digest where provided, plus algorithm/encoding identity. Bounded keyset reads repeat that binding check in the same fresh source-consistent read snapshot as the page. They do not adopt the latest revision halfway through a scan. A changed revision aborts the candidate and requires current-owner reconciliation. A missing source or accepted outcome is not an optional-cache miss.

Do not assume today's processing claim blocker supplies the necessary source pin: an expired active claim without output can stop blocking deletion. Add an accepted-seal-pending/original-receiving blocker in the existing `processing_claim_blockers` owner, consumed by `collection_deletions.py`. It retains the exact claim dependencies independently of execution-lease expiry from accepted seal intent through original execution/installer/reader receiving. Clear it only after complete accepted selection or safely failed execution AND positive receiving of the original resources. Current-source revocation prevents new reads/selection; it does not discard the original owner or source pin. This closes the gap where an already validated source could otherwise disappear before final acceptance without changing the claim's revision.

Disposition and outcome ordinals are needed by current exact paging contracts. Preserve that representation: generate deterministic ordering outside the shared writer, then install bounded `(original row key, ordinal, prepared-generation identity)` batches. These are required final representation writes, not private hash-cursor checkpoints. Matching retry batches are idempotent; incompatible rows conflict. Installation is write-once for this generation and does not advance the captured semantic revision. Until final seal acceptance, public identity-gated paging cannot treat provisional ordering as a complete set. The operational prepared-generation identity binds claim/fence/source revision/set-kind/algorithm and is independent of archived bytes.

The original private owner produces a typed `PreparedProcessingSet` only after verifying every canonical row exactly once, the full canonical count/digest, contiguous required ordinals with no duplicate/omitted row, and the exact completed installation generation. It contains the immutable captured source/fence/algorithm binding and this complete proof, not merely a count or last-page cursor. Verification executes outside the shared writer. Retain at most one pending required installation generation per set; separately admitted optional generations obey the common configured generation limit. Invalidation first stops adoption and requests cancellation, then retains the original installer/readers until positively received before clearing their provisional generation. Cold recovery rebuilds/validates a complete proof from required accepted rows and exact installed batches; it does not trust a partial durable cursor.

The final short transaction acquires the current application-key mutation lock using the existing `retain_key_authorization` fence, then stable-ordered claim locks and the set lock. Call `services/app_keys.py::require_current_principal` inside this same transaction, serialized with the `AppKeyRecord` mutation used for revoke/grant changes; the router's earlier `Principal` and `_owned_claim`'s consumer-ID comparison are insufficient for fresh acceptance. Check current controller/key/fence and the appropriate original reconciliation authority, compare the captured fixed binding and original `PreparedProcessingSet`, and select the complete seal and final immutable semantic receipt atomically. No full set rescan belongs in that acceptance transaction. Use the same source protections for bounded installation; do not add a loose count-only final check. Required accepted rows are frozen while sealing; all ordinary mutation/reset/cleanup delegates must participate in the revision/fence protocol. A lost seal reply reads back the same complete receipt. A changed/missing receipt fails; a state name alone is insufficient. Revoked public authority blocks new selection/disclosure while the narrowly bound private original receiver retains outcome, cost, source blockers and resources until received.

Private spill, provisional ordinal installations and optional saved pages all enter the existing Core resource-admission ownership, with explicit live-byte reservations and concurrent-owner limits. A worker-count limit alone is insufficient. Reserve before allocation or installation, retain the liability through uncertain close, and release only after original receiving; required rows already accepted by the public operation cannot be evicted to make scratch quota. Use one in-progress set execution per claim/set, bounded keyset batches and fair admission pauses. Extend the owning capacity declarations/installed configuration where the existing controls do not cover this byte class; do not default to unlimited scratch or add a hidden total set-size limit.

The current `_advance_disposition_set` writes phase, two cursor families, hash continuations and timestamps under its writer transaction on each turn. `_advance_outcome_set` similarly writes cursor/count/hash and required row order on each page. The selected cut removes those unconditional derived projections while retaining full canonical validation and required ordering installation. Optional resumability can save the private conductor only under the common root grant and complete #996-compatible generation protocol. Null resumable state means recomputation from the retained authoritative set, not a partial durable identity.

Exact settlement and source-retirement checks remain with their current owner. They include the complete accepted disposition identity, byte-exact preserved successors, immutable collection roots, accepted completion, retained effect/no-output evidence, exact parent binding, every required leaf outcome and declared source-retirement permission. Keep these metadata acceptance checks; do not replace them with cached target status or broaden the current archive/deletion contract. For long metadata proof work use the existing execution role and current source protections; coordination/status never invokes the proof. #999 continues to own actual deletion/storage mechanics. No provider wait, tool execution or Native replay is added inside a shared catalog writer.

## 4. Effects, no-output and abandonment

The current settlement owner has important correct behavior: exact replay survives service restart, lease expiry under the same current fence, source deletion, `retiring` and `released` states. It compares the original settlement and parent binding, rather than treating a retry as new work. Keep that behavior. Fresh execution/capability use still requires a live lease; original settlement receiving must not be stranded merely because that execution lease expired. Current controller authentication and exact identity checks still apply.

There is a concrete gap to close: `_require_no_execution_output` prevents restart once an external-effect plan is sealed, but ordinary `abandon_claim` only calls `_require_no_transform_output`. The controller's ordinary nonretryable failed/inapplicable/canceled mapping can consequently attempt abandonment and remove a source blocker even though an external effect is unresolved.

**Selected conservative behavior:** after `result_kind="external-effect"` is sealed, ordinary abandonment, restart and substitution with a no-output outcome are refused. Controller failure/cancellation/timeout/process exit/missing remote marker cannot clear the original effect or its source claim. Preserve the original accepted target job and expose unresolved effect/receiving state. Only the exact successful effect receipt and existing Core effect settlement close that execution under this proposal. Pre-seal no-action/abandon and explicitly declared no-output workflows retain their separate valid paths.

This refusal also applies when a local component thinks a sealed external-effect invocation never started: there is no current end-to-end authenticated Core-owned negative-effect receipt contract to adopt that assertion. This proposal does not invent one or make it an implementation prerequisite. The selected behavior is conservative retention, with current operator-visible ownership and admission pressure. A separately authorized future contract could prove a narrower negative outcome; it is not a missing decision for #998. `STOVE0.md` specifies the matching target/controller exception and cancellation mapping.

For declared no-output work, preserve exact controller evidence, operation permission, all input dispositions and successful `NoOutputSettlement`; no-output is not the absence of output, an exception, an abandoned claim or a timeout. Mixed parent workflows must retain and validate the full exact set of leaf collection/effect/no-output settlements. A local coordinator completion receipt cannot stand in for the verified leaf outcomes. Source retirement retains its explicit recipe/operation permission, coverage and grace; lease expiry does not authorize it.

## 5. SDK processing and public coupling

Keep `ClaimedCollectionRuntime` and `CollectionTransformRuntime` capability readers/refresh, input materialization/workspace admission and original close. Reusable SDK code imports public application-independent contracts; it does not import Stove0, FTP or Gogurt implementations. `DerivedCollectionWriter` and `IncrementalDerivedCollectionWriter` continue to delegate publication to the common SDK/Core owner.

`IncrementalDerivedCollectionWriter.finish` must retain its order: exact completion preimages and the original recording reservation, deterministic completion journal authoring, completion-stage acceptance, then producer finish and final receipt. Preserve every output mapping and selected input history, including late retained history/retractions; a convenient current file is not a replacement for original captured history. The shared #997 activation must reach the actual public routes before these consumers claim it is active.

Runtime close, factory admission, source byte custody, completion spool close and publication receiving remain separate. A failed/uncertain close retains the original resource owner; no automatic replacement reader or completion upload may bypass it. Forward current authorization/fences at source acquisition and effect/adoption boundaries; do not cache permissions with immutable history selections. Carry one original deadline through metadata retries and polling. Status should distinguish processed/advisory work from complete resumable state and pending original receiving.

## 6. Qualification and state disposition

The actual unchanged baseline ran **63 cases**: all maintained Core collection-workflow tests, selected SDK processing-history tests, and focused original close/retry/completion-admission witnesses. It includes conflicting retries, exact effect/no-output/mixed settlement, stale fences, source-loss evidence, parent outcomes and exact completion bytes. It uses SQLite/seeded published metadata and controlled API fixtures; it is not an installed complete processing lifecycle or the proposed implementation. Exact commands/results are linked from [VALIDATION.md](VALIDATION.md).

Integration adds causal tests for zero derived hash/cursor writes in cheap mode; one bounded private rebuild; source/plan/revision changes between pages and final acceptance; same-count mutation; incomplete required ordinal installation; lost append/seal/settlement acknowledgement; unknown effect refusal; expired lease versus current-fence receiving; original resource close refusal; exact nested outcome coverage; late source deletion; and current permission revocation. Count result/intent/ordering transactions separately from optional saves. Use actual backend commit/rollback events; do not call them physical fsync counts.

Update `catalog_workflow_models`, the current Core baseline, public workflow transport/router/client, SDK and application consumers together. Populated incompatible pre-v1 state is explicitly refused; startup must not clear accepted evidence, outcomes or unresolved claims. Existing compatible owners receive old work and preserve their state. Reinitialization is only for genuinely new/empty state via explicit state tooling. This reference does not supply or assume a migration of irreplaceable work records. [QUALIFICATION.md](QUALIFICATION.md) states the exact integration gates and installed/platform limits.
