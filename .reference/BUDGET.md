# One application workflow budget

Selected proposal for #998. This extends the ownership mapping of the pinned [#995 policy reference](https://github.com/nashspence/riverhog/blob/b545a77996fbc9fe98019796860473bda1bb1aa0/.reference/IMPLEMENTATION.md); it does not replace its admission arithmetic or give this reference authority. [#994](https://github.com/nashspence/riverhog/issues/994) controls. Public names below are proposed operational contracts, not claims that the audited source already implements them.

## 1. Root ownership and configuration

Use the existing durable application acceptance record as the root of a logical application workflow. Never create a recovery database or service. Add `recovery_policy`, `recovery_accounting`, `recovery_revision` and a bounded active-grant set to that record's owning state model/store, outside its semantic identity. Keep lifetime counters as exact nonnegative decimal text where a fixed SQL integer would impose an artificial lifetime ceiling. Reuse #995's focused policy values and validation: adaptive; net replay target 120s; optional fraction 1/8; unlimited successful checkpoint count; two usable generations. Root policy is snapshotted at original acceptance and remains fixed through retry, claim renewal, phase, worker and child changes. A stricter child policy can suppress optional work, not enlarge the root's allowance.

| Workflow | Existing root and selected treatment |
| --- | --- |
| Stove0 recipe/work, including nested branches and target collections | Root `WorkRecord.work.work_id`, owned by `stove0_core/work_state.py` and its store, exists before Core claim/output collection. Child WorkRecords carry the original root reference and disjoint grant; they do not initialize independent policy. Preview work is a separate accepted preview operation only when the operator actually requested an independent preview; accepting that preview retains its semantic evidence but does not duplicate its spent budget as new credit. |
| Review0 as a Stove0 target, including its samplers | Inherit the root work/invocation attachment. Subdivide the same grant for bounded sampler/SDK/Native work. No per-sample percentage. A standalone accepted Review0 job can own a root on its existing job record. |
| FTP delivery | Root is the original durable claim/manifest identity in the spool's existing state owner. Attach it during the same claim-registration transaction that accepts the original manifest. All retries and eventual SDK/Core publication keep that root. Separate independently accepted claims are independent logical workflows. |
| Direct CLI upload | Use #995's Core construction root. CLI/SDK optional work needs a server grant; CLI policy is a stricter local clamp. A CLI command consuming an existing processing capability forwards its existing root attachment. |
| CLI retrieval/local publication | Pass the existing materialization operation's policy/attachment to the #999 owner. This reference does not create a second output authority or redesign local publication. |
| Gogurt arbitrary dispatch | Preserve the existing original dispatch ledger. The opaque command has no proven mid-operation checkpoint or useful-work accounting; declare tool-level restart limits and zero optional midpoint work. Do not add a checkpoint store merely to implement configuration. A cooperating supplied child receives the original attachment through its explicit supported invocation contract; arbitrary argv receives no invented resume ability. |
| Event relay and witnesses | Their accepted delivery cursors, original signing/calendar intents and exact evidence are mandatory anchors. The reviewed paths need no optional computation checkpoint and no new budget store. Policy remains available through owned settings for an actual future optional consumer, not through an unconditional new write. |

The root survives required receiving and charged cleanup. A root WorkRecord cannot be compacted away while any child grant, exact result, process, source or cleanup outcome is unresolved. A finite completed-root retention policy must retain whatever existing contracts still require; budget retirement does not authorize deleting semantic evidence.

## 2. Attach grants without transferring authority

Keep the current application/controller, target/observer, processing capability and Core contracts as the authority boundary. A recovery grant authorizes only optional resource expenditure within an already authorized operation. It grants no input read, output write, source deletion, target invocation or server setting change.

Use a shared operational `RecoveryAttachment` value in `riverhog-protocol`, consumed through public imports. It carries the immutable root owner/application identity and stable root ID; effective policy digest; exact logical replay-domain ID; stable receiver-assignment ID; exact accepted invocation/execution identity and original receiving component/service incarnation. It contains no credentials or initial spending authority. Establish this zero-allowance assignment at original admission, including cheap work that has not earned any credit. A separately numbered `RecoveryGrantOffer` later binds that same assignment to the parent grant/revision, disjoint optional cost reservation, potential-success count slots and capacity references. This permits the first long in-flight domain to receive a grant after useful work has accumulated without reparenting it or recreating its invocation. The full root grant remains with its existing owner; the bounded attachment/offer is not a workflow transcript.

Place attachments outside `WorkIdentity`, `ExecutionEnvelope`, observer evidence, target plans, artifact/history hashes, completion journals, creation idempotency hashes and archived receipts. Existing canonical semantic encoders retain their exact inputs. The operational request envelope/state version changes in the coordinated hard cut; adding an attachment to a semantic model that happens to be canonically hashed is not an acceptable implementation.

For Stove0 → target, capture the operational attachment alongside the original accepted request before optional work. Authenticate it as part of the existing current controller/target channel and compare it to that accepted invocation on every adoption. A raw attachment is never a bearer capability. Before dispatch, persist the assignment against the exact receiving component and stable invocation/creation-idempotency identity in the parent's original owner. Later offers are addressed only to this configured component and original invocation. A target may forward only an authorized subgrant whose cost and count reservations have already been deducted from its parent envelope; parallel branches cannot each forward the whole parent cap.

For controller → Core, capture the original attachment on the Core processing claim through the existing authenticated controller-owned claim/plan admission. Output construction obtains it from that verified claim/capability binding, not arbitrary target-supplied useful-time assertions. For FTP/direct application publication without a processing claim, the authenticated creating principal supplies the attachment on original construction admission; it becomes immutable operational control state. A conflicting retry cannot replace the root, assignment or original invocation. Core enforces an indexed unique `(root_owner, root_id, receiver_assignment_id)` binding on construction control state, so one parent assignment cannot fund two `ArchiveWriteControlRecord`s. Multiple separately reserved offers can fund the same original construction; every offer retains its exact assignment and unique sequence. Attachment must be established before any optional work; an already independent construction cannot be retroactively reparented to reset accounting.

An attached `ArchiveWriteControlRecord` remains the Core safety/resource owner and receives exact costs/results, but does not mint another workflow percentage. It may spend only a disjoint attached reservation AND satisfy its server-snapshotted policy/local admission. Server-observed fresh work remains the basis of that local clamp; caller-claimed useful seconds never become server credit. This intersection can conservatively refuse a checkpoint that the parent alone could afford. Standalone Core construction retains #995's existing root behavior unchanged. Optional eligibility is not a reason to refuse mandatory authorized semantics.

There is no transaction across application and Core databases. Original zero-allowance assignment is accepted once. For each later offer, the root reserves first by CAS in its existing owner transaction; the receiver then accepts the exact offer on that already accepted operation. Lost offer acknowledgement leaves the root reservation held. Existing authenticated operation readback returns the exact assignment, offer and original cost/result receipt, so the original controller can reconcile them. No arbitrary callback URL, root-supplied SQL file, cross-application implementation import or new central scheduler is needed.

## 3. Grant and receipt lifecycle

Use the #995 grant sequence/CAS, conservative cost envelope, count-slot, unknown-cost, failed-attempt and retirement semantics. Root reservation is persisted before optional candidate construction; every selected generation consumes one root success slot exactly once. Splitting one candidate among workers does not create several checkpoints; separate successful generations require separately reserved slots. Parent envelope reservation is counted once, and child actuals settle into it rather than being added again as another parent cost.

Add these bounded operations to the existing accepted-operation protocols and client adapters. For HTTP owners, append the suffix to the existing canonical operation URI; no alternate operation identity or service is introduced. Local owners use the same typed methods directly.

| Typed method | HTTP suffix/method | Exact behavior |
| --- | --- | --- |
| `offer_recovery_grant(original_operation, offer, expected_revision)` | `POST /recovery/grants` | Accept the exact already-reserved offer on its immutable assignment. Same sequence/exact bytes returns the original acceptance; conflicting bytes, another receiver or another invocation fail. No optional execution before acceptance. |
| `start_recovery_phase(original_grant, exact_phase_request, expected_receiver_revision)` | `POST /recovery/phases/{phase_id}/start` | Parent reads the receiver's cached exact phase request, records its own freeze gate/reservation, then sends a permit to that configured receiver. Receiver accepts the exact permit idempotently and schedules execution outside the control call. Lost reply keeps the parent's gate/reservation pending; exact retry/readback returns the same acceptance. |
| `receive_recovery_phase(original_grant, phase_id, exact_cost_prefix)` | `POST /recovery/phases/{phase_id}/receive` | Parent reads and positively receives the receiver's exact cumulative costs, closes its local gate once, then acknowledges that same cost prefix to the receiver. Unknown outcome retains liability and seals new optional admission. The acknowledgement retires only that received accounting obligation; it does not settle semantic results or close a process by assertion. |
| `get_recovery_accounting(original_operation)` | `GET /recovery/accounting` | Return bounded cached assignment/offer/phase/prefix state. No execution, full-history scan, checkpoint creation or worker receiving. |

Use a **parent-driven pull handshake** over the parent's existing authenticated connection to its configured receiver. The receiver exposes a bounded pending phase request and completed cost prefix in cached accounting readback; the parent reads them, records the root gate before sending a start permit, receives exact costs locally and sends their acknowledgement. Core never calls an arbitrary FTP/CLI/Stove0 URL, and a CLI need not become an HTTP server. Each immediate parent applies the handshake recursively: it obtains its own upstream permit before allowing a child phase. Keep the bounded active-grant/phase summaries and exact request hashes in their original owners, with phase IDs unique within their grant. A lost permit or cost acknowledgement reconciles the same phase through readback. Deferred optional cleanup waits for the same permit; an unavailable parent leaves its original reservation/capacity held rather than running invisible optional work. Mandatory process/resource receiving continues independently.

Persist phase uncertainty with the existing grant liability record; a restart never infers a refund or a closed phase from absent volatile state. Current authorization is required for a new offer or phase-start permit. The separately bounded original-receiving path can settle the already owned phase after revocation without granting new execution or public disclosure. In particular, Review0's original-only receiving proof cannot authorize a grant or phase start. Status returns cached requests/costs without executing their work; the execution owner performs the permitted phase. Do not drive grants or phases by repeating a semantic seal/execute POST.

Add operational `RecoveryAccountingPrefix` and `RecoveryExecutionReceipt` values to existing bounded progress/readback and terminal contracts respectively. Their exact binding always includes root/domain/receiver-assignment/invocation, original accepted request hash, source/algorithm binding, worker generation and monotonic prefix sequence. Pure fresh-useful prefixes have no grant, allowing first eligibility on the original zero-allowance assignment without fabricating a grant zero. Optional lifecycle amounts, held unknown costs and a selected generation identity must instead bind the exact accepted grant and phase; bounded active-grant summaries accompany the cumulative fresh useful amount. Only the terminal receipt additionally attests original execution receiving, while unresolved grant cleanup remains with its original owner. A prefix is immutable once emitted at a complete execution accounting boundary; a repeated sequence must have identical amounts and bindings. These values are separate from target-specific `TargetExecutionEvidence.runtime` and archived effect/completion evidence. Generic target runtime dictionaries, process duration, queue age and an outstanding Future are not measurements of fresh useful work.

The receiving owner verifies the original prefix/receipt on the currently authenticated exact operation channel before folding accounting. Core-generated records are obtained from Core readback, not accepted as new authority merely because a target forwards JSON. Duplicate exact prefixes/receiving do not change cost/count/credit twice; conflicting bytes or regressing cumulative amounts fail. Application restart cannot allocate a new grant to escape an unresolved original. Returned output, terminal semantic status, process/resource receiving and accounting receiving remain separate facts. A private original receiver retains the #997 distinction from public result reads: verify its original identity without granting new disclosure/mutation authority; revocation must not strand an already owned original.

If cost/receipt outcome is unknown, retain known reservations and slots and seal further optional admission for that root. Continue authorized mandatory work and original receiving. An unclean cost epoch cannot invent missing credits or erase possible unrecorded cost; follow #995's selected conservative completion without further optional checkpoints when exact finite reconciliation is unavailable. Neither a timeout nor an empty active cache proves a refund is safe.

## 4. Conservative useful elapsed across application processes

For actual locally owned pure execution, count the union of fresh useful intervals once. Exclude replay, sleeps, polling, scheduling/backoff, provider/network waits, process waiting and optional work. Exclude an interval whenever optional work overlaps useful work. These signals come from the execution owner at bounded boundaries, not from a status request. The counter is volatile between existing durable anchors; do not add a per-callback timing journal.

Across hosts, do not sum child wall times or assume synchronized monotonic clock origins. Select this conservative **cohort rule**:

1. When the root's active remote invocation count changes 0→1, open one volatile cohort using the root monotonic clock. Suspend local useful credit while that cohort's originals or optional accounting phases remain open. Children can report bounded cumulative accounting prefixes WHILE RUNNING; the first long remote Native/planning domain can therefore become eligible before terminal completion.
2. Maintain only the bounded active original invocation set, each original's last exact prefix sequence/amounts/receiving time, a maximum conservative child cumulative fresh-useful duration, a conservative optional-overlap debit, the already credited cohort lower bound and an accounting-known bit. A newly admitted child joins the same cohort while any original or accounting phase remains active. Phase changes do not close it.
3. On a new authenticated prefix, take the positive fresh-useful delta from that original's last prefix and cap it by the root monotonic interval between those prefix observations (the first interval starts at original dispatch admission). Add that capped delta to that child's conservative cumulative fresh duration. Use the MAXIMUM such cumulative child duration, never their sum. This per-prefix cap prevents an early oversized remote duration from gaining credit later merely because root polling time passed. A late report from a concurrent child cannot recredit work already covered by the maximum. Each child applies the same composition rule to descendants.
4. Before any authorized optional phase can start, including later cleanup under a held grant, the root records a bounded live accounting-phase gate and its root-clock start time, then freezes new prefix credit. This is part of the existing grant/phase execution handshake, not a per-semantic-step durable ledger. A lost acknowledgement leaves the phase pending. Fold each child's cumulative whole-subtree optional elapsed delta once and root-measured local optional elapsed into the overlap debit. At phase end, also debit the root-clock intersection of the gate interval with the current cohort. This covers cleanup from an already received invocation whose meter token has retired while another original now runs. It may conservatively subtract reported optional elapsed again from useful credit; it never charges actual optional cost twice. Close the gate only after the exact original cost prefix for that phase is positively received; unexplained optional work, unknown accounting or an overrun follows #995's conservative liability/backoff rules. A child cannot execute optional work invisibly after the root unfreezes credit.
5. At each verified prefix or positively received accounting-phase end, compute `L = max(0, min(max_child_conservative_fresh_ns, root_cohort_elapsed_ns) - optional_overlap_debit_ns)`. Credit only `max(0, L - already_credited_cohort_ns)`, and advance the credited lower bound by that increase. Existing valid prefix credit is never counted again or retroactively rewritten. The optional debit deliberately overestimates possible overlap. Any unknown/missing accounting suppresses further credit for that cohort and seals optional admission when its cost is unknown. Prefix receiving does NOT end an invocation, release resources, certify a tool stopped or select a generation.
6. Close the cohort only after its original invocations and accounting phases are actually received. Do not delay mandatory work or a ready receiver to improve credit. On restart, discard unanchored prefix/cohort credit. Restore only the latest durable root summary and outstanding grants. An old epoch's prefix/result still receives original outcome/cost/resources through its actual owner but earns no new useful credit. Selected optional generations never restore an older, larger allowance.

The max rule can undercount serial children that overlap one long-lived child; that is intentional. It is not a new scheduling obligation or a promise to reach 120s of eligibility as soon as possible. Prefixes are coalesced at existing bounded execution boundaries and become durable only with an actual grant/selection or mandatory anchor. Root grant admission captures the credit summary and necessary exact prefix bindings atomically, so an admitted grant cannot rely on subsequently forgotten credit. Active metadata is bounded by existing execution admission; scalar lifetime counters do not impose a total workflow limit. An unresolved optional phase can prevent new credit without preventing unrelated mandatory execution.

[application_credit.py](implementation/application_credit.py) is a reference-only implementation of this arithmetic. Its tests cover in-flight 120s eligibility, repeated promotion, cumulative-prefix duplicate/conflict/regression, overlap, receive order, continuous cohorts, optional-start freezing, unknown accounting, duplicate/old receipts, clock clipping that cannot grow by polling, capacity refusal and unbounded total work with bounded active state. It does not authenticate a receipt, settle cost, persist a grant, join a worker, or implement the product policy. The application owner must perform those operations before invoking it. No product integration or distributed-clock qualification is claimed by these deterministic tests.

## 5. What can actually be saved

Cheap planning/validation uses bounded volatile state and private admitted spill. Only supported complete snapshots can consume grants. The common Native executor/generation owner comes from [#996](https://github.com/nashspence/riverhog/blob/e4a607081d17ae1a067bb766241bd5febd9ddeb9/.reference/IMPLEMENTATION.md). Controller-owned planning state may use an equivalent bounded complete generation over its private derived store; it must bind the exact accepted work, recipe/compiler/provider configuration, retained observation envelopes, source set, dependency closure and original effect receipts. Persist dependencies before atomic root selection. Do not serialize a partial Python stack or claim that a tool's percent-complete value can resume that tool.

Every candidate still supplies its own bounded evidence of net replay work saved (`W`) under #995. Accumulated root useful time (`U`) only limits available spending; it does not make an otherwise cheap child candidate eligible. Deduct restore, validation and selection cost when assessing that candidate's replay saving, and account separately for already retained natural anchors. Do not checkpoint each short child merely because its long parent has earned credit.

External ffmpeg/ffprobe/exiftool/minisign/rclone/native commands and the current synchronous sampler have no qualified mid-operation save contract. Preserve their exact inputs/intent, declare tool-level restart/refusal behavior, and record zero optional midpoint checkpoints. Their waits earn no invented useful credit. An immutable successfully retained output or exact observation is a mandatory natural anchor; replay starts after that anchor without rerunning the original nondeterministic work. Once an observer response has been accepted, replacing it with a newly sampled response is a new semantic act, not recovery.

At a safe boundary, if required final acceptance can complete, complete it rather than creating a last optional checkpoint. Missing optional state causes exact-source recomputation; missing original evidence/accepted output/intent remains a custody failure or unresolved obligation, never a cache miss.

## 6. Public progress and hard cut

Expose bounded `processed`, optional `resumable`, `replay_guarantee`, and uncertainty/receiving diagnostics through existing progress/status models. Processed/advisory values may disappear or move backward after restart; only a selected complete generation or required original outcome can support resumable claims. A tool-level restart limitation must be visible when relevant. Status reads do no payload IO, semantic replay, synchronization, checkpoint creation or worker receiving. Heartbeats, current authorization and stale-worker checks retain their actual safety cadence independent of this policy.

Update shared policy definitions, application configuration schemas/readers, protocol/client/OpenAPI, CLI presentation, installed examples, current application state baselines and owned growth/resource declarations together. Preserve the existing state-schema upgrade machinery, but explicitly refuse populated incompatible pre-v1 state. No startup reset, silent initialization, fake migration, or deletion of irreplaceable application records is part of the cut. Existing original work remains with its old compatible owner until safely received and explicitly disposed. Integration requirements are in [QUALIFICATION.md](QUALIFICATION.md).
