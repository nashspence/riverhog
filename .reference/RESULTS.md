# Native phase cost and available parallelism

## Finding and scope

The remaining invocation count has several causes with different owners. Native deliberately exposes small durable phases, including empty completion/reclamation phases, and repeats fixed control around them. Corrections additionally rebuild and revalidate the effective projection. The exhaustive publication observer performs fresh semantic verification through several independent readers. Core adds source, worker, certificate and catalog publication fences around a retained Native turn. These costs cannot be inferred from payload bytes alone or added as overlapping inclusive timings.

The new observation reconciles **every one of 479 retained Native advances** on three tiny histories at ordinary budgets. It establishes repeated `_start` invocation and parent loads, but does not justify removing a fence, changing phase order or raising concurrency. No runtime patch is proposed by this packet.

The [request](evidence/context/request.md) pins **3b47cbba770c31eb1487b50f7e3b16533c10e827**. All product/test/helper paths in this reference equal that source. The relevant Native, Core, API, client, state-schema and qualification-helper trees also equal the historical **931f01e65d8849835774a97ffbd2954ae6802ce5** publication source; this is a checked subtree relationship, not a claim that the entire repository is unchanged. [Source audit](evidence/source-audit.json).

Each used a fresh retained Session and the normal validator/materialization as its oracle. Six active assertions cover activities, agents, artifacts, descriptions, occurrences and states. The correction replaces one agent assertion and leaves six active assertions. These cases contain no graph certificates and no inserted derivation/specialization edge.

### Why 64 rows still produce many turns

[Session.advance](https://github.com/nashspence/riverhog/blob/3b47cbba770c31eb1487b50f7e3b16533c10e827/packages/riverhog-provenance/src/riverhog_provenance/journal_session.py#L1513-L1562) dispatches one source/entry action. [EntryReplay.advance](https://github.com/nashspence/riverhog/blob/3b47cbba770c31eb1487b50f7e3b16533c10e827/packages/riverhog-provenance/src/riverhog_provenance/_entry_replay.py#L2441-L2673) dispatches one child, row, lifecycle, graph, recorder or publication action. A child needs admission, one or more prepare/apply batches, then a later completion-recognition turn. The row budget limits work within that selected action; it does not make one Session call finish 64 assertions.

For an uninterrupted retained success, with no retries, reopen or extra post-completion polling:

`Session calls = source scan calls + frame synchronization calls + replay calls + 2 terminal calls`.

The three cases reconcile exactly as **1+1+103+2=107**, **2+2+(103+16)+2=125**, and **2+2+(103+138)+2=247**. The checkpoint adds **18** total calls: one scan, one synchronization and 16 replay calls, even though it adds no assertions. The correction adds **140** total calls: one scan, one synchronization and 138 replay calls. This is a causal decomposition of the observed cases, not a growth fit.

Generic semantics includes separate walk, key-reclamation and output-reclamation phases. Semantic finish revisits an active changed row through selection, lifecycle, content and externals; empty lookups still need a bounded completion transition. Row-specific child work, indexed diagnostic scans, graph requests, byte capacity and cleanup can add further batches. The full source-derived algebra and measured child counts are in [NATIVE.md](NATIVE.md) and [RECONCILIATION.md](RECONCILIATION.md).

### Repeated fixed control is real; its meaning matters

Every observed Session call performed an outer `_start`. Each of the 463 replay admit/advance calls performed an inner `_start`: **479+463=942**. Both admission and the active non-frame route exhibit this pattern. `_start` checks certificate-binding equality, encodes metadata to reserve its actual width, sets the budget and resets spent work. The second reservation replaces the first; it does not double-charge the effective allowance. It issues no SQL itself. The separately repeated parent loads are real current worker/checkpoint observations.

All `_start` calls together recorded about **0.029826 s instrumented thread CPU** in this observation. That is a small part of the approximately **3.091 s** process CPU in the three retained-advance stages. This does not support treating duplicated budget serialization as the primary explanation of historical publication time. It does justify a narrowly scoped source-owner review of accounting reuse, provided standalone EntryReplay checks, currentness, admission and failure ordering are preserved. Removing the second ledger load is a separate and materially stronger change.

Let h=1 after a nonempty accepted prefix, otherwise 0. The successful parent-control path has **2+h** explicit SELECTs per `load`/transactional fence and **2+h** statements per publication. A warm active ordinary commit/move path therefore has **9+4h explicit parent-control execute calls**: two detached loads, BEGIN IMMEDIATE, transactional fence and publication. Child SQL, provider work and the DB commit method are additional. Fixed statement count does not imply fixed physical latency or constant-width metadata. Exact source and coverage limits are in [the control-query analysis](NATIVE.md#control-query-algebra-and-physical-costs).

The measured retained-advance selection confirms that repeated control is substantial in call count. These are admitted Native `execute` attempts, with setup/materialization excluded:

| History | Ledger-owned attempts plus BEGIN | All execute attempts during advances |
| --- | ---: | ---: |
| Initial | 965 | 1,955 |
| Checkpoint | 1,193 | 2,288 |
| Correction | 2,779 | 5,011 |
| **Total** | **4,937** | **9,254** |

The first column is a disjoint owner-based selection and agrees with the parent-control model. It does not count physical pages, fsyncs or Core catalog queries. Every observed advance publishes one parent version. Equal captured fields across the two loads describe this successful trace; they do not prove that the second observation is dispensable under interference.

## Repeated input work and growth

Warm ordinary continuation retains the current frame; cold continuation restores the quarantined current frame. Prefix hashing resumes its continuation state and adds the current encoded frame. This is different from re-reading or re-hashing every accepted frame on every turn. Existing cold-resume/history-hash tests were inspected, not rerun.

Retained scanning does have bounded lookahead: the source returns a window, while framing stops after one frame. The unused suffix can be fetched again on the next scan. The maintained test source implements `read_window` by calling `read_exact`; that nested delivery is not a second independent byte read to add again.

| History | Unique source / consumed bytes | Returned scan-window bytes | Direct admission atom bytes |
| --- | ---: | ---: | ---: |
| Initial | 4,913 | 4,913 | 4,911 |
| Checkpoint | 5,903 | 6,893 | 5,899 |
| Correction | 6,193 | 7,473 | 6,189 |

Direct admission reads each JSON atom without its two framing bytes. The extra window bytes in the two-frame cases are the returned later-frame suffix, not an accepted-prefix hash scan. With full windows W and sufficient admission, returned bytes are bounded by source bytes plus at most F(W−1) suffix bytes; valid short provider windows can increase call counts. A future buffer-reuse proposal must preserve the one-frame frontier and first-error order, including an earlier semantic failure before later framing failure.

Corrections are the substantive repeated projection work. They retire four aggregate relations, replace/retire the derivation and specialization graph runs, enumerate all active assertions, then validate the reseeded effective projection. The correction-specific contribution here is **36 replay calls**: 10 fixed transitions + 6 target prepares + 6 aggregate-retirement prepares + 2 seed prepares + 6+6 returned graph-retirement plans. A returned plan may advance an empty relation; it does not prove that rows or adjacency were visited. The diagnostic records zero adjacency visits and no edge-start/repair work, so graph traversal cost remains a static question.

Across corrections, total work includes the sum of the effective projection sizes and the graph/semantic work re-established at each correction. A page budget does not establish linearity in newly appended bytes. The OnlineDag owner also explicitly excludes a whole-stream amortized claim from its unit contract. Reducing invalidation needs an owner-level dependency proof with correction/restart/error-order and growth evidence; increasing concurrency or caching old acceptance does not supply that proof.

## Cost attribution and catalog raises

[COSTS.md](COSTS.md) and its [derived tables](evidence/cost-summary.json) partition observed scopes without adding their inclusive parents. The raw observation is preserved byte-for-byte in compressed form; [EVIDENCE.md](EVIDENCE.md) explains how to inspect it and its limits.

Across retained setup, advance, materialization and receiving, the complete stage clocks sum to **5.529906 s wall / 3.228685 s process CPU**. The corresponding selected exclusive scopes sum to **5.529375 s wall / 3.228154 s thread CPU**; these use different outer clocks and scope boundaries. Within that disjoint partition, ledger controls excluding separately scoped children account for **0.944522 s CPU**, DBAPI execution for **0.815808 s**, and explicit commits for **0.198315 s CPU / 2.026572 s wall**. These are materially larger captured categories than `_start`, but remain instrumented costs on these inputs. The commit wall/CPU difference does not identify a particular wait. Session and semantic residual categories include unwrapped work and observer effects, not a measured pool of removable overhead.

| --- | --- | --- |
| Source/worker/certificate fences | Exact source sites; Native fixture source-call counts; historical aggregate callback counts | Tiny OwnedSource checks a boolean and has no Core catalog/certificate cost |

The new retained observation recorded **9,524 execute calls and 12 executescript calls** across retained setup/advance/materialization/receiving, plus **7,789 fetch/iterator attempts**, **497 explicit commit API calls**, no explicit rollback and no observed DBAPI exception family. The explicit commit API calls split into 15 during setup and 482 during advances: 479 parent checkpoint publications plus three terminal store-freeze commit calls. A freeze call may be a no-op outside an active transaction; these counts do not establish three additional durable transactions or fsyncs. Twenty-two `StopIteration` outcomes are normal iterator exhaustion. An `executescript` call counts one DBAPI attempt, not each SQL statement in the script; fetched rows are not SQLite engine row visits. These counts are a different domain from Core's historical **51,377 catalog execution attempts**.

The historical **418 raised catalog attempts remain unclassified**. The publication comment explicitly says error families were not captured. The retained material provides no driver-code, query-site or handled-versus-propagated attribution, and the exact extended recorder/raw output was unavailable. The catalog does have [explicit contention classification](https://github.com/nashspence/riverhog/blob/3b47cbba770c31eb1487b50f7e3b16533c10e827/riverhog/src/riverhog_core/catalog_db.py#L75-L131): SQLite BUSY/LOCKED and PostgreSQL 40001/40P01/55P03. Some scheduler paths intentionally defer on such contention. That establishes a possible control path, not the cause of any historical raise. They must not be called product errors, retries, wasted work or contention from the aggregate alone.

The old observer window's **40.116 s wall / 32.866 s process CPU**, **26.186 s selected disjoint exclusive thread CPU**, and **6.680 s unassigned CPU** are different inventories. Native inclusive **15.166 s** and Core inclusive **8.136 s** overlap. Neither adding them nor subtracting process CPU from wall time isolates database wait or unused execution capacity.

## Core dependencies, API cadence and parallelism

The [Core turn](COORDINATION.md#the-core-turn-surrounds-native-work) brackets its unit with catalog metadata stamps. The unit advances or checks capture, epoch scan, topology, union, rank and replay binding before the Native owner; after Native commits, Core conditionally adopts progress and separately publishes the terminal journal outcome. Completed preparations still check fresh metadata; they do not automatically rerun whole preparation, and an earlier ready result is not current authority.

Worker currentness and progress publication are distinct. The original source/job/epoch identity fences a worker without comparing stale saved progress. Publication separately uses the latest slot version/progress compare-and-set. An exact source/certificate check remains fresh even when its SQL statement structure is reused. The workspace lease, retained slot and dependent readers stay charged until original receiving completes. [Fence and custody detail](COORDINATION.md#fresh-fences-and-commit-order).

| Boundary | Available independent work | What the observation does not prove |
| --- | --- | --- |
| One journal | Successive phases depend on the same checkpoint, current frame and effective projection | A second worker cannot make dependent phases independently runnable |
| Journal concurrency 2 | Two independent exact source keys may retain distinct slots; the pool mutex covers reservation | This limit is not a two-thread executor or evidence that both slots were ready/occupied |
| Scheduler `limit=1` | Tries eligible candidates sequentially until one progresses; another caller can advance another source | No fan-out is created by setting capacity above one |
| Physical archive execution | Independent original execution keys may use separate global/per-target grants | Four forward/two terminal defaults, or worker lifetime counts, do not establish occupancy |
| Published helper | Workers can execute between finalization polls | Sequential append, upload, assembly and reader passes are not a concurrency saturation test |

The supplied **428 AnyIO hook-observed lifetimes** are neither 428 concurrent workers nor an independently measured OS thread-creation count. The helper creates unentered TestClient instances. In pinned Starlette 1.3.1, an absent persistent portal creates a blocking portal per request; synchronous FastAPI endpoints use AnyIO's per-event-loop worker pool. This is a source-supported turnover mechanism, not measured startup CPU or an exact mapping to all 427 requests. [Pinned transport sources and lifecycle caveat](COORDINATION.md#pinned-transport-mechanism-and-lifecycle-caveat).

One local seal call gives the direct scheduler an opportunity and then issues an HTTP seal whose service gives the selected journal another opportunity. These opportunities are sequential. Either may make no progress; the direct scheduler may select another eligible journal, while the HTTP seal remains bound to the requested journal. The SDK immediately repeats journal-seal requests while validating. **The 50 ms sleep belongs to finalization/custody polling, not that journal-seal loop.** Historical totals alone cannot assign all 399 owner advances to these call sites.

Using TestClient as a context manager would reuse a portal **and start ASGI lifespan**. Riverhog lifespan starts archive, restore and cache maintenance, including immediate archive work through `asyncio.to_thread`. That changes scheduler conditions. A valid transport comparison needs explicitly equivalent startup, background scheduling, cancellation and receiving; setting a private portal or mechanically adding `with TestClient(...)` is not a justified optimization.

There is no retained ready-queue/admission/start/end/receive timeline for the historical run. To establish missed parallelism, show at least two independent ready keys during the same interval, sufficient grants, and why each remained unstarted: dependency, same-key lock, capacity/per-target limit, retained reader/cleanup, delayed poll or scheduling. CPU/wall ratios and thread-lifetime totals cannot supply that evidence. No concurrency-policy change is recommended.

## Narrow recommendations and open obligations

1. **Use the exact Native reconciliation as the first review input.** It identifies scheduling granularity and repeated control without replacing contracts. If coalescing transitions is investigated, retain each original commit/fence, byte/row accounting, cancellation boundary, custody and first-error order. A loop with a step limit alone is not a total-growth proof.
2. **Prioritize an attributable warm Core control question over removing `_start` blindly.** Distinguish completed-prerequisite metadata checks, predicate construction, source/worker/certificate callbacks and conditional progress/outcome publication. Any reuse should first concern immutable statement construction or proven within-call accounting; successful acceptance/currentness cannot be cached from an earlier snapshot. This packet does not measure savings or authorize a fence removal.
3. **Classify catalog raises before optimization claims.** A later already-authorized bounded Core observation should retain exception class, driver code/SQLSTATE, query/owner site and handled-versus-propagated disposition. Preserve original exceptions; do not label all raises as waste.
4. **Treat transport lifetime and ready-work occupancy as separate questions.** Define equivalent lifespan/background policy before a portal experiment. Require an actual ready-key/grant timeline before changing concurrency. Preserve original worker, lease, independent-reader and result-receiving obligations.

These are focused investigation choices, not new approval gates or mandatory campaigns. No new publication or broad suite was needed for this handoff. Large campaigns remain held under the request; no timing gate or CI qualification is claimed.
