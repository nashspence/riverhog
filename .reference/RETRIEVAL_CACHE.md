# Retrieval, paid read preparation and cache ownership

This is a proposed implementation for [#999](https://github.com/nashspence/riverhog/issues/999), based on `c28eceaa2dfec1b3712135469ba12230e74f5ffa`. Names introduced below are proposed contracts, not claims that current product code implements them. [IMPLEMENTATION.md](IMPLEMENTATION.md) owns the common policy and integration order.

## Shared read-preparation invocation

**One storage-protocol implementation serves copy and retrieval.** Extend the existing exact invocation/result pattern in [`riverhog-storage-adapter-protocol`](../packages/riverhog-storage-adapter-protocol/src/riverhog_storage_adapter_protocol/protocol.py); do not introduce a second retry engine or a provider-neutral billing policy. Add `ReadPreparationCallIdentity` with the same four-field canonical correlation validation as `WriteCallIdentity`: call ID, exact request hash, target incarnation and dispatch owner. Keep existing write/cleanup names and consumers unchanged; share the focused validation mechanics rather than commissioning an unrelated rename.

Add `ReadPreparationInvocation` and `ReadPreparationExecutionResult`, plus `execute_read_preparation` on the port, supplied adapters, HTTP contract/server/client and installed consumer parity tests. Its request selects **one exact object** per potentially paid invocation; bounded callers decompose multi-object work before entry. This prevents partial multi-object failure from obscuring which objects may already have incurred effects. Readiness inspection can continue to use bounded canonical object selections.

The durable original contains:

| Binding | Required content |
|---|---|
| Owning work | Original copy generation or retrieval plan/job, workflow recovery attachment, object ordinal, current execution owner and dispatch identity. |
| Exact source | Store registration/incarnation, exact object path and revision, expected stored bytes/hash and source manifest identity. Potentially paid AWS preparation requires a concrete immutable `VersionId`; missing revision and the mutable `"null"` token are refused. A path or preflight HEAD cannot fence this mutation. Other adapters must supply their actual qualified exact-object primitive; no generic fence is presumed. |
| Preparation policy | Adapter-issued opaque digest of its effective preparation policy and semantic version. AWS owns `Days`/`Tier` and serializes/validates that policy; Core does not learn AWS configuration fields. A changed adapter policy refuses an old invocation. |
| Consent | Original selected plan ETag or copy request identity, restore-allowed decision, current principal/key scope binding, and exact predecessor attempt when renewed consent is required. Stored consent is not current authorization. |
| Resource/correlation | Call ID, canonical exact-request hash, dispatch owner, target incarnation, bounded request/result/receiving capacity and entered/no-effect/unknown outcome. Reserve before possible entry. |

Add `read_preparation_policy_sha256` to `AdapterDescriptor` and bind it in the invocation. All supplied adapters expose one, including a stable immediate-read policy identity. The adapter owns the digest's canonical policy representation. A policy change blocks new entry under an old request but cannot prevent receiving the exact old original result or its required cleanup under original-receipt authority.

The adapter result has exact call correlation; `execution` is `closed` or `unknown`, and `outcome` is `no_effect`, `readiness` or `unknown`. `readiness` carries the existing typed requested/ready/expired observation and an opaque provider receipt if the provider supplies one. `no_effect` requires positive closed non-entry evidence. A positive readiness observation with unknown execution remains useful evidence, but it does not release original execution resources. Use the same validation rule as write/cleanup: missing reply is unknown, a refreshed descriptor or HTTP status is not closure, and a result for another request/incarnation is rejected. Later original closure is accepted only from that original trusted execution/receiving owner; readiness observations cannot synthesize it.

Before dispatch, durably select the invocation and capacity, then exclusively admit that original executor under the current fence. Provider I/O occurs outside the catalog writer. `execute_read_preparation` is one physical entry, not a retry/readback operation: resending the same ID is prohibited after possible entry, because a correlation ID alone supplies no provider deduplication. Reconciliation reads retained original results and exact-object readiness without invoking preparation again. If arming commits but its reply is lost, reload the exact original; do not send a replacement merely because the caller did not see the commit. If the process dies after arming but before a provable non-entry result, conservative reconciliation can lose an opportunity to run; it must not create another paid attempt. After a positively received immutable `closed/no_effect` receipt, the same logical preparation intent may admit a **new dispatch ticket/call ID** bound to that predecessor and unchanged consent/source/policy. Its reservation and fresh current checks precede entry; the old no-effect receipt is never overwritten. This is not a paid renewal because non-entry was proved. A false-positive arm without that proof has a concrete, safe refusal outcome rather than an invented successful retry.

### Paid attempt and consent decisions

1. **An ordinary retry always names the original invocation.** After possible entry, neither a timeout, a discarded cursor, an `expired` readiness result, nor a new worker authorizes another prepare call. Reconcile exact-object readiness and retain the original unknown outcome. The AWS policy's initial HEAD check is useful but is not an application idempotency key.
2. **Expiry is a semantic outcome, not an automatic renewal.** After a previously known requested/ready restore expires before successful hydration, record `restore_window_expired`. If entry/outcome is still uncertain, record `restore_outcome_unknown`. Both stop automatic prepare/reprepare and expose a typed attention reason. These are additive closed values in the retrieval/copy reason contract; do not overload arbitrary exception text as retry policy.
3. **A new paid attempt requires closed original execution and new explicit consent.** All delegated executing children of the previous conflicting invocation must be positively received by the exact original owner. A local Future or HTTP body close is insufficient. While execution is unknown, even a new ETag/consent refuses fresh conflicting preparation. Once execution is closed, fresh consent may explicitly accept an unknown prior charge or a later expired window without declaring that charge absent. A fresh plan/copy offer identifies the previous attempt and uncertainty; its ETag commits that information and the new source/policy. Acceptance requires `restore_policy=allow` and, for renewed attempts, `renewal_consent_sha256` equal to the complete offered decision-manifest digest. This grants at most one new attempt per selected object. Automatic SDK/CLI retries retain the prior planning key/ETag and never add renewal consent. `restore_policy=never` never enters preparation. The predecessor remains retained according to its original result/accounting obligations; source- or policy-changed work is independently revalidated. If the provider/transport cannot prove original execution closed, the selected behavior is visible retention/refusal, not a new negative-proof API or an operator bypass.
4. **Requested versus uncertain controls polling, not authority.** Read-only readiness inspection may continue under current access. Known readiness can permit a separate authorized cache hydration once exact bytes and live dependencies are pinned, without claiming the old call closed. No new paid mutation is inferred from that observation.
5. **Preparation cleanup is provider-specific.** AWS's current cleanup is a no-op; closing a local HTTP body does not cancel an S3 restore or remove its temporary restored copy. Record that disposition. A provider with a real cleanup effect uses its exact retained cleanup invocation and receipt, under fresh authority.

AWS documents temporary restored copies, expiry changes and charges for repeated restore requests, and exact `VersionId` selection in [RestoreObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_RestoreObject.html). Its [HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) contract describes restore observations and generic error responses. The documented RestoreObject request has no application invocation token equivalent to this proposed retained original; the selected no-repeat rule is Riverhog's conservative policy, not a claim that a HEAD result proves provider non-entry. The experiment substitutes only the provider client, exercises the actual `AwsDeepArchiveReadPreparation`, and deterministically advances the fixture to a later expired window. It does not assert a live AWS consistency anomaly.

The AWS owner currently sends no restore `If-Match`/expected-content mutation fence. [Versioning-suspended bucket semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/AddingObjectstoVersionSuspendedBuckets.html) allow the same key and null version to be overwritten. Therefore refuse paid preparation for an absent or null version rather than racing a preflight hash against replacement. This operational refusal does not invalidate existing archive bytes or disable independently authorized offline recovery; it prevents a new chargeable effect whose exact target is unproved.

### Exact public attention and renewal cut

Extend the closed retrieval job state with `reconciling` (unknown original execution), `needs_consent` (execution closed, no usable preparation window) and `canceling` (new work sealed, original receiving incomplete). Keep existing ready/requested and terminal values; a terminal public result never deletes separately retained original resources. Add nullable closed `attention_reason` with only `restore_outcome_unknown` and `restore_window_expired`; ordinary pending work has null. The same reason type is consumed by the copy owner. A ready result can coexist with separately retained accounting/receiving liabilities only when exact bytes, current authority and required pins are established; readiness does not implicitly retire those originals.

Plans/offers expose `preparation_decision_count` and `preparation_decision_sha256`. Add `GET /retrieval-plans/{plan_id}/preparation-decisions` and SDK `list_plan_preparations(plan_id, start_ordinal, page_size)`, using required `If-Match`, an exact nonnegative object ordinal and page_size1..100. Seek by indexed ordinal; do not introduce a total object-count limit. It returns bounded ordered selected-object/predecessor/closure/uncertainty/policy decisions under current plan authority. Public predecessor references are opaque commitments within this authorized selection; do not expose another principal's job/request IDs, receiver credentials or unrelated source members. The Core owner retains the full internal original binding. The complete count/digest is sealed before acceptance and included in the ETag; a page callback or partial list is not complete consent. Every repeated acceptance compares `renewal_consent_sha256` as part of its original request identity. The CLI adds explicit `--renew-restore` for a new user-requested attempt, displays the count and uncertainty and binds that returned digest; normal resume never supplies the flag. SDK automated callers must deliberately pass the typed digest. Existing `/retrieval-jobs/{job_id}/renew` remains lease renewal and never grants another paid preparation. No unbounded object array is added to a status or plan response. Copy's current same-tuple resume API has no such intent; its concrete request/offer cut is specified in [STORAGE_ADAPTERS.md](STORAGE_ADAPTERS.md).

When renewed consent continues an existing materialization/retrieval workflow, the new plan/request/ticket inherits that workflow's already retained recovery attachment and spent/reserved accounting. It cannot mint fresh replay credit by changing IDs. An independently requested user workflow may have its own root under #995 admission, but it still cannot bypass a conflicting unreceived provider original or discard its retained liability.

## Execution, waits and current authorization

Make the existing retrieval service own a bounded registry of original object executions, using the repository's existing retained Native execution pattern. Copy also needs a new owner-local retained registry: its current synchronous per-volume pool is not such a registry. `process_due` claims a bounded page of due original jobs and starts/polls already-admitted workers; it never waits for provider restoration, streams ciphertext or waits for worker teardown on the coordinator thread. One unreceived invocation occupies its actual slot. Separate bounded capacity for status/receipt collection and mandatory receiving prevents a full payload pool from deadlocking cancellation. An unreceived worker is not evicted to make room for a successor.

Schedule requested readiness checks in a volatile per-original due heap and round-robin keyset cursor. On restart, recover mandatory originals from the start of the ordered owner index in bounded pages and spread their first inspection no earlier than the configured restore poll interval. During that process lifetime wrap fairly over all selected originals; repeated process failures may replay the scan and provide no cross-restart fairness guarantee. Neither the cursor nor a round-robin position is persisted or smuggled into a mandatory transaction. Keep the heap bounded by admitted worker/control slots. Queued originals remain in the mandatory owner index, so a huge pending set does not become an unbounded Python queue. A wait produces no new useful-work credit and no identical progress commit. An actual externally required retry-after/lease renewal or authoritative outcome transition is recorded by its owner, separately from advisory progress.

Use fresh key/grant status, collection/artifact scope, source-copy retirement/deletion fence, selected source incarnation and cache incarnation before effects and before adopting/disclosing results. Capture versioned catalog decisions in a bounded transaction; probe provider readiness outside it; recheck the version/fences in the short adoption transaction. In particular, `_cache_record_is_usable` must not perform readiness/descriptor network calls from `_advance_plan_record` or `_claim_restore_step` while a catalog writer is held. Current permission revocation stops new disclosure/effects; original resource receiving remains possible through the established narrow original-receipt authority without granting new content access.

Ready jobs, plans, source selections, live hydration writers and live plaintext response iterators hold distinct dependencies. Lease expiry or requested cancellation seals new admission and marks public work unavailable; it does not delete the original execution or release source/cache pins. Track and receive the actual response/transport iterator, including a never-started iterator. Preserve the stream object and its explicit close callback rather than extracting `.content` and dropping the owner. Release quota/pins only after the original workers and streams settle and their final observed byte accounting is installed.

## Retrieval plans and download accounting

Retain the original request before work: canonical artifact selection, explicit effective lease, restore policy, selected source option and request idempotency identity. This consumes the same CLI intent seam specified by the pinned [#998 application handoff](https://github.com/nashspence/riverhog/blob/e2083a7a17f33820bca4ed696a97fa50f317cbcf/.reference/INGRESS_LIFETIME.md) and its [composed budget](https://github.com/nashspence/riverhog/blob/e2083a7a17f33820bca4ed696a97fa50f317cbcf/.reference/BUDGET.md); do not invent a second planner key or root allowance.

Plan construction uses a private bounded workspace. Required source-copy pins are installed before releasing the source-selection transaction, and survive the original execution independently of public plan expiry. Per-page hashes, ordinal cursors and partial projections are replayable; they are not accepted public plans. Use #995/#996 only when a complete, useful saved frontier qualifies. Persist selected artifact/object/placement rows as immutable bounded batches, with staged-versus-accepted visibility, and select the complete plan/ETag through the same fixed-revision prepared-completion pattern as #997. Final selection checks current source revisions, exact complete counts/digests and current permission without rescanning the corpus under a writer. Missing placements, holes or corrupt authority fail; no cache fallback may manufacture completeness.

Keep `create` consumed-plan retry returning its original job. Refactor [`download_allowances.py`](../riverhog/src/riverhog_core/services/download_allowances.py) into a Core-owned SQL reservation helper that accepts the **existing catalog session**; the facade uses that helper for its own calls. Retrieval creation calls that helper in the same transaction as plan consumption/job creation/lifecycle insertion. This is internal Core composition, not a database session exported to a storage adapter or reusable package. Remove the separately committed reservation and compensating release from `create`'s generic exception path. After an uncertain commit, read the original plan/job/reservation as a unit; do not release before proving no job was accepted. Update injected test doubles at the helper seam. Keep stream/provider download usage in its existing owner; actual observed stream bytes, monthly quota resets and required reservation heartbeats remain mandatory.

The current-owner experiment commits the real job and then injects a lost commit reply. It observes the surviving job, the current unconditional allowance release and consumed-plan reuse without a second reservation. This confirms the transaction boundary defect through the real service while the allowance itself is a recording fixture. It is not a PostgreSQL or deployed quota-race qualification.

### Stream quota survives expiry and month rollover

The current allowance `_reap_expired` / `_reap_expired_key_reservations` conservatively charge expired streams and delete their reservation rows. `_finish` / `_finish_key_stream` then return if the row is absent. A stalled original can therefore outlive expiry and the monthly counter reset, then transfer late bytes with no surviving charge identity. Required heartbeats alone do not solve that window.

For each existing store/key allowance owner, retain the original stream row until positive original transport/iterator receiving. Store immutable `reserved_ceiling_bytes R`, `accepted_month`, monotone `observed_bytes H`, `liability_bytes L=max(R,H)`, `expiry_charged` and an exact final settlement receipt. `accepted_month` is the original reservation's accounting month: key streams funded by a job inherit that job's month; independent provider streams use their own acceptance month. The accounting row holds current-month `finalized_accounted_bytes S` plus month-independent aggregates `active_stream_liability A` and `expired_stream_liability E`. Effective charge is `S+A+E` plus unspent job reservations, with no additional double-counted carry total.

New streams add L to A. The first lease expiry atomically marks `expiry_charged` and moves L from A to E while retaining the original and execution pins. This is a provisional worst-case charge, not observed usage or receiving; repeat expiry is a no-op. Month rollover resets only S; A and E survive as unresolved carry. The same-session job-to-stream transfer moves credit atomically and selects the original stream before body entry. No historical scan or per-byte progress journal is introduced.

At positive final receiving with exact cumulative bytes `T >= H`, choose `F=T` only if the accepted month is current and expiry was never charged; otherwise choose `F=max(T,R)`, preserving the current conservative expiry/cross-month floor. Atomically remove L from its single A/E bucket, add F to S and retain `(original_id, settlement_month, T, F)` as the exact final receipt. A duplicate or lost-reply settlement first compares its exact original result/T and returns that receipt without charging again; a conflicting late report refuses and retains the conflict rather than overwriting it or debiting another month. A non-null final receipt excludes the original from A/E, expiry and heartbeat liability mutation. H increases at already-required heartbeat/outcome boundaries. Compute each increase as `delta_L=max(R,H_new)-L_old` and add only delta_L to its one bucket; repeated cumulative overrun reports cannot charge the excess again. Record capacity debt and stop new admission on overrun without rejecting or discarding the original outcome. Known byte bounds/transport stop are still required; unknown receiving retains L. A missing original is an error, not successful finish. Compact only after original receiving and receipt acknowledgement.

Existing public `accounted_bytes` can expose `S+E` and `reserved_bytes` can expose `A+unspent_job_reservations`; document that these are conservative accounting, not measured actual usage. Observed T remains separately identifiable. Test never-started iterators, stalled streams past expiry, expiry then month rollover then late bytes, repeated expiry, lost final commit reply and concurrent quota admission with both actual backends. This accounting correction is source-audited proposal, not covered by the recording-allowance witness above.

## Cache population and accounting

Implement a discriminated original population parent: `archive_upload` or `retrieval_job`. Each arm binds its own immutable original, current authority, source selection, owner generation and terminal receiving. Do not widen `CachePopulationDispositionRecord`'s upload-terminal foreign key to a nullable untyped ID. Keep separate concrete parent foreign keys/records or a rigorously discriminated Core-owned common original table; select **separate parent records feeding one shared mechanics layer** for this cut. Existing upload behavior remains #997-owned; #999 adds retrieval records and routes. The mechanics layer owns invocation validation, exact write session/parts/completion receipts, capacity and original receiving, not either parent's authorization.

Replace the legacy unmanaged retrieval `admit`/`put`/abort path completely. Reserve destination quota and exact population identity before begin; persist bounded begin/part/complete invocation batches before entry; receive original results; hash/length verify ciphertext; then adopt the exact final cache receipt and quota change in a short transaction after fresh parent/incarnation checks. A completed object whose adoption reply is lost is found by that exact original receipt. Do not start another random cache object. Cache data stays encrypted, and no plaintext payload spool is introduced.

Claims allow multiple current jobs to depend on a shared verified population without taking over its execution identity. Losing the last public claimant requests retirement, but a writer, reader or uncertain original still pins the population. Replace startup `deleting -> delete_pending` inference and abandoned-age guesses with original receiving/reconciliation. Eviction, cancellation and sweep use exact current-revision cleanup effects outside the writer, then atomically adopt their original receipts and adjust committed bytes. Source retirement sees these live pins. Missing cache bytes can cause an explicitly safe refetch only when no sole custody, unknown original or quota liability is being discarded.

Keep `observe_completed_population` read-only and bounded; its existing focused tests are a no-change witness. Keep bounded item paging and exact cache range identity. Do not call recovery helpers or create a cache execution during a GET/observation.

### Accounting rebuild without per-page persistence

Transactional committed/reserved counters and active claims are required capacity authority. Initialization and each insert/delete/resize continue to update them with the owning mandatory transaction. Replace the startup reconciliation's repeatedly committed scan cursor with one private executor and a consistent `state_schema.read_snapshot`. Retain its original session/construction/connection owner before entering that helper; its current `finally: Session.close()` is not proof of receiving if close fails. Capture the cache incarnation, accounting epoch, `C0` committed counter and source generation in that same snapshot; calculate `B0` from bounded object pages. Every concurrent object accounting mutation must use the one existing `adjust_cache_committed_bytes` helper in the same transaction as its object change. Detach the bounded completed proof and positively receive the original snapshot/connection before opening a **fresh** final writer transaction; never upgrade an old SQLite WAL snapshot after concurrent writes.

Under the final short row lock, first return an existing exact original rebuild receipt if one is present. Otherwise install `B0 + (Cnow - C0)` only if incarnation, accounting epoch and this exact rebuild owner are unchanged; atomically advance the rebuild epoch/generation and persist its exact final receipt with the corrected counter. Retried finalization reads that receipt and never applies the correction twice. A different reconciler/reset invalidates the epoch; ordinary accounted insert/deletion does not force another whole-corpus scan. Reserved bytes are not rebuilt or released by this operation. The result/receiving envelope is reserved before the scan, and its receipt retires only under ordinary original receiving rules.

This is an explicit **O(objects + concurrent mandatory mutations)** reconciliation with indexed paging, not a repeated generation-mismatch restart loop. Count every committed cache liability, including `ready`, `delete_pending` and `deleting`; a ready-only sum releases bytes whose original deletion has not settled. It requires qualification that all insert/delete/accounting delegates use the helper and that signed deltas/epochs are exact on both databases. Missing or corrupt mandatory quota accounting is an error requiring its owner disposition, not permission to create a zero/default accounting row from `publish_cached_object` or trust a cheap rebuilt total. Capture the actual backend snapshot and its retained connection; no shared writer is held while scanning. Bound snapshot lifetime and retained WAL/MVCC storage through execution/capacity admission. If the snapshot cannot be retained safely, close/receive it and report deferred maintenance; do not advance a cursor into a different snapshot. Select zero optional checkpoints for this scan: there is no source-stable resumable snapshot after restart, so a naked saved accumulator is not eligible. A long discovery/rebuild generation uses #996 instead; this counter scan does not create another generation store.

### Bounded status contract cut

Remove `objects`, `stored_bytes`, `protected_objects` and `unleased_objects` whole-inventory aggregates from `cache_status`. Update protocol models, generated contracts, CLI presentation and tests together; do not keep aliases, stale numbers, a background per-principal aggregate registry or `0` meaning unknown. The response reports configuration and the exact operational per-store quota counters already owned by accounting, only under the existing permissions appropriate to that information. Restricted users discover their visible cache objects through the existing authorized bounded list. If a CLI user explicitly consumes all list pages and totals them, label it an observed paged inventory, not a transactionally exact live status count; concurrent changes can invalidate the view under the existing paging contract. This choice keeps control calls bounded without introducing a new server analytics service.

`get` returns the effective current value in the existing `state` field (for example `expired` when its lease has elapsed), without performing a lifecycle transaction; it does not expose two conflicting stored/effective state fields. Owner-driven maintenance and fresh effect/adoption checks enforce that expiry and emit terminal events. A read-derived expired state neither grants source reclamation nor proves receiving; durable originals remain until the owning terminal/receiving protocol settles them.

## Evidence boundary

[restore_experiment.py](implementation/restore_experiment.py) is an executable reference guard, not production storage or the complete adapter protocol. It retains an original in SQLite, demonstrates conservative lost-commit handling, rejects changed identities, uses real AWS policy calls, and writes no progress for identical waits. It does not implement current remote authorization, runtime worker closure, cross-process transport dispatch, final quota integration, provider billing, PostgreSQL, native power loss or installed clients. Those exact implementation/qualification obligations are in [QUALIFICATION.md](QUALIFICATION.md). No root guard test is presented as #999 acceptance.
