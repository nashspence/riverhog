# Concurrency and ownership research for #991

Audited source: `8ce49de94c32ae39562aab5ea4178b1dc8c75e77` on `codex/964-session-owner` / PR #979. This is read-only source research for the external reference, not a measured utilization result or a proposed authority change. Product code is unchanged. This chapter makes no measured utilization claim; the limited diagnostic and its actual scope are reported in [RESULTS.md](RESULTS.md).

## Findings that change the investigation

1. **The maintained fixture intentionally supplies serial, single-member append work.** `publish_shared_history` calls `producer.append_inputs((source,))` for each input; its comment explicitly separates this SQLite history witness from the PostgreSQL upload-concurrency rail. The SDK may be configured for eight upload workers, but `_upload_work` creates only `min(concurrency, len(assignments))`. With a single 64 KiB raw unit admitted at a time, increasing the configured number cannot supply missing independent work. Confirm actual assignment lengths rather than assuming the default equals active concurrency. [Fixture][fixture] [SDK upload owner][uploads]

2. **This fixture's progress driver is materially different from the app lifespan reaper.** `TestClient` is instantiated without entering its context manager, including the distinct request clients created by `_api`. `_LocalApi.get_collection_upload_session` explicitly runs custody and finalization coordinators before each status request; journal seal calls explicitly run validation. Starlette requires context-manager entry to run lifespan. The installed, locked Starlette 1.3.1 `_TestClientTransport.handle_request` enters `portal_factory` per request; `TestClient._portal_factory` creates a new blocking portal when no persistent portal is set. Therefore count and time portal/thread setup as test-transport work. It is not established as a dominant cost. Simply entering the clients as contexts would also start maintenance tasks and change conditions, so that is not a controlled “optimization.” [Fixture][fixture] [Test API][test-api] [Starlette documentation][starlette]

3. **Execution capacity, running workers, original results, and reusable capacity are distinct.** The physical owner has bounded slots and no extra internal job queue. Its default four forward/two terminal slots and two/one per target are resource admission limits. An original future can publish its result before its thread exits; joined outcomes can remain unreceived. Resource receiving and cleanup have further owner-specific obligations after physical join. An idle CPU does not prove a slot is reusable. [Physical owner][physical] [Tuning][tuning] [Finalizer registry][registry]

4. **Native validation concurrency is a pool of retained sessions, not a guarantee of parallel execution.** `UploadJournalValidationOwner` has a default capacity of two, but its caller's bounded scheduler processes candidates synchronously. Each exact session has nonblocking exclusion; expensive Native/catalog/file work runs outside the global reservation mutex. Raising session capacity without a caller that can expose independent work can increase retained resource use without parallel progress. [Validation owner][validation-owner] [Service scheduler][service]

5. **The catalog and Native databases have different lock and durability stories.** The catalog uses WAL and early `BEGIN IMMEDIATE` in selected writers. SQLite permits only one writer to a WAL database, even though readers can overlap. Native storage admission has shared resource grants, but its reservation mutexes do not themselves serialize all database work. Serialized SQLite threading protects individual connection objects; it is not a global single-database or single-process lock. Never use “SQLite is serialized” as a complete attribution. [Catalog][catalog] [Native admission][native-admission] [SQLite WAL][wal] [SQLite threading][sqlite-threads]

## Concrete instrumentation boundaries

Use stable run/operation/attempt IDs with parent IDs and original resource identity. A thread name is not an operation identity; thread identifiers can be reused. Event records need monotonic timestamps, thread native ID and creation sequence, lifecycle phase, and current-thread CPU where collected by that worker. Avoid secrets, authorization tokens, plaintext payloads and raw SQL parameter values.

- **Client batches:** surround `uploads._upload_work`, executor submission, worker entry/exit and client initialization/close. Keep enqueue-to-start separate from transfer duration and retry backoff. Count actual assignments, not configured workers.
- **Source locking:** measure `_source_lock` acquisition delay and held interval around `content_for_unit`; separately label source restoration/hash and range read. Do not move the source read out of its lock merely to instrument it.
- **Test transport:** count `TimeoutNeutralTestClient` request method/route family and locked Starlette portal creations. Measure setup/teardown under a dedicated fixture transport owner. Keep app request inclusive time and child SQL/Native time separate.
- **Physical slots:** record `_try_submit` return reason, actual `_run` entry/exit, future publication, join receipt, and semantic owner receiving. `collect` rotates bounded owner buckets; sampling a foreign slot must not consume its outcome.
- **Scheduler readiness:** at `process_due_custody_receipts`, `process_due_finalizations`, `_schedule_ready_finalizations`, `_finalization_due.select`, and `process_due_provenance_journal_validations`, capture candidates/attempts/progress/refusals and the work's readiness before its next poll. A physical pool “queue depth” is zero by design; label durable due work, admission-deferred work and SDK executor queued work separately.
- **Finalizer:** distinguish pipeline stage scan, original construction, retained resume, work body, catalog receiving, and terminal drainage. Record which predecessor actually prevented work rather than attributing every idle interval to a lock.
- **SQL:** classify catalog and admitted Native connections independently. Record acquisition/admission, statement invocation/fetch, row/byte or VM-step work when supportable, transaction commit, and catalog contention. Ordinary query timers do not identify OS scheduling, fsync or SQLite mutex time by themselves.
- **Validation:** observe `_reserve`, `advance`, `release_stale` and `_drop`; count open Native sessions versus concurrently executing advances. A retained warm session that is not selected is not an idle worker.
- **Cleanup:** retain every started attempt's outcome, original process/thread join and original workspace receipt even after observer failure. Observer cancellation is not evidence that product execution stopped.

For wall accounting, construct a timeline and use interval unions for elapsed overlap. Sum current-thread CPU only over disjoint worker intervals; parent process CPU is inclusive of all threads and must not be added again. A parent operation's elapsed time includes blocking and child work. Sum of worker elapsed durations can exceed end-to-end elapsed time without inconsistency. Derive a critical path from observed readiness and completion dependencies, not from function names or the sum of inclusive profiler rows.

Passive all-thread samples show where threads were found, including sleeps and waits. They do not establish per-thread CPU. CPython 3.12's GIL restricts simultaneous Python-bytecode execution, while I/O/native code may run differently; do not prescribe more threads or processes without demonstrating which work could overlap and how original resources would be received. [Python threading][threading] [Executor lifecycle][futures]

## Bounded opportunities, conditional on attribution

These are candidate follow-ups with owners, not an optimization commitment:

| Candidate | Evidence required before proposing change | Small discriminating experiment | Preservation boundary |
| --- | --- | --- | --- |
| Amortize repeated per-member/per-batch setup | Material time or counts in executor/client/portal setup or repeated registration/preparation, not just high total append time | Fixed exact small workload, current single-member append versus already-supported bounded multi-member append, with all geometry/custody equal; keep base diagnostic as separate condition | Producer exact identities, ordering, failure/retry receiving and byte/resource bounds; no unbounded all-member batch |
| Reduce coarse source critical section | Independent ready units wait materially on `_source_lock` while one range read/restoration occupies it | Tiny multi-unit workload and an isolated delayed source; attribute held versus wait time before changing lock scope | Source lifetime, digest/range identity, restart resolver and close cannot race |
| Improve receiving cadence / avoid polling amplification | Ready original results remain unreceived for meaningful time, or repeated no-progress polls consume material work | Same small workload with explicit permitted poll conditions; measure ready→received distribution and work counts, not elapsed alone | Bounded status calls, original join, fair progress, no busy loop and no weakening auth |
| Shorten catalog writer critical path | Significant non-catalog work actually runs inside early-writer intervals and blocks independent work | Trace a small controlled overlap of independent operations and actual writer ownership | Exact epoch/current authorization, cursor atomicity and lost-commit receiving; moving work outside may require explicit contract decision |
| Expose independent validation work | Multiple independent due journals exist while execution capacity and storage grants are unused, with caller serialization established | Two tiny independent jobs with one intentionally blocked owner, using existing unit support first | Same-job exclusion, source/worker epoch fence, per-process grants and exact original receiving |
| Verification parallelism | Verification dominates and independent journal/object/member tasks are identified without violating cache-state semantics | Separate small observer-only comparison, preserving all three named reader states and exact checks; first prefer avoiding duplicated required preparation under approved semantics | Concurrent passes would change cache conditions; don't quietly remove or share checks and call the old workload faster |

The serial one-collection fixture is useful for deterministic attribution. To evaluate available service concurrency, one can eventually add a separate small independent-job experiment; its output is not evidence that a single collection's dependent finalization can run concurrently. Parallelization is an efficiency hypothesis, not a way to hide repeated whole-resource growth.
