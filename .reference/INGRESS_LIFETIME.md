# FTP, Gogurt and CLI application replay/lifetime handoff

This is the selected #998 application integration proposal, audited against product commit `c28eceaa2dfec1b3712135469ba12230e74f5ffa`. The reference does not change installed product code or complete #998 qualification. [#998](https://github.com/nashspence/riverhog/issues/998) and [#994](https://github.com/nashspence/riverhog/issues/994) control. [BUDGET.md](BUDGET.md) owns the common policy and accounting mapping; [#997](https://github.com/nashspence/riverhog/issues/997) owns publication barriers; [#999](https://github.com/nashspence/riverhog/issues/999) owns storage/materialization mechanics. The changes below compose those owners rather than introduce another recovery engine.

**Selected disposition:** retain original accepted inputs, observations, effect intents and receipts; use volatile scheduling/progress by default; receive the original worker and storage before deletion; change Gogurt's unsafe automatic post-entry retry contract; retain a CLI retrieval intent before creating a remote plan/job. None of these applications gains an arbitrary-command midpoint checkpoint.

## 2. FTP: mandatory cuts and bounded derived work

### 2.1 Accepted custody remains mandatory

Keep these ordered cuts:

1. A successful FTP upload finishes the original byte stream. `CompletionHandoff.complete` fsyncs that file, writes the exact random event-bound intent, moves it to event custody, fsyncs the affected directories, appends the exact canonical completion record under the log lock, and retires the intent. Only then can the handler release its withheld success response. A crash between rename and log append is reconciled through that same intent. Removing this cut would allow acknowledged bytes to disappear before any retained input owner can find them.
2. Before moving a discovered payload into a claim, retain its original observer result and nondeterministic IDs, initialize the original SDK primary allocation, and durably finish `claim.json`. Register the exact manifest, completion-event mappings, claim counters and `CLAIM_REGISTERED` lifecycle event together. The manifest/observation is the natural anchor; recomputing a new observation is not replay.
3. Reconcile the original handoff acquisition and payload identity. Reject substituted/replaced bytes or two different originals. `CUSTODY_READY` records the accepted custody transition. Duplicate delivery of the same completion event/claim uses its existing identity; this does not promise protocol-level exactly once delivery.
4. Publish through the SDK/Core owners with that same claim key and retained original primary bytes. #997's exact materialization/decision/custody/publication receiving governs downstream release. A transient API exception, timeout or lost final reply does not prove that publication failed or that new input identity is allowed.
5. Persist the exact surviving final receipt before reclaiming claim files. Record the public publication event with the exact original collection/archive/artifact-set identity and mark that same claim row `publication-received/accounting-pending` in the existing owner transaction. Receive original payload workers/readers and the primary storage close. Then separately remove the covered exact claim payload/tree and handoff remnants. **Keep the same durable claim/accounting root** until every attached grant, count slot, accounting phase, cost result and retained-generation cleanup liability is positively received. Only then retire its row/counters. A final publication receipt or successful PrimaryStore close alone cannot settle those downstream obligations. Preserve the independent surviving receipt and event feed required for later reconciliation.

Add that explicit terminal/accounting-pending state to the existing claim model and current state baseline. Publication retry selection skips it through an indexed state/ordinal predicate; a separate bounded receiving/retirement pass services its original obligations without republishing. Keep terminal roots charged against `pending_claim_capacity` and the existing claim reservation counters until complete root retirement, and expose their pending-receiving status rather than claiming that all counted rows still contain payload bytes. This conservative backpressure bounds retained claim-root population. Do not move accounting to another unbound file, reset it on payload disposal or call `_forget_claim` from the payload-removal helper. Split those two retirement operations explicitly. Unknown accounting leaves the original compact root retained and further optional spending sealed while unrelated already-authorized mandatory work can continue.

`completion_offset` is not equivalent to `reconcile_after`. `_reclaim_completion_events` relies on the same completion-log generation, its exact fully consumed tip, a surviving final receipt, no active claim and no outstanding original handoff intent. If the cursor could revert while old replay guards were gone, an old log event could be interpreted as new work after its original payload was already retired. Therefore retain the cursor/generation atomically with accepted claim/failure handling and maintain its monotonicity.

For an empty discovery pass whose offset is unchanged, omit the no-op cursor write. For an advancing bounded scan, persist the cursor once at the existing safe scan/admission boundary. Keep `completion_failures` raw original record, generation/offset, reason and capacity accounting; advancing past an invalid/unavailable original requires retaining its failure obligation. Failure recovery appends the exact original record durably before deleting that retained failure. Do not fabricate a new event.

Reclamation can delete one bounded candidate page in one short transaction, keeping the exact eligibility predicates and checked log-generation/tip. Select candidate identities and read bounded receipt controls first. Use the source custody-pass owner, then the completion-log shared lock, then the short operational SQLite writer; no path may hold that writer while waiting for the log lock. Recheck generation/offset/tip and absence of the exact active claim/intent before deleting the page, commit, close the state cursor/connection, then release the log lock. Do not perform payload reads, publication or callbacks under the writer. An unknown commit outcome is read back against the same candidate/event identities. This is batching a mandatory release obligation, not allowing an optional checkpoint to authorize deletion.

### 2.2 Reconciliation rotation is volatile

Do not keep `_save_reconcile_cursor`'s extra SQLite commit after every claim attempt. Do not relabel a copied cursor as mandatory merely because another transaction is available.

Use a volatile ordinal per live source with the existing bounded indexed seek/wrap algorithm. Preserve `claim_attempt_budget`, bounded failure/discovery work, pending-claim capacity and the reserved new-input slot. Only active publication rows participate: terminal/accounting-pending roots leave the publication retry set even while their receiving liability remains retained.

For cold start, derive a hint from the last **already retained public `ATTEMPT_FAILED` outcome**, then point-read that active claim's current ordinal. Add an ordinary expression index on `(json_extract(event_json, '$.type'), sequence DESC)` to the existing exact state baseline; this permits a one-row latest-failure lookup even when newer successful publication events exist. If the last failed claim is absent, terminal/accounting-pending, or no failure outcome exists, use ordinal zero. Validate the original event before using it. The selector neither updates a cursor nor emits a failure event for scheduling purposes.

The existing event feed deliberately records actual failed publication attempts as `io.riverhog.ftp_spool.claim.attempt_failed`, including exact claim/source-event binding and error type. Preserving those accepted public outcomes is independent of recovery speed. The proposed selector consumes that obligation; it does not create a new per-attempt recovery record. Index maintenance has real CPU/page/storage cost and must be measured; it is not claimed to be free. Cold lookup is indexed `O(log E)` over `E` retained events plus one claim lookup, with one event decoded; a page is `O(log C + B)` over `C` claims and `B` admitted candidates. Do not claim constant physical database work.

No outcome committed before a crash means no durable scheduling advancement for that attempt. After restart, a bounded retry may repeat it. There is no liveness guarantee under infinitely repeated crashes before every outcome boundary. Once outcomes are received, failed prefixes rotate across cold restarts, including when later new admissions succeed. The reference witness cold-reopens ten passes across five pending failures, interleaves newer successful publication events, and obtains exactly two rounds without a cursor write or history scan. That selector witness uses the audited schema with active fixture claims; production adds the terminal-state predicate above and must separately prove that accounting-pending roots never re-enter publication scheduling.

Existing microstep tests that assert the private `reconcile_after` commit must be rebaselined to this public fairness/custody behavior. Keep the generic `FtpOperationalState` commit-outcome tests; removing a derived cursor does not make unknown commits safe to ignore. Do not turn unrelated diagnostic/status emission into a source of budget credit.

### 2.3 Fix registration ambiguity before performance work

At the audited source, both `_claim_new_batch` and `_accept_completed_file` put `_register_claim` inside `except BaseException: shutil.rmtree(claim_root)`. `_register_claim` has already committed the manifest, exact observation references and event mappings before returning. An after-commit exception therefore leaves a registered claim whose original observation and primary allocation have been deleted. Reconstructing only `claim.json` cannot restore the original sampled graph.

The selected rule is conservative and concrete: **once the original finalized claim manifest exists, construction failure never automatically deletes that candidate.** Reopen and compare the original manifest; use exact registration lookup/retry. A known absent/uncommitted registration does not require new IDs: retry the retained candidate. If admission must be abandoned, use an explicit owning disposition after proving no accepted registration/effect and receiving all original resources. Pre-manifest scratch can be removed only when the actual original constructors/readers/storage have positively closed. A constructor exception or absent returned object is not that proof.

Use the SDK's existing `PrimaryStorageFactory` seam to retain the actual opened storage before handing it to `PrimaryStore`. The factory retains anything it fails to return; the application retains returned storage/store and its exact allocation/root. This provides an original close receiver even if `PrimaryStore` construction or its internal close raises. Do not infer ownership from a filename or recreate a store solely to declare an earlier handle closed. Mechanical backend changes belong to #999.

The executable fault witness uses the real `CompletionHandoff`, native provenance observer, PrimaryStore and SQLite commit. Baseline cleanup deletes the original evidence after the injected committed-reply loss. The reference's narrow cleanup guard preserves byte-identical manifest and graph and permits exact `_register_claim` retry. This is a demonstrated source defect and a guarded reference splice, not a shipped fix.

### 2.4 Complete shutdown and reclamation order

`create_app` currently cancels `_scheduler`, gathers the canceled asyncio task, and closes `ApiClient`. The awaited `asyncio.to_thread(adapter.run_once)` can still be executing. An actual lifespan witness observes API close before the original blocked pass exits.

Implement this application-owned order:

1. Close admission for scheduler, management `run`/`flush`, and any protocol publication entrypoint. Retain each admitted original pass and receiver before starting it. Keep one active pass slot for the existing serialized spool and refuse/defer additional submissions; do not replace the existing lock with an unbounded executor queue.
2. Stop scheduling another pass. Cancellation can detach an HTTP/async waiter; it cannot clear the pass slot or cancel away original result/resource obligations. Status reads only bounded owner state and durable status counters.
3. Let the original SDK/Core call reach its authorized result or uncertainty boundary. Pass the cooperative stop request to supported owners; do not claim cancellation of a network call or thread stops remote work. Keep the original thread, result/exception and exact private receiving callback. Receive only after actual thread termination/join, never from a reconstructed Future.
4. Receive the original pass result exactly once, or retain the exact failed/unknown receiver for explicit retry. Public caller authentication is not needed to finish private original receiving; no new public operation or read authority is granted by this cleanup path.
5. Receive all original primary stores, borrowed readers and `FtpOperationalState` connections/cursors. Unknown close keeps the original object and exact directory/identity charged. No implicit second close while unwinding. Explicit retry invokes the same original close owner and checks its positive completion contract.
6. Close the original API client only after those obligations settle. Failed API close retains that client and its receiver. A normal return from a storage adapter whose contract reports pending work is not positive close; translate pending to an explicit pending result/refusal.
7. Complete shutdown only after these receivers settle. If the supervising process is forcibly killed, retain durable claim/intent/receipt state for original reconciliation; do not issue a success message claiming the unfinished resources or remote effects were received.

For a receipted claim, move the payload-removal part of `_finish_claim_cleanup` outside the current `with self._primary_store(...)` block. In the audited implementation it runs inside that block, before `PrimaryStore.__exit__` calls `close`. The new application receiver first checks authenticated custody and records publication/terminal status, then positively receives original store close, then invokes exact payload cleanup. If removal is interrupted, the surviving SQLite manifest and receipt allow another bounded retirement attempt without re-closing an already received original or republishing the collection. Its accounting root remains separately retained as specified in §2.1; only complete original child/grant/cost/cleanup receiving authorizes `_forget_claim`.

For `serve_ftp`, a service stop closes new accepts, retains active data-channel/handoff operations, completes or records each original receive's non-success outcome, closes the actual server/channels, and receives them before removing any intake owner. Preserve a completed handoff even if sending `226` loses its reply; the client may retry with the existing delivery semantics. Incomplete transfer bytes have no successful completion receipt; their cleanup still follows their actual file/channel owner. Local listener fixtures and explicit installed POSIX qualification must cover these operations; this reference does not run a real FTP service against user input.

The [reference lifetime code](implementation/ingress_lifetime.py) implements the bounded pass/result slot, independent storage/API receiving, and close-before-retire guard. It is not a complete ASGI listener integration, remote authority checker, factory implementation or storage backend. Failed/ambiguous thread start remains with the original start owner; it cannot be inferred absent and retried through another worker.

### 2.5 Explicit retained-metadata capacity for FTP and Gogurt

Add **required** positive exact integer deployment settings `retained_state_max_bytes` and `retained_state_min_free_bytes`: per FTP `SourceConfig` and on Gogurt's `ListenerConfig`. Wire the fields through strict document readers, generated/installed schemas, constructors, CLI configuration and examples in the same state/configuration cut. Neither setting has an implicit unlimited or production default. Their values are operational admission, not a maximum archive size or a replacement for payload/workspace admission. Do not claim that `pending_claim_capacity` or the number of active workers/processes bounds historical metadata bytes.

Use a small owner-local capacity adapter over each application's existing public resource/state primitives: FTP's operational-state and original file owners, and Gogurt's listener-state and native-resource owners. Do not import a Stove0 implementation or create a quota database/service. Keep finite live-byte accounting and the bounded outstanding reservation set in the existing owning state/accepted records. Account for selected originals, unselected candidates still owned, staging, cleanup liability and backend overhead supplied by the real storage owner. #999 supplies shared physical admission/storage mechanics; this application cut determines when acceptance and release are allowed.

For FTP, the admitted population includes completion-log/intent/acquisition metadata, claim manifests, retained observation/control metadata, lifecycle events, surviving final receipts, terminal/accounting-pending roots and their original reservations. Existing prepared-primary/payload limits remain separately enforced and cannot be borrowed to hide these costs. For Gogurt, include accepted configuration/registration state, mount/dispatch intent, started/terminal/uncertain results, retained operator evidence, tombstones and pending native/reader/cleanup ownership. Retaining a completed row consumes capacity even though it no longer consumes an execution slot.

Reserve both the next accepted original and a conservative bounded mandatory result/cancel/receive allowance **before** the corresponding action: before FTP success/claim adoption, and before Gogurt dispatch. Required lifecycle outcome events consume that reservation; a publication retry cannot start if it has no reserved outcome/receiving capacity. Reserve any larger next barrier before accepting or disclosing it. Keep separate headroom for original cancellation, terminal receiving and retirement, so refusing new work does not prevent the already accepted work from settling. Capacity refusal stops new acceptance/dispatch; it does not erase acknowledged spool bytes, unconfirmed handoffs, an entered command, an accepted result or an unresolved accounting root. A denied new admission may report a bounded live diagnostic without recursively allocating a new durable attempt record.

The dedicated protected volume quota is an independent physical bound. A `statvfs`/free-space observation and `retained_state_min_free_bytes` alone are not proof that mandatory headroom is reserved against competing writes; the physical owner must provide the actual reservation/admission guarantee. If that guarantee is unavailable, refuse new acceptance before the external acknowledgement/effect. Do not weaken durability or delete originals to force a write through. Existing admitted work retains its original reservations and receiver even when the next unrelated admission is refused.

On startup, reconstruct exact accounting through bounded indexed pages and bounded streaming traversal of the known owned namespaces before declaring readiness for new acceptance. Retain the original file/connection/reader for each step, conservatively charge unexplained candidates and honor the original outstanding reservations. Do not infer zero usage from an empty live-object cache, missing accounting field or interrupted prior close. A populated incompatible or corrupt authority state is refused intact. Recovery scans are explicit owned work; status and cleanup observations do not run them. Persist accounting changes with the existing required acceptance/selection/retirement boundary, not a quota journal after every scanned file, callback or poll. Positive original deletion/transfer/close receiving is required before releasing its charge.

**Integration gate:** independently grow active claims/dispatches and historical log/event/receipt/terminal records; exhaust retained metadata and physical capacity before acceptance, during result selection and during cleanup. Prove refusal preserves all acknowledged/entered originals, pending roots are excluded from publication/command retry, reserved receiving remains operable, unknown writes/closes retain their exact reservations, and restart neither rescans whole history on each status call nor rebuilds accounting into an unbounded in-memory list. The 19 reference tests do not implement or qualify this capacity adapter or the new terminal-root state; they are explicit production integration obligations.

## 3. Gogurt: command entry is the replay boundary

### 3.1 Preserve dispatch authority; change automatic retry deliberately

`ListenerStore.observe` retains a mount generation, marker identity, route and complete plan before work is enqueued. `start_dispatch` atomically changes an eligible row to running and increments attempts before `Popen`. `revalidate_gogurt_action` checks current mounted-volume provider and marker before using the accepted argv. On restart, `ListenerStore.create` turns running rows into uncertain instead of rerunning them. Keep these safeguards.

Current `_worker` permits ordinary nonzero command exits to enter `retry` (up to three attempts). The child receives arbitrary argv with no accepted effect-idempotency or mid-operation resume contract. A nonzero exit can follow an external write. This is a deliberate public behavior hard cut:

| Original launch/wait evidence | New disposition | Automatic next invocation |
| --- | --- | --- |
| Positive refusal before calling the process entry operation, such as current marker revalidation failure | Pre-entry failure; retain original plan and bounded existing retry/backoff limits | Permitted only after current revalidation under that same plan/invocation authority |
| Entered original child, original wait received, exit zero | Command completed; preserve its original result | None for the same dispatch |
| Entered original child, original wait received, nonzero exit | Observed failed command; external effects remain unproven | None |
| Process creation outcome unknown, lost child/result, crash, or wait/termination/kill not positively received | Uncertain original invocation | None |

Persist entry/wait/effect-disposition facts in the existing dispatch row/result, outside marker/plan semantic identity. `running` remains a conservative “entry may have happened” anchor; do not add a mandatory write immediately after `Popen` solely to mirror the process microstep. A `Popen` exception is conservatively unknown unless its original launch owner proves entry did not occur. A PID check, elapsed timeout or empty queue cannot establish that fact.

A manual operator rerun is a new explicitly accepted invocation linked to the original unresolved/failed dispatch. It must visibly state that the prior effects are unproven; it cannot reset the original row, reuse a new retry budget invisibly or claim recovery. A cooperating child may use an explicit supported idempotent invocation/result protocol with its original attachment; arbitrary argv gets no implicit idempotency opt-in and no fabricated checkpoint.

Tool/process/provider waits earn zero useful work here. No optional midpoint generation is selected for the arbitrary command. Keep the ledger as its existing application authority, not as an independent recovery-percentage store. A supported downstream Riverhog application receives a disjoint parent grant through its explicit invocation contract, with current authorization and actual receiver binding as in BUDGET.md.

### 3.2 Stop, uninstall and installed platforms

Current `_settle_worker` performs terminate, bounded joins, kill and wait and records uncertainty if it cannot settle. Keep the actual `Popen` and worker on the runtime owner, rather than only a local daemon-thread variable. Stop admission, request termination of the original child, receive its original wait, receive the worker/result, then release its application lock and other resources. Do not hold a status/coordinator lock across join/wait/close. If receiving remains pending, retain the runtime, worker, process and `ListenerLock` with a bounded pending diagnostic; repeated status must not attempt cleanup.

The direct child's positive exit/wait proves only the direct process result. An arbitrary child may spawn descendants or effects outside the listener. Do not certify their absence from the parent PID, listener lock, native-service status or a zero exit alone. Existing mounted-volume/marker checks and downstream exact effect protocols continue to supply their own authority. When they provide no receipt, retain the unproven effect disposition; do not add an assumed process-tree recovery guarantee.

`uninstall_listener` currently unregisters the native service, waits for native absence/old parent death/lock release, then recursively deletes the state root. That can erase uncertain dispatches or completed but irreplaceable operator evidence. Selected behavior:

- Ordinary uninstall stops/unregisters the native service and returns an explicit **native-uninstalled, state-retained** result containing the state location and bounded unresolved counts. It never automatically deletes the ledger, accepted plans or original results, including when state is corrupt/unreadable.
- Add an explicit owner-controlled state-disposition operation, separate from uninstall. It requires the exact retained state identity and explicit acknowledgement of irreplaceable-evidence loss, takes the application control lock, and refuses while any actual native worker/process/reader/cleanup owner is unresolved. An operator may explicitly abandon an unknown external-effect record; that acknowledgement does not become proof the effect never occurred and does not release another owner's live resource or budget reservation.
- Retain quarantined/unreadable original state rather than reinitialize it. Preserve the original configuration/native registration rollback identity until settlement. A failed unregister/stop cannot authorize restoring a replacement native worker while the original may still run.

That local operator disposition cannot abandon, restart, settle as no-output, or retire the source of an attached sealed Core external-effect claim. Preserve any original attachment/receiving/accounting reference still needed by that owner; the stricter [Core sealed-effect rule](CORE_WORKFLOWS.md#4-effects-no-output-and-abandonment) controls until the original successful effect settlement is received. A local acknowledgement of evidence loss is never a Core negative-effect receipt.

Update the installed CLI result contract and platform tests together. In particular, rebaseline tests named `test_uninstall_removes_corrupt_state_without_reading_it`, `test_uninstall_removes_non_directory_state_root_without_following_it`, and retry timing tests that currently assume a nonzero entered command is automatically retryable. Preserve no-symlink/private-path refusal and operator-safe diagnostics.

Platform implementations remain owned by their real adapters: Linux systemd user registration, macOS launchd user registration, and Windows Task Scheduler with the cooperative `stop.request` file. Windows already waits for task stop rather than blindly treating `/End` as receipt. Test each actual installed stop/restart/unregister path, delayed replies, inaccessible process status and original-child wait on its platform. This reference's Linux fixture child tests do not qualify systemd, launchd or Task Scheduler.

### 3.3 Heartbeat and growth

`_heartbeat` currently writes an fsync-backed `atomic_write` on each poll and calls `ListenerStore.summary`, whose `GROUP BY state` counts all retained dispatches. The heartbeat is advisory liveness/presentation. Use an atomic complete snapshot with the existing private-file and platform promotion rules, without forcing durable replay publication on every poll. Keep durable configuration, installation identity and cooperative stop requests on their own mandatory paths; do not weaken `atomic_write` globally.

Materialize bounded state counts in the same required dispatch-transition transaction and add an appropriate attention-order index. Preserve exact counts under known rollback/lost commit; status reads only fixed counters and a bounded attention page. Per-state indexed pages can merge at most the fixed number of attention states times the page size, rather than scanning all history. Charge/observe ordinary index and counter maintenance; these are public status projections, not useful-work credits or semantic effect authority.

Apply §2.5's explicit retained-metadata admission before accepting a new activation/dispatch and reserve its terminal/cancel/receive barrier before process entry. The default retained-ledger uninstall behavior is not permission for unbounded unadmitted growth: refuse new work when that operational capacity is exhausted while preserving original receiving and operator inspection.

Avoid unchanged-poll writer transactions by comparing prepared mount observations against the current accepted state before the short transition commit. Move marker/route I/O and action planning outside `BEGIN IMMEDIATE`, then recheck exact expected mount generation/marker/provider/configuration when accepting a changed plan. Never mark a mount absent from an incomplete/failed enumeration. A bounded derived enumeration can restart; already accepted activations/dispatches remain durable. Preserve the current rule that unchanged marker identity does not create another dispatch.

Measure history growth, mount population, bounded attention reads and repeated restarts. Existing schema/integrity verification at owner open is not claimed constant-time; charge and qualify that real work and retain the database on refusal. #999 owns any required physical index/staging/verification mechanics. No whole-ledger rewrite or optional checkpoint is added to a heartbeat/status request.

## 4. CLI: original inputs and effects, delegated checkpoints

### 4.1 Upload and progress

Keep `prepare_primary_upload`'s explicit fresh/resume decision. The original identity contains a source naming view and random artifact IDs, is published before remote registration, and is checked against complete source fixity. Missing one original half cannot silently initialize a replacement. `LocalUpload.open_sources`/`open_inventory` verify the original commitment before exposing descriptors and retain independent actual readers.
