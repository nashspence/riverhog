# Bounded Core stepping: static validation and receiving matrix

## Conclusion and scope

**The accepted prefix-codec refinement is independent of the proposed Core scheduling change. A simple loop around Native advance is not yet justified.** The important gaps are the extra predicates currently checked at every outer Core turn, the meaning of a capacity or failure exit after earlier durable Native commits, and the larger amount of work held under one scheduler reservation. These are source and ownership questions; another tiny success timing would not resolve them.

This review inspected clean source **d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e**, compared it with **3b47cbba770c31eb1487b50f7e3b16533c10e827**, and read the owning tests and qualification definitions. No product or probe ran, no tests were collected or run, no product/test modules were imported, and no repository file was edited. The accompanying **core-stepping-source-audit.json** records exact trees, file hashes, tool metadata, and both supplied issue-comment body hashes.

The request comment [6887528297](https://github.com/nashspence/riverhog/issues/991#issuecomment-6887528297) still describes CI as pending. The later receiving-owner report [6889181049](https://github.com/nashspence/riverhog/issues/991#issuecomment-6889181049) supersedes that status: d4d7 is reported fully qualified through CI 43664490758 attempt 1, tested merge 05abffaef7f87a93b4949fcd6981e4ce6d033864, with 31 actual jobs, 26 workloads, 7,579 selected supplemental cases, 48 scoped witnesses, 54 executions and 1,219 top-level samples. Those are **receiving-owner results**, not a new execution or independent raw-artifact qualification by this reviewer. The report explicitly leaves whole-path G10/G12/G13 open.

## 1. Exact codec reconciliation

Only two tracked files differ from 3b47: the Native private checkpoint implementation and its owning checkpoint tests. Core, API, SDK, growth reader, SampleBatch, all Core tests, qualification scripts, guides and lock files are unchanged.

The private prefix reader now returns its exact freshly selected row tuple together with the PrefixState it already decoded to validate that row. Initialization consumes that parsed state. The private read path consumes it for the frame-ordinal comparison; load and fence each still perform a new read. Publication deliberately ignores the returned parsed state and independently parses its selected prefix after exact current-row equality. The change adds no ledger-held decoded state, acceptance cache, skipped SQL, or altered transaction/CAS predicate. [Checkpoint implementation][checkpoint]

The new test adds the Cartesian product of three boundaries—load, fence, publication—and three warm corruptions—noncanonical JSON, inconsistent source position, unknown field. It warms the same parent, corrupts the stored prefix, expects rejection at the next observation, checks the database snapshot is unchanged and rolls back. That is nine parametrized cases, read statically here. [Warm-corruption test][warm-corruption]

The receiving owner reports 5,185 to 3,758 PrefixState parses with unchanged 1,903 ValidationCheckpoint parses and 479 semantic traces. The arithmetic reduction is 1,427: 945 load observations, 479 fence observations and three initialization repeats. It is not a new performance measurement by this review. This within-observation codec reuse grants no authority to reuse a successful Core prerequisite or source-fence result across Native steps.

## 2. Boundaries that the candidate must name explicitly

| Existing boundary | Current behavior | Consequence for several inner advances |
| --- | --- | --- |
| Stamped Core service call | Reads a catalog stamp, executes one service unit, reads another stamp, and reports catalog-visible change. | Native commits alone need not change that stamp. A partial batch cannot inherit the old interpretation of a no-progress capacity return without defining adoption. |
| Core service unit | Checks capture, detached validation source, epoch scan, topology, union, rank and replay preparation before selecting the retained owner. | Some completed preparations still check dependent rows and exact captured bytes. A fresh certificate-manifest check is not a replacement for all these predicates. |
| Retained owner reservation | One nonblocking slot lock is held around progress, one Native advance, catalog adoption, optional terminal receiving and return. | An inner loop lengthens that reservation. The pool capacity is not a parallel executor, and a step ceiling alone does not specify coordination latency. |
| Native advance | Preserves its own fresh source/certificate/worker checks, checkpoint load/fence, bounded child work and durable phase transaction. | Every attempted inner advance remains a real child obligation; its checks, writes, failures and returned state cannot be represented by only the last sample. |
| Catalog adoption | Publishes detached metadata after Native commit; validates workspace/epoch, monotonic progress and exact source plus job version/progress CAS. | It can accept a monotonic jump, but every intervening exit and competing change still needs a specified result and recovery rule. |
| Original receiving | A slot, construction, SQLite body, lease and borrowed readers remain charged until their original owners confirm closure. | Terminal completion, budget exhaustion or cancellation must not free these early or substitute a new owner for an uncertain close. |

The exact service sequence is in [Core unit and stamps][service-unit]. The reservation, publication and exception paths are in [Owner.advance][owner-advance]; source/worker/certificate layering is in [_OwnedSource][owned-source]. The separate monotonicity and compare-and-set checks are in [jobs.publish_progress][jobs].

### A concrete guard gap before any performance question

At the old next Core turn, the epoch preparation checks its last Frame row; topology checks its last Fact; union checks its last Fact/Arc; rank checks its saved vertex/arc/graph links. The detached validation-source read also checks the captured tail segment. These are stronger than merely testing that the Scan manifest and source identity still match. [Epoch guard][epoch-guard], [topology guard][topology-guard], [union guard][union-guard], [rank guard][rank-guard], [captured-source read][source-read]

A focused counterexample is therefore: complete one valid step; remove or alter the exact dependent row or captured tail while leaving the top-level manifest/version unchanged; attempt the next step in a phase that does not otherwise consult that row. The old outer path rejects before entering that Native step. A proposed inner path that checks only source/worker/certificate metadata may proceed farther. This is a **static behavioral distinction to resolve**, not a claim that such a candidate was executed.

The source owner must either preserve the relevant fresh predicates at each inner boundary or justify a changed ownership/invalidation rule that makes the omitted state inaccessible to mutation and preserves corruption/error ordering. Increasing a loop bound, reusing a manifest digest, or showing a tiny valid success does not supply that proof. Existing owning corruption tests explicitly cover missing checkpoint links and changed captured pages. [Preparation tests][epoch-tests] [topology-tests] [union-tests] [rank-tests] [source-tests]

### Catalog progress lag is already possible, but not fully qualified for a batch

The existing worker-exit test deliberately dies after Native accepted-prefix commit and before catalog publication. Reopening claims a new epoch, adopts the committed prefix and forbids reading an already accepted frame again. This proves an existing single-boundary recovery behavior. [Crash-before-adoption test][crash-test]

Worker currentness intentionally checks identity, source/certificate binding, epoch and allowed state without comparing an old saved job version/progress. Final adoption separately compares the current slot job version/progress. This distinction permits the source fence to remain current while Native leads the catalog; it does not settle capacity, rejection, cancellation, reply-loss or fairness semantics for several steps. [Job identity and adoption][jobs]

In the maintained warm atom-capacity witness, the single attempted Native action leaves both Native and catalog progress unchanged. If earlier actions in a future loop already committed, applying the same false-return handler without a partial-progress rule could leave the catalog stamp unchanged after real work. The candidate must specify whether and when it adopts the last valid progress under fresh fences, and how its caller observes that result. Separately, even the current one-step route can cold-open or recover, adopt restored progress in `_open`, and then return false on capacity: the real catalog stamp must still observe that opening effect. A false owner return is therefore not proof of an unchanged catalog. A stale source or lost worker must never gain authority to publish merely because some Native work already committed. [Opening and advance][owner-open]

### Exact exception and receiving outcomes matter

Keep normal capacity separate from stale authority, invalid certificate/workspace, semantic rejection, unknown provider exceptions and cancellation. Distinguish `JournalValidationCapacity` from the exact SQLite-admission failure site; their shared owner catch does not make all input, commit and construction states identical. Existing close failures can replace normal return or another primary exception and keep the same slot marked closing; retain their exact chaining and precedence instead of flattening them into no-progress. Confirmed terminal catalog outcome survives a later close failure. An independent pending reader must not hide another slot's unknown close exception. The existing custody tests distinguish these cases. [Custody tests][custody]

The scheduler currently calls `_schedule_finalization_if_ready` after each progressed candidate. Grouping several old units before that point also moves this scheduling boundary, even if each Native step still adopts catalog progress. The owning design must preserve or explicitly justify that behavior; the matrix does not assume delayed scheduling is equivalent. [Scheduler boundary][scheduler]

For each injected boundary retain the pre/post Native checkpoint and input identity, job identity/version/progress, catalog terminal row, exact exception family and chaining, active slot identity, original construction and lease, checked-out catalog connections, admission counters and final resource receipts. These observations are more discriminating than a final successful archive or a changed elapsed time.

## 4. Current tests and declarations assume one step

The owner capacity witness explicitly asserts one Native call, no drop/publication, an unchanged Native snapshot and input object, unchanged catalog job, no payload read, and one load child. A late capacity case after several successful steps has different aggregate observations and needs its own expected behavior; weakening the old assertion would conceal a regression. [Capacity witness][capacity-witness]

The stamped caller witness expects one service unit and two stamps on the normal return path, but only the first stamp when the unit raises. Its actual fixture deliberately fast-forwards the Native session between three selected service-owned turns. The ordinary service-unit witness has the same three-turn shortcut. These are valid current scoped tests; they are not a baseline for silently adding extra children to an unchanged declaration. [Caller witness][caller-witness] [Service-unit witness][unit-witness]

Several existing witnesses also select 1,025 unrelated rows, 65,537-byte metadata, large preparation windows, or full finite-case families. Do not invoke those whole tests as the proposed tiny diagnostic. Existing helper loops with 1,000/10,000 maxima are source fixtures, not permission for a new campaign. None were run here.

Any future implementation must change the owning executable declaration and observer dimensions together: admitted step/work limits, actual attempted steps, Native/source/worker/certificate calls, progress reads, adoption attempts, result reads, terminal receiving, and the sum of all nested work. The enclosing unit/stamped-caller/scheduler composition must receive that change. Standalone Native steps keep their independent obligations and fresh validation. Memory/resource peaks do not equal sequential operation totals, and correction-wide reconstruction remains a separate total-growth term.

Qualification is derived from maintained Make/workload definitions and source-owned witness markers with exact declaration digests, not from the number of test names in this note. Actual pytest collection determines selected node IDs; the receiving logic requires exact workload and growth-result bindings. This review reads those definitions without importing or invoking discovery. [Qualification definitions][qualification] [Case inventory][inventory] [Evidence receiving][evidence]

## 5. Is a tiny actual Core observation needed now?

**No additional execution is needed to identify the present blockers.** Source establishes the extra prerequisite predicates and the single-step capacity/adoption assumption. The accepted codec delta is fully enumerated and separately reported qualified. A new success run cannot authorize skipping guards, determine acceptable catalog lag, prove fairness, or close correction-wide growth.

After the source owner chooses a concrete boundary contract, a tiny actual observation could answer one narrower uncertainty: whether the proposed partial-progress/adoption path preserves the original durable checkpoint, exception and lease behavior when the second step pauses or fails. That should be a bounded falsification of the design, not a performance demonstration.

If that question remains unresolved, use one maintained minimal journal recipe with no unrelated-row geometry and an explicit original construction/reader owner. Include source/certificate preparation in the recorded work. Admit at most two or three Core units, with a fixed small inner-step grant; compare exact retained progress and catalog adoption at each selected boundary. A second exact journal is only necessary for the ready-key test. Do not run the whole witness modules or an entire publication. If the selected boundary is partial, report it as partial; do not claim terminal verification merely because the small admitted prefix agrees.

Use a single external 120-second cooperative workload cap covering construction, preparation and observations. Check it before starting each bounded action. Stop admitting work at expiry, retain any incomplete evidence, and let original receiving/join finish without a hard-kill promise. Record clean source and exact script/tool identities, all actual child/primitive observations, original probe/lane/launcher exits, borrowed readers, construction frames, SQLite admission counts, catalog checkouts and scratch cleanup. A failed setup remains its own original receipt. Preserve nonempty/unreceived scratch for review. This is a conditional outline only: no driver, product execution or tests were created or run for it.

## Decision for the parent design

Leave an implementation out unless the owning design explicitly resolves (1) which old Core prerequisites remain fresh between inner steps, (2) adoption and error precedence after partial durable progress, (3) per-unit aggregate work/resource admission and actual child multiplicity, and (4) the scheduler's return-to-other-work boundary. The request does not permit phase fusion, commit removal or concurrency changes as shortcuts. Passing the focused matrix would support the chosen boundary behavior; it would still not establish whole-path G10/G12/G13 acceptance or production throughput.
