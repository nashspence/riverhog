# Independent review: completed Finish handoff

## Conclusion and scope

The best narrow candidate is to combine **application of the final `SemanticFinish` batch with the parent's move to `recording`**, then return immediately. It would not run recording validation, publish the accepted frame, or execute another semantic phase inside that call. It would remove a later parent-only handoff, not any of the measured 25 Finish preparations for six assertions.

**Keep the current boundary unless the Native owner defines an explicit completed-child discharge contract and Core owns the corresponding observation mapping.** The current next call freshly loads the completed child and checks its digest and cursor dependencies. A direct parent promotion stops doing that check. Deleting the completed child checkpoint between returned calls supplies a concrete source-derived behavioral difference. This is a rejection/restart counterexample, not a claim of accepted invalid output.

This review is static. No product package was imported, no tests were collected or run, no fixture or fault injection was executed, and no implementation was changed. Local source reads, git object/diff inspection, standard-library JSON/hash processing of existing evidence, and external report creation are the only new work. Runtime experimentation would not decide the missing ownership contract.

Source is exact `d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e`. The controlling request is [6890881026](https://github.com/nashspence/riverhog/issues/991#issuecomment-6890881026); the retained one-step Core decision is [6889902338](https://github.com/nashspence/riverhog/issues/991#issuecomment-6889902338). ## 2. Exact current handoff and the direct counterexample

The final Finish preparation reads no next changed assertion, sets `phase="done"`, increments the child version, and returns an empty write tuple. `_child_step` applies it within `_commit`, then publishes the parent at `phase="finish"` with that child's identity and digest. The following call loads the child, compares its digest to the parent, observes `done`, and calls `_move(..., "recording")`. `_move` clears the child fields. Finish is not one of the child types for which this branch calls `result()`.

These are separate committed public observations. The child application and its parent publication already share one transaction: `BEGIN IMMEDIATE`, fresh parent fence, child application, parent publication, commit, with rollback on `BaseException`. The candidate is not removal of a redundant standalone child `commit()`; replay does not invoke that standalone method. Sources: [`_entry_replay.py:2294–2316`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_entry_replay.py#L2294-L2316), [`2463–2497`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_entry_replay.py#L2463-L2497), and [`_semantic_finish.py:790–823`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_semantic_finish.py#L790-L823).

### Static fault sequence

1. Start from a valid final `row` state, such as the state preceding historical initial ordinal 100. Keep source, worker, catalog, accepted prefix, predecessor, frame, and Core preparation records unchanged.
2. Let the final Finish application and its parent publication commit and return.
3. Delete only the retained `journal_semantic_finish` row, or replace its attempt/binding/header/checkpoint so it no longer matches the exact completed child.
4. Invoke the next ordinary public step through its normal owner.

Under the current implementation, parent phase remains `finish`. The next `_child_step` calls `child.load()`. A missing or differently bound row raises `StaleSemanticFinish`; an unknown algorithm or corrupt checkpoint fails its own validation; a different valid child state fails the retained parent digest comparison. The last completed assertion remains a checked dependency even when the child is done. Its missing cursor link can also cause rejection. No parent handoff is committed after that rejection. See [`_semantic_finish.py:541–599`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_semantic_finish.py#L541-L599).

Under the direct combined promotion, the same first return would leave parent phase `recording`. The next dispatch calls `_check_entry_recording(current.document)` and then moves to `publish`. That check resolves effective agent/context references; it does not load `journal_semantic_finish`. With otherwise valid recording inputs, the child-row deletion alone does not reproduce the former rejection and the path can commit another parent transition. See [`_entry_replay.py:2653–2673`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_entry_replay.py#L2653-L2673) and [`journal_store.py:1293–1312`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/journal_store.py#L1293-L1312).

The other fresh checks do not secretly restore this child dependency:

| Later path | Checks it actually owns | Completed Finish check? |
| --- | --- | --- |
| Parent ledger load/fence | Exact parent algorithm, attempt, binding, worker; canonical parent; exact prefix marker/frame ordinal and predecessor frame reference | No |
| Recording branch | Effective recorded-by agent and optional recording context | No |
| Accepted-frame publication | Prepared prefix application, exact parent/prefix CAS, frame acceptance and quarantine replacement | No |
| Session terminal/result construction | Complete input, no pending/quarantined frame, exact final source identity/bytes/hash/frame count, successful prefix finish, store freeze | No |
| Core source/certificate currentness | Exact selected source/worker and captured certificate manifest authority | No |

Sources: [`_session_checkpoint.py:416–565`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_session_checkpoint.py#L416-L565), [`_entry_replay.py:2564–2587`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_entry_replay.py#L2564-L2587), and [`journal_session.py:1469–1510`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/journal_session.py#L1469-L1510).

The conclusion is deliberately limited: **the time and necessity of rejecting corrupted/replaced completed-child state changes**. This does not prove ordinary executions encounter this fault or that a final invalid journal becomes accepted. The current protocol also eventually stops consulting the child after its checked handoff. What is missing is permission and durable evidence to move that discharge point earlier.

`ValidationCheckpoint.from_json` requires child fields in child phases, but does not prohibit them in `recording`. Thus a schema change is not established as necessary. Merely retaining the fields would also be insufficient: current recording dispatch does not validate them. The owner must define completion evidence, live-dependency versus retirement semantics, restart behavior and the exact point of discharge. See [`_session_checkpoint.py:155–190`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_session_checkpoint.py#L155-L190).

## 3. Core observation mapping and the rank-result limit

Each ordinary Core unit freshly performs source/capture, epoch, topology, union, rank and replay preparation before one owner advance. The owner calls Native `advance` once and publishes returned progress through the catalog CAS. The surrounding method compares actual before/after stamps. A successful scheduled unit can then trigger finalization readiness and rotate scheduling opportunities. Sources: [`collection_uploads.py:2122–2177`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/collection_uploads.py#L2122-L2177), [`2209–2251`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/collection_uploads.py#L2209-L2251), [`upload_journal_validation_owner.py:2054–2089`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/upload_journal_validation_owner.py#L2054-L2089).

The retained missing-rank-Result counterexample remains binding against a hidden Native loop. Rank preparation checks the exact last published `Result` row and its counters. `verify_current()` freshly reads manifest/source records but does not check that result. Deleting that dependent row while preserving the manifest can make the next ordinary Core unit reject. Passing Native's ordinary certificate callback is not a continuing all-dependency readiness grant. See [`upload_journal_rank.py:251–279`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/upload_journal_rank.py#L251-L279) and [`upload_journal_certificates.py:735–751`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/upload_journal_certificates.py#L735-L751).

For the one immediate-return candidate, however, actual recording work would still occur on a later Core call with the ordinary preparation chain. A rank deletion after the fused commit would therefore still be checked before that recording work. C1 alone does not demonstrate this candidate loses that next recording guard. It demonstrates why the proposal cannot quietly grow into a loop or execute recording/publish under earlier preparation.

The narrower Core issue is the removed observation: the old `finish(done)` catalog progress, next handoff's independent preparation, parent version/hash, actual stamp, scheduling return and potential finalization check are no longer the same sequence. A combined parent publication must still increment exactly one parent version; simply skipping two versions violates `ValidationLedger._publish`. Catalog `publish_progress` permits monotone native progress, but this does not authorize delayed adoption or bless changed observation semantics. Native commit followed by catalog conflict already has explicit recovery ownership. The Core owner must decide the new observation map, including reply loss, failure and cold reopen. See [`_session_checkpoint.py:534–565`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_session_checkpoint.py#L534-L565) and [`upload_journal_validation_jobs.py:474–544`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/upload_journal_validation_jobs.py#L474-L544).

## 4. Failure, capacity and receiving stay with their current owners

`StaleSemanticFinish` is a `RuntimeError`. A child load failure propagates through `JournalValidationSession.advance`, which records non-capacity exceptions as session failure. The Core owner catches only designated semantic exceptions as a semantic outcome; a Finish stale `RuntimeError` instead reaches the generic exception branch, attempts `_drop`, and re-raises. `_drop` must receive the original session, construction, final storage readers and workspace/lease before removing the slot. If receiving itself fails, its exception may become the direct error with the original in Python exception context; the slot remains charged according to the existing closing path. It would be inaccurate to claim every failure is converted to a validation outcome or that every cleanup attempt necessarily completes. Sources: [`_semantic_finish.py:49–54`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/_semantic_finish.py#L49-L54), [`journal_session.py:1558–1599`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/packages/riverhog-provenance/src/riverhog_provenance/journal_session.py#L1558-L1599), [`upload_journal_validation_owner.py:1875–1893`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/upload_journal_validation_owner.py#L1875-L1893) and [`2061–2122`](https://github.com/nashspence/riverhog/blob/d4d7b6535be2cf491b7859cacea2a9ada4ac8d9e/riverhog/src/riverhog_core/services/upload_journal_validation_owner.py#L2061-L2122).

Capacity cannot be generalized into universal no-progress. Within a Finish scan, preceding admitted rows can be committed before a later invocation reports capacity. Cold Core opening can adopt initialized/restored progress before the attempted Native step. A future combined unit must describe whether it committed anything before a capacity/error result; it cannot reuse per-phase budgets or return an unchanged/refused story that hides durable work. The selected candidate runs only the final existing batch and handoff, but its metadata/completion work still needs aggregate admission and updated actual child composition.

This edge is not terminal success and grants no result borrow or source-release authority. Session completion must still validate exact source/prefix/input and freeze the store; Core must still compare terminal journal identity/hash/bytes/tail. Independent readers can outlive the session owner, and `storage_received` is the required storage receiving observation. Existing close behavior cannot be replaced by a counter decrement, elapsed deadline or assumed worker exit.
