# Focused investigation sequence

This is a menu for the integration owner, not a new campaign, acceptance gate or
obligation to adopt the reference probe. #991 owns the cost investigation within
#964; its recorded hold on routine costly trials remains in force. Follow the
current issue decisions if they change. The research envelope is 1,000 / 10,000 /
100,000 members, not an instruction to launch those sizes now.

## Start with a named question

Consume the delivered diagnostic and source map. Select the largest material
unexplained cost, or a repeated unit whose purpose is understood and whose cost
can plausibly be reduced. Name its owning operation, caller, phase, input/state
dimensions, actual invocation count, and the observation that would discriminate
between the remaining explanations. A high call count alone is not proof of
waste. A small measured elapsed time is not proof of growth conformance.

The existing one/two/four-member timings are useful context. They do not justify
rerunning the same ladder without new attribution, nor fitting a completion-time
prediction for 100,000 members. Their N, total bytes, primary journals and fanout
co-vary. Separate those factors when a specific hypothesis warrants another run.

## Select one small contrast

Examples below are proposed diagnostic conditions. They are neither numerical
targets nor a full factorial matrix to execute. Preserve exact output and all
required verification in any maintained publication contrast. Prefer an existing
owner-local test when it can answer the same question more cheaply.

| Question | Small controlled contrast | Evidence that decides the next action |
| --- | --- | --- |
| Does work repeat per member independently of payload volume? | N=1/2/4 with fixed total payload, F=1/C=1/K=2/Q=1; choose an exact total divisible by all sizes. Reuse prior fixed-bytes/member observations only as context unless conditions match. | Actual preparation, SQL, journal-session, checkpoint and closure counts; input/output bytes; time by owner; distinct versus repeated identities. |
| Is byte processing the driver? | Fixed N/history; change exact payload bytes while recording chunk/part/unit boundaries. | Bytes hashed/encrypted/copied and calls per actual unit; explain threshold changes rather than labeling them superlinear from elapsed time. |
| Is selected shared-root work multiplied by attachments? | Fixed N=4, C=1, K=2/Q=1 and payload; F=1 versus F=4. | Selected-prefix validation calls and bytes by owning caller; logical history occurrences versus unique physical bytes. |
| Does shared-prefix size interact with fanout? | Fix N/F/payload/K/Q; vary C or actual shared journal frames/bytes. If both F and C matter, use a tiny two-factor contrast deliberately. | Product term in measured primitive work, reconciled with the owner's declared logical-history or unique-history obligation. |
| Do retained physical journals and required dependencies differ? | At fixed N/F/C/payload, vary K with Q fixed; separately vary Q with K fixed. | Physical journal validation, closure traversal, dependencies, retained-state and ciphertext reads; exact scope/custody unchanged. |
| Is unrelated population causing scans? | Populate unrelated catalog/prepared state in a targeted owner test, keeping selected output fixed. | Actual scanned rows/bytes or supported VM work, query plan and selected output; returned-row count alone is insufficient. |
| Is repeated fixture/SDK construction expensive? | First count and time existing client/portal/executor/primary construction. If material, compare an already-supported bounded batch with the same small exact work. | Setup versus useful work, batch/queue counts and exact failure/receiving behavior. Record changed conditions; do not call it the old benchmark. |
| Is there independent ready work waiting unnecessarily? | Two tiny independent jobs, one with controlled delay; inspect existing scheduler/owner tests first. | Ready/admitted/start/end/join/received timeline, resource grants, queue/refusal reasons and unaffected independent progress. |
| Are retries or cleanup multiplying work? | Targeted interruption at a real owner boundary, then resume the exact original under existing tests. | Attempt lineage, preserved confirmed work, repeated primitive counts, retained grants and actual original/resource receiving. |

Never normalize away failed/interrupted attempts. A restarted operation's work
includes abandoned preparation and receiving when the owning contract requires
it. Any cache contrast must state which cache was fresh or evicted; the maintained
Native reader states do not clear OS caches.

## From evidence to a change

For demonstrated repetition, first distinguish required current authority or
custody checks, justified repeated validation under a new owner/identity, and
work that can be reused under already-approved semantics. Record the selected
identity, invalidation and lifetime boundaries. Preserve original exceptions and
receiving when adding instrumentation or changing scheduling.

An implementation correction belongs with its owner and a meaningful maintained
regression that observes actual work and exact results. For example, observe
unique and repeated validation inputs at the service caller, then retain the
existing changed-bytes/current-fence/history tests. A synthetic counter that
simply repeats the proposed formula is not that evidence. Read the exact
source-owned declaration and delegate coverage before claiming conformance.

Instrumentation accepted for continued use belongs under the current
`make profile` path and its maintained tests. The supplied probe remains a
disposable reference experiment. Receipt validity, observer coverage, failures,
clock accounting and actual process/workspace receiving need assertions if that
instrumentation is adopted. Do not introduce a second profiling CLI or duplicate
the repository's growth/qualification registry.

## Concurrency decision

Show independent ready work and the dependency that delays it before changing
capacity. Separate SDK executor queues, durable due work, resource-admission
refusals, active workers and completed-but-unreceived slots. Count CPU/work across
owners; use overlap and dependency intervals for elapsed critical-path time.
Defaults and observed thread counts do not establish utilization or speedup.

Prefer reductions in unnecessary work before adding concurrency that would hide
that work. A concurrency change must retain bounded admission, exact per-scope
exclusion, terminal headroom, authority fences and original receiving. Existing
semantics-preserving implementation choices remain with integration. Escalate
only a concrete new semantic/security/custody decision, with evidence and a
narrow proposed trade-off.
